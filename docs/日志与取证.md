# 日志与取证

> 目标：设备再出事时，**不要再只剩一张手机拍屏的照片**。

## 一、为什么专门做这一层

2026-09-21 设备在跑备份时整机卡死，屏幕和串口一直在刷 RCU stall 报告。
重启后去翻 journald，结果：

```
$ journalctl -b -1 -o short-monotonic | tail -3
[  5783.529396] systemd-timesyncd[285]: Timed out waiting for reply from ...
[  5793.779284] systemd-timesyncd[285]: Timed out waiting for reply from ...
[  5804.029215] systemd-timesyncd[285]: Timed out waiting for reply from ...
$ journalctl -b -1 | grep -c -i "stall"
0
```

**一条 stall 都没有。** 不是 journald 配置错了 —— 之前就已经是
`Storage=persistent`（`/var/log/journal/` 有 machine-id 目录，`--list-boots` 能看到 -4…0）。

真正的原因是物理限制：

> RCU stall / 关中断死等时，内核不再调度用户态进程。
> journald 也是用户态进程 —— 它连 `/dev/kmsg` 都读不了，自然写不进任何东西。

所以设备侧再怎么加脚本，都救不了"整机停摆"这一刻。
**能救的只有一条路：让 PC 一直趴在串口上录。** 因为 console 输出走的是 printk
原子路径，不需要任何用户态参与。

结论沉淀成三条设计约束：

| 约束 | 原因 |
|---|---|
| 取证必须有一端在**设备之外** | 设备停摆时设备内一切都是死的 |
| 设备侧日志要**尽量早落盘** | 只能保证"停摆前最后一刻"，所以延迟越小越好 |
| 必须有**进度心跳** | 否则无法判断"停摆发生在第几秒"，日志断在哪都是个谜 |

## 二、三层日志体系

```
┌─ L1  PC 侧串口持续记录（z17s-serial-log.ps1）   ← 唯一能扛整机停摆
│      PC 一直读 COM15，实时落盘，带 PC 时间戳锚点
│      顺带消除"串口写阻塞拖死 PID1"的老雷
│
├─ L2  设备侧低延迟守护（z17s-logwatch.py）        ← 停摆前 0.25 秒
│      直读 /dev/kmsg，攒够 8KB 或每 0.25s 就 fdatasync
│      每 10s 打心跳、每 60s 存现场快照
│
└─ L3  journald 加固（10-z17s.conf）               ← 兜底 + 可检索
       SyncIntervalSec 300s → 5s，放开速率限流
```

三层是互补的，不是替代关系：

- **L1** 拿得到整机停摆现场（RCU stall 全文、各 CPU 栈），但只在 PC 插着线并运行记录器时有效
- **L2** 拿得到停摆前最后一刻，且不依赖 PC；快照还能看出"哪个进程挂在哪个内核函数"
- **L3** 提供 `journalctl` 的检索能力（按单元/优先级/时间查），日常排错最顺手

## 三、L1：PC 侧串口持续记录器

### 启动

双击 `host\windows\serial\start-serial-log.cmd`，窗口留着别关。

或手工：

```powershell
.\host\windows\serial\z17s-serial-log.ps1 -OutDir D:\z17s-log
```

产物在 `_z17s\serial-log\`：

| 文件 | 内容 |
|---|---|
| `serial-YYYYMMDD-HHMMSS.log` | 串口原文，每块数据前有 PC 时间戳锚点 |
| `serial-log.status` | 每 10 秒刷新：端口、累计字节、最后数据/心跳时间、重连次数 |

### 特点

- **自动探测 COM 口**：优先取 PnP 里 `VID_0525` 且状态 OK 的那个（当前是 COM15）。
  ⚠️ 注意历史上 COM9/COM11 是 `PID_A4A7` 那套的残留，**别手工指定错**。
- **断线自动重连**：设备重启时 COM 口会消失，脚本会等 6 秒重试，直到重新打开。
- **每次写入都 `Flush($true)`**：真落盘，PC 突然断电也保住已收到的。
- **不会误报停摆**：只有在"曾经收到过至少一次心跳"之后才开始检测，
  所以没装 L2 时不会一直告警。

### 让它在开机时自动跑（可选）

不想每次手动双击，把 `.cmd` 的快捷方式丢进启动文件夹：

```
Win+R → shell:startup → 把 start-serial-log.cmd 的快捷方式粘进去
```

## 四、L2：设备侧低延迟守护

### 安装

```bash
# 在 PC 上
tar -cf - device/usr/local/sbin/z17s-logwatch.py \
          device/etc/systemd/system/z17s-logwatch.service \
          device/etc/systemd/journald.conf.d/10-z17s.conf \
          scripts/install-logwatch.sh \
  | ssh z17s 'rm -rf /tmp/z17s-inst && mkdir -p /tmp/z17s-inst && tar -xf - -C /tmp/z17s-inst'

ssh z17s 'bash /tmp/z17s-inst/scripts/install-logwatch.sh /tmp/z17s-inst'
```

脚本幂等，可反复跑。它会剥掉 CR（CRLF 会让 shebang 变成 `python3\r` 而执行失败）、
做 `py_compile` 自检、装文件、重启 journald、启动服务并验证心跳。

### 产物

都在 `/var/log/z17s-kmsg/`：

| 文件 | 说明 |
|---|---|
| `kmsg-<bootid8>-<启动时刻>.log` | 内核日志。单文件 16MB，保留最近 12 个 |
| `snapshot-<bootid8>.log` | 每 60 秒一段现场快照 |
| `boots.tsv` | 每次开机登记一行（boot_id / release / 首次见到时间 / uptime） |
| `latest` | 指向当前日志的符号链接 |

日志行格式是 `<monotonic 秒> <printk 级别> 正文`：

```
[  3310.604639] <3> z17s-hb uptime=3310 load=0.37/0.22/0.14
[  5804.029215] <4> systemd-timesyncd[285]: Timed out waiting for reply ...
```

### 现场快照能看出什么

每 60 秒记一次：loadavg、内存关键项、**每个 CPU 的 jiffies 分解**、
**D 状态（不可中断睡眠）任务及其 wchan**、关键中断计数、UDC/USB 状态。

其中 D 状态那段最有用 —— 卡死时能直接看出是谁挂在哪个内核函数上：

```
D-task  : pid=1234   comm=kworker/u16:2    wchan=msm_serial_gen_irq
```

⚠️ 快照本身也依赖用户态调度，**整机停摆时同样会停**。它的价值在于
"半卡死"（部分 CPU 还能跑、I/O 长时间阻塞）那种场景。

## 五、L3：journald 加固

`/etc/systemd/journald.conf.d/10-z17s.conf`：

| 项 | 默认 | 现在 | 理由 |
|---|---|---|---|
| `SyncIntervalSec` | 300s | **5s** | 强制断电最多丢 5 秒，而不是 5 分钟 |
| `SystemMaxUse` | 10% (≈4.5G) | 1G | 别把 45G 根分区吃光 |
| `RateLimitBurst` | 10000 | 100000 | 崩溃风暴时不再静默丢消息 |
| `Storage` | auto | persistent | 显式声明，别依赖 auto 的推断 |

修改后 `systemctl restart systemd-journald` 生效。验证有没有写错键名：

```bash
journalctl -b -u systemd-journald -n 30 --no-pager | grep -iE 'unknown|ignoring|invalid'
```

> 刻意**没有**写 `MaxLevelKmsg` —— 参数名大小写在各 systemd 版本有差异，
> 而它能带来的收益很小（内核消息本来就以 WARNING 以上为主）。
> 宁可少一个优化，也不要冒"journald 起不来 = 完全没有系统日志"的风险。

## 六、出事之后怎么判读

### 第一步：看心跳断在哪

```powershell
# PC 侧，串口日志末尾
Get-Content .\_z17s\serial-log\serial-*.log -Tail 40
```

正常长这样：

```
[ 3350.885301] z17s-hb uptime=3350 load=0.26/0.21/0.13
[PC 2026-09-21T14:02:51.438 data]
[ 3360.935881] z17s-hb uptime=3361 load=0.30/0.22/0.14
```

判读法：

- **心跳还在** → 设备活着。日志断只是因为没内核消息，不是卡死。
- **心跳停在 `uptime=NNNN`** → 卡死发生在**开机后第 NNNN 秒**。
  拿 `[PC ...]` 锚点换算成墙上时间，就能对上你当时在干什么。
- **心跳停了但后面还有大量 RCU stall / BUG 输出** → 好消息，现场抓到了，往下看。

### 第二步：确认是不是真的停摆

| 现象 | 结论 |
|---|---|
| 心跳停 + 串口还有输出 | 内核活着，只是调度不平衡 → 还能救 |
| 心跳停 + 串口完全静默 + RNDIS 网卡消失 | 整机停摆 → 只能长按电源 15 秒 |
| 心跳停 + 屏幕黑 | 供电/硬件问题，方向完全不同 |

### 第三步：翻设备侧日志

```bash
# 上一次开机的日志（bootid 前半段能从 boots.tsv 找到）
cat /var/log/z17s-kmsg/boots.tsv

# 当前
less /var/log/z17s-kmsg/latest

# 有明确时间窗时用 journald 更顺手
journalctl -b -1 -k --since "12:40" --no-pager
```

## 七、还没做、但值得知道的

真正想抓"整机停摆那一刻的内核栈"，只有让**内核自己**把现场写进一块重启不清的内存。
这需要重编内核并改 DTS 预留内存：

| 选项 | 作用 | 现状 |
|---|---|---|
| `CONFIG_PSTORE` + `ramoops` | 崩死时 dump 到预留内存，重启后 `/sys/fs/pstore` 可读 | ❌ 未开，且需改 DTS |
| `CONFIG_DETECT_HUNG_TASK` | D 状态超时打印调用栈 | ❌ 未开 |
| `CONFIG_SOFTLOCKUP_DETECTOR` | 软死锁自动检测 + 打印 | ❌ 未开 |
| `CONFIG_MAGIC_SYSRQ` | 能用 SysRq 键强制 dump/重启 | ❌ 未开 |

代价：重编内核（WSL 里约 4 分钟）+ 改 DTS 加 `reserved-memory` 节点 + 刷 boot，
且 DTS 改错有不开机风险（可从 TWRP + T1 备份恢复）。

**当前判断：先不上。** 理由是 L1 的串口记录已经能拿到 stall 报告全文
（里面本来就含 CPU 状态和寄存器），而 ramoops 的边际收益主要在"更早、更完整的内核栈"。
等到某次真的卡在"串口也静默"的场景再动它。
