> 适用：努比亚 Z17S（NX595J），Debian 13 trixie arm64 + 主线 6.12.95+

## 2. 怎么连上它

### 2.1 SSH（日常首选）

手机插上 PC 的 USB 线，等约 1 分钟开机完成后：

```bash
ssh z17s
```

如果没有配别名，用完整命令：

```bash
ssh -i ~/.ssh/z17s_ed25519 root@192.168.137.2
```

`~/.ssh/config` 里对应的别名配置：

```
Host z17s
    HostName 192.168.137.2
    User root
    IdentityFile ~/.ssh/z17s_ed25519
    ServerAliveInterval 30
```

### 2.2 串口控制台（救命通道）

同一根 USB 线还虚拟出一个串口（**115200 8N1**），root 自动登录，**不需要任何认证**。

- 端口号**每次开机都会变**：开机早期是旧 gadget（`VID_0525&PID_A4A7`，COM11 一类），
  开机 +45 秒被 `z17s-usbnet.timer` 换成 configfs 复合 gadget（`VID_0525&PID_A4A2`，COM15）。
  **别信 `SERIALCOMM` 注册表** —— 它会留着已经消失的僵尸端口。只看"当前在场"的设备：
  ```powershell
  Get-PnpDevice -Class Ports -Status OK | Where-Object { $_.InstanceId -like 'USB\VID_0525&PID_*' } |
    Select-Object Status, FriendlyName, InstanceId
  ```
  （记录器已经内置这条判据，理论上你不需要手敲。）
- 工具：PuTTY / MobaXterm，或者本仓库的 `host/windows/serial/_z17s_shell.ps1`
- ⚠️ **重启前后串口会掉**，要关端口 → 等约 50 秒 → 带重试重新打开

**什么时候必须用它**：SSH 连不上、系统卡死、网络服务没起来时 —— 串口是唯一还能说话的地方。

> 📝 **别只在出事时才开串口。** PC 侧常驻记录器
> `host\windows\serial\start-serial-log.cmd`（双击即可）会把 console 输出持续写进
> `_z17s\serial-log\`。**整机卡死时用户态进程全部停摆，设备侧任何脚本都写不出日志，
> 只有 PC 侧一直录才能留下现场。** 设备侧另配了低延迟守护 + 10 秒心跳，
> 重启后看心跳停在第几秒就知道卡死时刻。详见 [日志与取证.md](日志与取证.md)。

### 2.3 1Panel 网页终端

浏览器打开 `http://192.168.137.2:28888/z17s_panel`，登录后在「主机 → 终端」里敲命令。适合不想碰命令行的场景。

## 3. 网络怎么走

### 3.1 架构

```
        ┌─────────────┐   USB 线    ┌──────────────────────┐
        │  PC(Windows)│◄───────────►│  Z17S / Debian 13    │
        └──────┬──────┘             └──────────────────────┘
               │                        usb0: 192.168.137.2/24
               │                        ttyGS0（串口控制台）
        ┌──────▼──────┐
        │ RNDIS 适配器 │  192.168.137.1/24
        │ ICS 共享 NAT │  ← 让手机出公网
        └─────────────┘
```

- 设备侧 **`usb0` 由 NetworkManager 管理**（连接名 `z17s-usb0`），静态地址 `192.168.137.2/24`、DNS `223.5.5.5 + 114.114.114.114`（**不是** PC 的 `192.168.137.1`，原因见 §3.3 末）、`route-metric 1000`
- USB gadget 由 `z17s-usbnet.timer` 在**开机后 45 秒**拉起（不是启动关键路径，所以不会卡开机）
- 复合 gadget = RNDIS 网卡 + ACM 串口，靠 configfs 手工组装

### 3.2 PC 侧让手机出公网（每台主机只需一次）

**双击 `host/windows/setup-rndis.cmd`**（自动弹 UAC 提权）。

它做的是：把 PC 的互联网连接共享给 RNDIS 适配器 → 手机获得透明 NAT 出网。优先走 Windows ICS，
ICS 没接住时自动退到 **WinNAT**（`New-NetNat`）—— 后者才是长期真正生效的那条路，见下文。

> ✅ **每台主机配一次就够，不需要跟着手机重启重跑**（v2 起）。
> 地址写进持久存储、NAT 走 WinNAT（绑网段而非网卡实例），两者都能扛住 USB 重新枚举。
> 📌 实证：09-21 09:28 跑过一次，当天手机 13:07、20:11 两次重启后网络一直通。
>
> ⚠️ 只有在**换 USB 口且 Windows 视作新网卡**、`Get-NetNat` 里 `z17s-usb` 消失、或换了主机时，
> 才需要重跑。详细的判据与验证命令见 [§3.5](#35-插到别的电脑上还能用吗可移植性)。
>
> 另一种会骗人的故障（**和上面完全两回事**）：ICS 的 DNS 代理单独挂掉 ——
> 适配器上 `192.168.137.1` 还在、能 ping 通公网 IP、但域名全部解析失败。
> 我们已把设备 DNS 改成公共 DNS，正常不会再遇到；详见 [修复记录 §15](修复记录.md)。

#### 不想拷文件？三条免文件路径

脚本只是把下面几条系统命令打了包，**文件从来不是必需品**。

**① 图形界面点几下**（最适合别人家的电脑，不用任何文件/命令行）

`控制面板 → 网络连接` → 右键 **Remote NDIS Compatible Device** → 属性 → **共享** →
勾上"允许其他网络用户通过此计算机的 Internet 连接来连接" → 家庭网络连接选**上游那块网卡** → 确定。
（弹 UAC 允许即可。它做的事和脚本一模一样：设 `192.168.137.1` + DHCP + NAT。
设备 DNS 已是公共 DNS，所以 ICS"DNS 代理单独静默失效"那个老毛病不会再咬人。）

**② 一行命令**（管理员 PowerShell，粘贴回车）

```powershell
irm https://raw.githubusercontent.com/c-08/nubia-z17s-debian/main/host/windows/setup-rndis.ps1 -OutFile $env:TEMP\z17s.ps1; Start-Process powershell -Verb RunAs -ArgumentList "-NoProfile -ExecutionPolicy Bypass -File $env:TEMP\z17s.ps1"
```

**③ 手打五条**（想弄明白到底在干什么，或脚本跑不动时）

```powershell
# 管理员 PowerShell。前两条只是"查"，不用管理员权限也能跑
Get-NetAdapter | Where-Object InterfaceDescription -match 'NDIS'   # 记下 RNDIS 那张的 ifIndex -> <R>
Get-NetRoute -DestinationPrefix '0.0.0.0/0'                        # 记下能上网那张的 ifIndex -> <U>

New-NetIPAddress -InterfaceIndex <R> -IPAddress 192.168.137.1 -PrefixLength 24
New-NetNat       -Name z17s-usb -InternalIPInterfaceAddressPrefix '192.168.137.0/24'
Set-NetIPInterface -InterfaceIndex <R> -Forwarding Enabled
Set-NetIPInterface -InterfaceIndex <U> -Forwarding Enabled
Test-Connection 192.168.137.2 -Count 2                             # 通 = 好了
```

📌 **三个下载入口实测都通**（2026-09，10,410 字节一致）：`raw.githubusercontent.com` 2.2s、
`cdn.jsdelivr.net/gh/c-08/nubia-z17s-debian@main/...` 5.5s、`github.com/.../raw/main/...` 5.3s。

PC 上显示「未识别的网络 / 无法连接 Internet」**是正常的** —— ICS 的私有侧就是这个样子，不要试图"修复"它。

### 3.3 降级方案：用户态代理（没有管理员权限时）

如果没法提权跑 ICS，用纯用户态的代理兜底：

```cmd
:: 双击
host\windows\start-proxy.cmd
```

它启动 `z17s-proxy.py`，在 PC 上开两个服务：

| 服务 | 端口 | 作用 |
|---|---|---|
| HTTP CONNECT 代理 | 3128 | 给 Docker 守护进程拉镜像 |
| DNS 中继 | 53 | 让设备能解析域名 |

设备侧要打开 docker 代理开关：

```bash
z17s-netfallback.sh on     # 写入 /etc/docker/daemon.json 的 proxies
z17s-netfallback.sh status # 查看当前状态
z17s-netfallback.sh off    # 关闭
```

⚠️ 三个必须知道的点：

1. **跑代理的 python.exe 必须有防火墙入站放行规则** —— RNDIS 网卡属于 Public 配置文件，入站默认拦截，Windows 会静默丢掉设备发来的连接。连不上时用管理员权限补一条：
   ```
   netsh advfirewall firewall add rule name="z17s-proxy" dir=in action=allow program="<python.exe 完整路径>" protocol=TCP
   ```
   也可以 `set Z17S_PYTHON=<路径>` 指定解释器（`start-proxy.cmd` 支持）。
2. **它只管 Docker 守护进程拉镜像，容器内的流量不走代理。**
3. **DNS 的归属要跟着模式走**：
   - **ICS 模式（默认）**：DNS 固定为公共 DNS `223.5.5.5 / 114.114.114.114`，走 NAT 的 UDP 53。
     **不要**指 `192.168.137.1` —— ICS 的 DNS 代理会静默失效（53 端口无响应）而 NAT 照常工作，
     症状是"能 ping 通 8.8.8.8、域名却全部解析失败"（2026-09-21 青龙装 npm 依赖报 `EAI_AGAIN` 就是这个）。
   - **用户态代理模式（本节，无 NAT）**：得让 DNS 指回 `192.168.137.1`，因为 `z17s-proxy.py` 自带 DNS 中继。
     命令：`nmcli con mod z17s-usb0 ipv4.dns "192.168.137.1" && nmcli device reapply usb0`
     —— 换句话说，**那个代理进程一停，设备 DNS 也会废**。

### 3.4 验证网络是否健康

```bash
# 在手机上
ping -c 3 -I usb0 223.5.5.5                  # 必须显式 -I usb0，否则会走 metric 更低的 Wi-Fi
curl --interface usb0 -I https://mirrors.aliyun.com/
```

正常结果：ping 0% 丢包、`HTTP/1.1 301`。

### 3.5 插到别的电脑上还能用吗（可移植性）

**网络：不能即插即用。** 这套 USB 网络是"和主机 1 对 1 绑定"的，换一台机器必须同时满足两个条件：

| 条件 | 说明 |
|---|---|
| ① 主机认得这个设备 | 只有 **RNDIS** 一种形态（gadget 里是 `acm + rndis`，**没有** ECM/NCM）。Windows 免驱（`0525:a4a2` + IAD 三元组 `ef/04/01` 命中 inbox `rndiscmp.inf`，见 [修复记录 §2.3](修复记录.md)）；Linux 内核有 `rndis_host` 可以绑；**macOS 根本没有 RNDIS 驱动**（只能靠第三方 HoRNDIS kext，现代 macOS 基本装不上） |
| ② 主机必须是 `192.168.137.1` | 手机侧 `usb0` 是 **静态** `192.168.137.2/24`（`ipv4.method=manual`），而且镜像里**连 DHCP 客户端都没装**（`dhclient` / `udhcpc` / `dhcpcd` 全部缺），它**不会**向主机要地址，只会去找 `192.168.137.1` 这个网关。Windows ICS 的共享网段恰好固定是 `192.168.137.0/24` —— 选这个地址就是有意蹭它 |

| 主机 | ① 网卡 | ② 网关 / NAT | 结论 |
|---|---|---|---|
| 当前这台 Windows | 免驱 | 跑一次 `setup-rndis.cmd` | ✅ |
| 别的 Windows 10/11 | 免驱 | 把那台也装一次 ICS（拷 `host/windows/` 过去跑同一个脚本） | ✅ 配置后可用 |
| Linux 主机 | 内核 `rndis_host` | 手工 `ip addr add 192.168.137.1/24 dev usb0` + `ip_forward=1` + MASQUERADE | ⚠️ 未实测 |
| macOS | 无 RNDIS 驱动 | — | ❌ 网络不通（**串口可用**） |
| 路由器 / NAS（OpenWrt 等） | 装 `kmod-usb-net-rndis` | 手工配 NAT | ⚠️ 未实测 |

三条要额外知道的事：

- 🔴 **手机现在唯一的默认路由就是 `usb0 → 192.168.137.1`**（Wi-Fi 没连上时没有任何备份路由）。所以插到一台没配 ICS/NAT 的电脑上，手机是**彻底没有外网**的 —— 不是"网速慢"，是断网。
- **反向共享（手机把网络给电脑，也就是 Android 说的"USB 共享网络"）没有配置。** 手机虽然 `ip_forward=1`，但 NAT 规则只覆盖 `172.17/172.18`（docker 网段），没有 `-s 192.168.137.0/24 -o <上行> -j MASQUERADE`。而且 Wi-Fi 每约 7 分钟崩一次，本来也不适合当上行。
- ✅ **真正"插哪都能用"的是串口。** CDC-ACM 是各系统内置驱动：Windows 出 COM 口、Linux 出 `/dev/ttyACM0`、macOS 出 `/dev/tty.usbmodem*`，且 root 自动登录。换机器时串口永远是你的保底通道。

#### 为什么"配这一端"躲不掉

不是 USB 驱动麻烦（Windows 侧其实**完全免驱**），而是"**谁的网被蹭，谁就得当网关**"：

1. 手机要上网 → 链路另一端的机器必须替它**转发**并做 **NAT**（改源地址），否则回包找不到路；
2. 手机不装 DHCP 客户端 → 它不会"要"地址，主机必须**自己变成** `192.168.137.1`；
3. 这两件事都需要管理员权限 —— 所以只能在主机上做。

对照 Android 原生的"USB 共享网络"为什么插上就能用：那是**反向**的 —— Android 端自己跑 `dnsmasq`(DHCP) + `iptables MASQUERADE`，电脑只是个自动拿地址的客户端。它把"网关"这个角色做进了手机里；而我们的场景是手机蹭电脑的网，角色自然落在电脑身上。

#### 好消息：在这台机器上"配一次就够"

`setup-rndis.ps1` v2 之后已经不依赖 ICS 那种会随网卡重枚举失效的临时绑定。实测真正生效的是两条**持久化**机制：

| 机制 | 现状 | 为什么扛得住 |
|---|---|---|
| 主机地址 | 已写进**持久存储**（`Get-NetIPAddress -PolicyStore PersistentStore` 能看到 `192.168.137.1` 绑在"以太网 3"） | 网卡重新枚举后按接口身份自动套回 |
| NAT | **WinNAT** 实例 `z17s-usb`（`192.168.137.0/24`，`Active=True`），服务 `winnat` 自动启动 | 绑的是**网段**，不是某个网卡实例 |

**实证**：`flash\ics-run.log` 显示脚本最后一次运行是 **09-21 09:28**，而手机在当天 13:07、20:11 各重启过一次（gadget 重新枚举、COM 号都换过），网络全程是通的 —— 也就是这台电脑上**不需要**每次重跑。

> ⚠️ 早期文档里"手机每次重启后要重跑 `setup-rndis.cmd`"是 v1 / 纯 ICS 时代的结论，**现已过时**。只有这几种情况才需要重跑：换了 USB 口且 Windows 视作新网卡、`Get-NetNat` 里 `z17s-usb` 消失、或主机自己换了（新机器本来就要跑一次）。

### 4.1 青龙面板

容器名 `qinglong`，数据目录 `/root/qinglong/data`（**刻意放在 `/root` 下，不归 1Panel 管**，避免被"删除应用"连带删掉）。

```bash
docker ps --filter name=qinglong                          # 看状态
docker logs -f qinglong                                   # 看日志
docker restart qinglong                                   # 重启
docker exec -it qinglong ql resetname                     # 改用户名
docker exec -it qinglong ql resetpwd                      # 改密码
```

**首次启动会显示 `unhealthy` 约 2 分钟，这是正常的** —— 它要生成 gRPC 的 mTLS 证书，在 ARM 上耗时超过内置的 30 秒超时，导致 pm2 重启两次，第三次才成功。判断依据：

```bash
docker logs qinglong | grep "HTTP service started"   # 出现这行才算真好
```

#### 依赖管理：包名必须按 Debian 写（踩过坑）

「依赖管理」分三类，落地位置完全不同：

| 类型 | 青龙实际执行的命令 | 装到哪 |
|---|---|---|
| NodeJS | `pnpm add -g <名>` | `/ql/data/dep_cache/node/global/5/node_modules` |
| Python | `pip3 install <名>` | `/ql/data/dep_cache/python3/lib/python3.11/site-packages` |
| Linux | **宿主系统的包管理器** —— 本机是 Debian 12，即 `apt-get install -y <名>` | 容器内 `/usr`，**容器一被删重建就没了** |

🔴 **Linux 依赖千万别照抄 Alpine 的说明。** node-canvas 官方给的是 apk 写法，照抄会全灭：

```bash
# ❌ Alpine 写法（本机不可用）
apk add --no-cache build-base g++ cairo-dev pango-dev giflib-dev
# ✅ Debian 写法
apt-get install -y build-essential g++ libcairo2-dev libpango1.0-dev libgif-dev
```

- `--no-cache` **不是包名**，是 apk 的开关。当成包名喂给 apt 会直接报
  `E: Command line option --no-cache is not understood in combination with the other options`；
  青龙是逐条安装，这条挂掉整个列表都会变红。
- `build-base` / `cairo-dev` / `pango-dev` / `giflib-dev` 都是 Alpine 名字，Debian 对应
  `build-essential` / `libcairo2-dev` / `libpango1.0-dev` / `libgif-dev`。

⚠️ **装之前先 `apt-get update`**：容器里的索引是镜像构建时留下的（可能已数月），
索引一旧，apt 会按旧版本号去 pool 取包 → 404 → 几秒内失败。症状是"包名明明对却装不上"。

```bash
docker exec qinglong apt-get update
docker exec qinglong apt-get install -y build-essential g++ libcairo2-dev libpango1.0-dev libgif-dev
```

> 全套约 **71 MB**，2026-09-21 已装好（g++ 12.2.0 / make 4.3）。容器若被 `docker rm` 重建，重跑上面两条。
> 另外：`canvas@3.2.3` 走的是**预编译二进制**，本身并不需要这套编译依赖 —— 装它是为了将来需要现场编译的 npm 包。

⚠️ **面板的"已安装"是字符串 grep，会误报**：NodeJS 用 `pnpm ls -g | grep <名>`、Python 用 `pip3 list`。
例如 `canvas` 会被 `jsdom@30.1.0_canvas@3.2.3` 命中而显示"已安装"。
**别只信标签，实测**：`docker exec qinglong node -e 'require("canvas")'`。

依赖记录在 `/root/qinglong/data/db/database.sqlite` 的 `Dependences` 表
（status：0 安装中 / 1 已安装 / 2 安装失败 / 3 删除中 / 4 已删除 / 5 删除失败 / 6 等待 / 7 已取消）。
要改先备份 —— 不能直接 `cp`（WAL 模式），用 sqlite 的 backup API：

#### 跑自己的脚本

脚本放 **`/root/qinglong/data/scripts/`**（宿主）↔ 容器内 **`/ql/data/scripts/`**，面板里"新建任务"填
`node 文件名.js` 或 `task 文件名.py` 即可。

面板点"运行"实际执行的是容器内的：

```bash
bash /ql/shell/task.sh <文件名>
```

`task.sh` → `otask.sh` 会按扩展名选解释器，并注入依赖搜索路径：

| 类型 | 注入 |
|---|---|
| `.js` / `.mjs` | `NODE_PATH=…:/ql/data/dep_cache/node/global/5/node_modules` |
| `.py` | `PYTHONUSERBASE=/ql/data/dep_cache/python3` |
| `.ts` | `ts-node-transpile-only` |

**要手动跑（不开浏览器）时，用同一条命令最接近面板行为：**

```bash
docker exec -e QL_DIR=/ql qinglong bash /ql/shell/task.sh z17s_depcheck.js
```

🔴 **别把测试脚本放 `/tmp` 里 `node /tmp/x.js`**。Node 解析 `require` 的基准是**脚本所在目录**
（不是 cwd），`/tmp` 下往上找不到 `node_modules`，会甩一屏 `Cannot find module` ——
看起来像"依赖没装"，其实只是路径不对。放 `/ql/data/scripts/` 下跑就正常。

**已知坏依赖**（面板标着"已安装"，`require` 就炸，2026-09-21 实测）：

| 包 | 症状 |
|---|---|
| `ts-md5@2.0.1` | 纯 ESM（`"type":"module"`）→ CommonJS `require` 报 `exports is not defined in ES module scope` |
| `jsdom@30.x` | 需要 Node ≥ 22，容器是 20.20.2 → `Iterator is not defined` / `webidl.util.markAsUncloneable is not a function` |
| `jieba` | 包本身损坏，`package.json` 的 `main` 指向不存在的 `index.js` |

✅ 实测可用的全局依赖：`axios` `crypto-js` `canvas` `js-base64` `json5` `moment` `date-fns`
`dotenv` `node-fetch` `ws` `prettytable`（Python 侧：`requests`、`Crypto`/pycryptodome、标准库）。

⚠️ **`prettytable` 这版 `addRow()` 是坏的** —— 恒报 `Rows must be an array of arrays`，
必须一次性 `table.create(fieldNames, rows)`。另外它按**字节**算列宽，**中文表头会错位**，
要漂亮的中文表格得自己按东亚宽字符算宽度。

**canvas 画中文需要有中文字体**：容器只有 DejaVu（西文），中文会变方框。
字体放**持久卷** `/root/qinglong/data/fonts/`，脚本里 `registerFont()` 注册；容器重建也不丢：

```bash
docker exec qinglong sh -c 'cd /tmp && apt-get download fonts-wqy-microhei && dpkg-deb -x *.deb ext && cp ext/usr/share/fonts/truetype/wqy/*.ttc /ql/data/fonts/'
```

仓库自带一个现成的自检脚本 `scripts/qinglong/z17s_depcheck.js`（外加 `.py` 版）：
把三层依赖（NodeJS / Python / Linux 工具链）逐个 `require` + 真实调用一遍，
再出一张 canvas 图，最后汇总成表。装上就是"这台设备的依赖是否真的可用"的答案。

### USB 网络

```bash
systemctl status z17s-usbnet.timer       # 定时器（应为 active）
systemctl show -p Result --value z17s-usbnet.service   # 期望 success
nmcli dev status | grep usb0             # 期望 connected
nmcli -f GENERAL.NM-MANAGED,GENERAL.REASON dev show usb0   # 期望 yes / reason 0
ip -br addr show usb0                    # 期望 192.168.137.2/24
ip route | head -3                       # 期望 default via 192.168.137.1 dev usb0 metric 1000
head -3 /etc/resolv.conf                 # 期望 nameserver 223.5.5.5（ICS 模式下不指 192.168.137.1）
```

> ⚠️ **容器内的 `/etc/resolv.conf` 不会跟着宿主变。** Docker 只在**容器启动那一刻**从宿主
> `resolv.conf` 复制一份（宿主里的 `127.0.0.x` 会被丢弃）。所以改了宿主 DNS 之后，
> **已经在跑的容器还是旧 DNS** —— 要么 `docker restart <容器>`，要么直接改进去：
> ```bash
> docker exec <容器> sh -c 'printf "nameserver 223.5.5.5\nnameserver 114.114.114.114\n" > /etc/resolv.conf'
> ```

## 6. 绝对不要做的事

| 禁止操作 | 后果 |
|---|---|
| 加载 `ipa.ko` | **boot loop**（已写入 `/etc/modprobe.d/10-z17s-unsafe-modules.conf` 黑名单，别移除） |
| 写 `persist` / `modem` / `dsp` / `vendor` / `system` 分区 | 丢失 Wi-Fi MAC、蓝牙 NV，甚至变砖 |
| `modprobe -r ath10k_snoc` | wlan0 之后**再也不出现**，只能重启 |
| 在 Wi-Fi 固件已崩的状态下反复操作 `wlan0` | 实测会触发**整机复位** |
| 把 `z17s-usbnet.service` 挂到 `WantedBy=multi-user.target` | **卡死整个开机**（它和 `z17s-early.service` 抢 USB 资源）—— 必须用 timer 驱动，且不要 `systemctl enable` 这个 service |
| 手写 `/etc/resolv.conf`，或用 NM 的 `dns=none` | 该镜像会忽略 `dns=none`，手写内容会被 NM 冲成空 → **DNS 全废**。正确做法是让 NM 的 `z17s-usb0` 连接带 `ipv4.dns` |
| 在 1Panel 里对 `qinglong` 点"删除" | 会直接 `docker rm` 容器。要删就先想清楚数据在 `/root/qinglong/data` |

## 7. 故障速查

| 现象 | 最可能的原因 | 处置 |
|---|---|---|
| 屏幕/串口长时间停在开机过程 | **串口控制台写阻塞了 systemd PID1** | **打开串口读一下，通常当场解卡**；根治见 [修复记录 §3](修复记录.md) |
| 设备突然从 PC"消失"（ping 不通、端口全关、连串口都没了） | ⚠️ **先看屏幕！** 还在刷 `rcu_preempt kthread starved` = 内核调度停摆（RCU stall），**不是掉电** | 长按电源 15 秒强断电 → 重启后取上次日志；见 [修复记录 §13](修复记录.md) |
| 手机 ping 通 PC 但**完全**上不了网（连公网 IP 都 ping 不通） | PC 侧 NAT 没了（换过 USB 口/换过主机） | 先 `Get-NetNat` 看 `z17s-usb` 在不在，再重跑 `setup-rndis.cmd` |
| **能 ping 通 8.8.8.8，但域名全部解析失败**（npm/apt 报 `EAI_AGAIN`） | PC 侧 ICS 的 **DNS 代理**挂了，而 NAT 还在（53 端口无响应） | DNS 已固定为公共 DNS：`nmcli device reapply usb0` 重刷；**容器还要单独改**（见 §3.4 提示） |
| `ssh` 连不上但串口正常 | `usb0` 没起来 / 没被 NM 接管 | 串口里看 `nmcli dev show usb0` 的 `GENERAL.REASON`，见 [修复记录 §4](修复记录.md) |
| 设备解析不了域名 | `resolv.conf` 空 / **ICS 的 DNS 代理静默失效** / 代理进程停了 | `head /etc/resolv.conf`；`nmcli device reapply usb0`；或重启代理 `start-proxy.cmd` |
| 换了一台电脑后手机上不了网 | 那台机器不是 `192.168.137.1` 或没开 NAT（手机是静态 IP，不会要 DHCP） | 见 §3.5；Windows 上跑 `setup-rndis.cmd`，Linux 需手工配 |
| 容器报 BPF 错误起不来 | 内核缺 `CONFIG_CGROUP_BPF` | 需要重编内核，见 [kernel/README.md](../kernel/README.md) |
| Wi-Fi 突然消失 / 狂刷 `firmware crashed` | WCN3990 固件崩溃（本机宿命） | 只能重启；可以把 Wi-Fi 关掉止损：`nmcli radio wifi off` |
| 做备份/大量 IO 时设备越来越卡、甚至卡死 | **在设备上就地打包根分区**（归档写进了被归档的文件系统） | **不要在手机上打包根分区** → 用 [备份与恢复](备份与恢复.md) 里 T1 / T2a 的分工 |
| **搬超过几百 MB 的数据时整机卡死** | 已知硬件级限制：**「大量存储读」+「USB/RNDIS 持续满载」叠加**（实测 966 MB 即触发） | 改用分块 + 限速：`host/pull-chunks.sh`；整盘镜像走 TWRP + adb。见 [修复记录 §13](修复记录.md) |
| 关机很慢、中途 TCP 端口全连不上 | 已知现象 | 耐心等，不是死机 |

> ⚠️ **"设备从 PC 上消失"的第一件事是看屏幕，不是查供电。**
> 能刷日志 = 内核活着（只是调度停了），方向是抓内核栈；屏幕黑且串口也没了才是供电/硬件问题。

## 8. 日常运维建议

- **把它当"USB 外设"用**，不要指望 Wi-Fi。网络主通道是那根线。
- **供电**：长期运行建议插着充电器，USB 线同时供数据与电。**跑备份等满载任务前务必接充电器。**
- **备份分工**：
  - **T1（关键分区，几十 MB）**：设备侧 `scripts/backup-system.sh`（20 秒）→ PC 侧 `pull-backup.cmd` 拉走
  - **T2a（数据归档）**：PC 侧 `host/pull-chunks.sh`，**分块 + 限速**，可续传
  - **T2b（整盘镜像）**：走 **TWRP + adb**
  - ❌ 不要在手机上打包根分区；❌ 不要把上 GB 数据压到 RNDIS 上搬（都会卡死，见故障速查）
- **重启前**先记一下当前配置有没有改到 `device/` 里没有的东西；改了记得同步回仓库。
- **改任何 `z17s-*` 服务后**记得 `systemctl daemon-reload`。
- **不确定的操作先在串口里试**，串口永远能救回来。
