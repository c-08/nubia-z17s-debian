# Z17S Debian 13 使用说明

> 适用：努比亚 Z17S（NX595J），Debian 13 trixie arm64 + 主线 6.12.95+
> 这份文档面向"日常使用"，故障排查看 [修复记录.md](修复记录.md)。

---

## 1. 设备概览

| 项目 | 值 |
|---|---|
| 机型 | 努比亚 Z17S / NX595J |
| SoC | 高通 MSM8998（骁龙 835） |
| 系统 | Debian 13 trixie arm64 |
| 内核 | `6.12.95+`（主线，非 Android 内核） |
| 主机名 | `nx595j-debian13` |
| 设备序列号 | `5d6d****`（真实值已在公开版本中隐去） |
| 根分区 | `/dev/sda10`，51G（已用约 3.4G） |
| boot 分区 | `/dev/sde18` |
| persist | `/dev/sda2`，28M（挂 `/mnt/persist`，存 Wi-Fi MAC / 蓝牙 NV） |
| 主机名对应 IP | `192.168.137.2`（USB 网络） |
| 登录方式 | `root`（无密码，串口自动登录；SSH 用公钥） |

## 2. 怎么连上它

### 2.1 SSH（日常首选）

手机插上 PC 的 USB 线，等约 1 分钟开机完成后：

```bash
ssh z17s
```

如果没有配别名，用完整命令：

```bash
ssh -i ~/.ssh/z17s_ed25519 root@192.168.137.2
```

`~/.ssh/config` 里对应的别名配置：

```
Host z17s
    HostName 192.168.137.2
    User root
    IdentityFile ~/.ssh/z17s_ed25519
    ServerAliveInterval 30
```

### 2.2 串口控制台（救命通道）

同一根 USB 线还虚拟出一个串口（**115200 8N1**），root 自动登录，**不需要任何认证**。

- 端口号会变：`g_serial` 阶段是 COM11，configfs 接管后是 **COM15**。以注册表为准：
  ```
  reg query "HKLM\HARDWARE\DEVICEMAP\SERIALCOMM"
  ```
- 工具：PuTTY / MobaXterm，或者本仓库的 `host/windows/serial/_z17s_shell.ps1`
- ⚠️ **重启前后串口会掉**，要关端口 → 等约 50 秒 → 带重试重新打开

**什么时候必须用它**：SSH 连不上、系统卡死、网络服务没起来时 —— 串口是唯一还能说话的地方。

> 📝 **别只在出事时才开串口。** PC 侧常驻记录器
> `host\windows\serial\start-serial-log.cmd`（双击即可）会把 console 输出持续写进
> `_z17s\serial-log\`。**整机卡死时用户态进程全部停摆，设备侧任何脚本都写不出日志，
> 只有 PC 侧一直录才能留下现场。** 设备侧另配了低延迟守护 + 10 秒心跳，
> 重启后看心跳停在第几秒就知道卡死时刻。详见 [日志与取证.md](日志与取证.md)。

### 2.3 1Panel 网页终端

浏览器打开 `http://192.168.137.2:28888/z17s_panel`，登录后在「主机 → 终端」里敲命令。适合不想碰命令行的场景。

## 3. 网络怎么走

### 3.1 架构

```
        ┌─────────────┐   USB 线    ┌──────────────────────┐
        │  PC(Windows)│◄───────────►│  Z17S / Debian 13    │
        └──────┬──────┘             └──────────────────────┘
               │                        usb0: 192.168.137.2/24
               │                        ttyGS0（串口控制台）
        ┌──────▼──────┐
        │ RNDIS 适配器 │  192.168.137.1/24
        │ ICS 共享 NAT │  ← 让手机出公网
        └─────────────┘
```

- 设备侧 **`usb0` 由 NetworkManager 管理**（连接名 `z17s-usb0`），静态地址 `192.168.137.2/24`、DNS `192.168.137.1`、`route-metric 1000`
- USB gadget 由 `z17s-usbnet.timer` 在**开机后 45 秒**拉起（不是启动关键路径，所以不会卡开机）
- 复合 gadget = RNDIS 网卡 + ACM 串口，靠 configfs 手工组装

### 3.2 PC 侧让手机出公网（必需，且每次重启都要做）

**双击 `host/windows/setup-rndis.cmd`**（自动弹 UAC 提权）。

它做的是：开启 Windows ICS（Internet 连接共享），把 PC 的互联网连接共享给 RNDIS 适配器 → 手机获得透明 NAT 出网。

> ⚠️ **手机每次重启后都要重跑一次。**
> 原因：USB 重新枚举后，Windows 注册表里的 ICS 绑定记录
> （`HKLM\SYSTEM\CurrentControlSet\Services\SharedAccess\Parameters\Interfaces`）会消失。
> 症状特别能骗人：**适配器上 `192.168.137.1` 还在、手机也能 ping 通 PC，但就是出不了公网**。
> 这不是手机坏了。

PC 上显示「未识别的网络 / 无法连接 Internet」**是正常的** —— ICS 的私有侧就是这个样子，不要试图"修复"它。

### 3.3 降级方案：用户态代理（没有管理员权限时）

如果没法提权跑 ICS，用纯用户态的代理兜底：

```cmd
:: 双击
host\windows\start-proxy.cmd
```

它启动 `z17s-proxy.py`，在 PC 上开两个服务：

| 服务 | 端口 | 作用 |
|---|---|---|
| HTTP CONNECT 代理 | 3128 | 给 Docker 守护进程拉镜像 |
| DNS 中继 | 53 | 让设备能解析域名 |

设备侧要打开 docker 代理开关：

```bash
z17s-netfallback.sh on     # 写入 /etc/docker/daemon.json 的 proxies
z17s-netfallback.sh status # 查看当前状态
z17s-netfallback.sh off    # 关闭
```

⚠️ 三个必须知道的点：

1. **跑代理的 python.exe 必须有防火墙入站放行规则** —— RNDIS 网卡属于 Public 配置文件，入站默认拦截，Windows 会静默丢掉设备发来的连接。连不上时用管理员权限补一条：
   ```
   netsh advfirewall firewall add rule name="z17s-proxy" dir=in action=allow program="<python.exe 完整路径>" protocol=TCP
   ```
   也可以 `set Z17S_PYTHON=<路径>` 指定解释器（`start-proxy.cmd` 支持）。
2. **它只管 Docker 守护进程拉镜像，容器内的流量不走代理。**
3. 如果设备 DNS 指向 `192.168.137.1`，**那个代理进程一停，设备 DNS 也会废**。想彻底摆脱这个依赖 → 用 ICS。

### 3.4 验证网络是否健康

```bash
# 在手机上
ping -c 3 -I usb0 223.5.5.5                  # 必须显式 -I usb0，否则会走 metric 更低的 Wi-Fi
curl --interface usb0 -I https://mirrors.aliyun.com/
```

正常结果：ping 0% 丢包、`HTTP/1.1 301`。

## 4. 上面跑着什么服务

| 服务 | 地址 | 账号 |
|---|---|---|
| 1Panel 面板 | `http://192.168.137.2:28888/z17s_panel` | `z17s` / 安装时自行设定 |
| 青龙 | `http://192.168.137.2:5700` | `admin` / 自行设定 |
| Docker | `docker` / `docker compose` | — |

### 4.1 青龙面板

容器名 `qinglong`，数据目录 `/root/qinglong/data`（**刻意放在 `/root` 下，不归 1Panel 管**，避免被"删除应用"连带删掉）。

```bash
docker ps --filter name=qinglong                          # 看状态
docker logs -f qinglong                                   # 看日志
docker restart qinglong                                   # 重启
docker exec -it qinglong ql resetname                     # 改用户名
docker exec -it qinglong ql resetpwd                      # 改密码
```

**首次启动会显示 `unhealthy` 约 2 分钟，这是正常的** —— 它要生成 gRPC 的 mTLS 证书，在 ARM 上耗时超过内置的 30 秒超时，导致 pm2 重启两次，第三次才成功。判断依据：

```bash
docker logs qinglong | grep "HTTP service started"   # 出现这行才算真好
```

### 4.2 1Panel

```bash
1pctl status          # 面板状态
1pctl user-info       # 查看访问地址与账号
docker ps | grep 1panel
```

⚠️ **1Panel 的「应用商店 → 已安装」里看不到青龙，这是正常的** —— 那个列表只包含 1Panel 自己安装的应用（在 `/opt/1panel/apps/` 下有 compose 记录）。手工 `docker run` 的容器只在 1Panel 的「容器」页面（Docker 层）可见。**这是刻意设计**，见 §6。

## 5. 日常命令速查

### 系统状态

```bash
systemctl is-system-running              # 期望 running
systemctl --failed                       # 期望 0 failed
systemd-analyze time                     # 开机耗时（正常约 1 分钟）
uptime                                   # 负载 / 运行时长
df -h /                                  # 磁盘
free -h                                  # 内存
```

### USB 网络

```bash
systemctl status z17s-usbnet.timer       # 定时器（应为 active）
systemctl show -p Result --value z17s-usbnet.service   # 期望 success
nmcli dev status | grep usb0             # 期望 connected
nmcli -f GENERAL.NM-MANAGED,GENERAL.REASON dev show usb0   # 期望 yes / reason 0
ip -br addr show usb0                    # 期望 192.168.137.2/24
ip route | head -3                       # 期望 default via 192.168.137.1 dev usb0 metric 1000
head -3 /etc/resolv.conf                 # 期望 nameserver 192.168.137.1
```

### 串口控制台降噪

```bash
dmesg -n 1                               # 临时把内核日志压到最低
```

## 6. 绝对不要做的事

| 禁止操作 | 后果 |
|---|---|
| 加载 `ipa.ko` | **boot loop**（已写入 `/etc/modprobe.d/10-z17s-unsafe-modules.conf` 黑名单，别移除） |
| 写 `persist` / `modem` / `dsp` / `vendor` / `system` 分区 | 丢失 Wi-Fi MAC、蓝牙 NV，甚至变砖 |
| `modprobe -r ath10k_snoc` | wlan0 之后**再也不出现**，只能重启 |
| 在 Wi-Fi 固件已崩的状态下反复操作 `wlan0` | 实测会触发**整机复位** |
| 把 `z17s-usbnet.service` 挂到 `WantedBy=multi-user.target` | **卡死整个开机**（它和 `z17s-early.service` 抢 USB 资源）—— 必须用 timer 驱动，且不要 `systemctl enable` 这个 service |
| 手写 `/etc/resolv.conf`，或用 NM 的 `dns=none` | 该镜像会忽略 `dns=none`，手写内容会被 NM 冲成空 → **DNS 全废**。正确做法是让 NM 的 `z17s-usb0` 连接带 `ipv4.dns` |
| 在 1Panel 里对 `qinglong` 点"删除" | 会直接 `docker rm` 容器。要删就先想清楚数据在 `/root/qinglong/data` |

## 7. 故障速查

| 现象 | 最可能的原因 | 处置 |
|---|---|---|
| 屏幕/串口长时间停在开机过程 | **串口控制台写阻塞了 systemd PID1** | **打开串口读一下，通常当场解卡**；根治见 [修复记录 §3](修复记录.md) |
| 设备突然从 PC"消失"（ping 不通、端口全关、连串口都没了） | ⚠️ **先看屏幕！** 还在刷 `rcu_preempt kthread starved` = 内核调度停摆（RCU stall），**不是掉电** | 长按电源 15 秒强断电 → 重启后取上次日志；见 [修复记录 §13](修复记录.md) |
| 手机 ping 通 PC 但上不了网 | PC 侧 ICS 绑定失效 | 重跑 `setup-rndis.cmd` |
| `ssh` 连不上但串口正常 | `usb0` 没起来 / 没被 NM 接管 | 串口里看 `nmcli dev show usb0` 的 `GENERAL.REASON`，见 [修复记录 §4](修复记录.md) |
| 设备解析不了域名 | `resolv.conf` 空 / 代理进程停了 | `head /etc/resolv.conf`；或重启代理 `start-proxy.cmd` |
| 容器报 BPF 错误起不来 | 内核缺 `CONFIG_CGROUP_BPF` | 需要重编内核，见 [kernel/README.md](../kernel/README.md) |
| Wi-Fi 突然消失 / 狂刷 `firmware crashed` | WCN3990 固件崩溃（本机宿命） | 只能重启；可以把 Wi-Fi 关掉止损：`nmcli radio wifi off` |
| 做备份/大量 IO 时设备越来越卡、甚至卡死 | **在设备上就地打包根分区**（归档写进了被归档的文件系统） | **不要在手机上打包根分区** → 用 [备份与恢复](备份与恢复.md) 里 T1 / T2a 的分工 |
| **搬超过几百 MB 的数据时整机卡死** | 已知硬件级限制：**「大量存储读」+「USB/RNDIS 持续满载」叠加**（实测 966 MB 即触发） | 改用分块 + 限速：`host/pull-chunks.sh`；整盘镜像走 TWRP + adb。见 [修复记录 §13](修复记录.md) |
| 关机很慢、中途 TCP 端口全连不上 | 已知现象 | 耐心等，不是死机 |

> ⚠️ **"设备从 PC 上消失"的第一件事是看屏幕，不是查供电。**
> 能刷日志 = 内核活着（只是调度停了），方向是抓内核栈；屏幕黑且串口也没了才是供电/硬件问题。

## 8. 日常运维建议

- **把它当"USB 外设"用**，不要指望 Wi-Fi。网络主通道是那根线。
- **供电**：长期运行建议插着充电器，USB 线同时供数据与电。**跑备份等满载任务前务必接充电器。**
- **备份分工**：
  - **T1（关键分区，几十 MB）**：设备侧 `scripts/backup-system.sh`（20 秒）→ PC 侧 `pull-backup.cmd` 拉走
  - **T2a（数据归档）**：PC 侧 `host/pull-chunks.sh`，**分块 + 限速**，可续传
  - **T2b（整盘镜像）**：走 **TWRP + adb**
  - ❌ 不要在手机上打包根分区；❌ 不要把上 GB 数据压到 RNDIS 上搬（都会卡死，见故障速查）
- **重启前**先记一下当前配置有没有改到 `device/` 里没有的东西；改了记得同步回仓库。
- **改任何 `z17s-*` 服务后**记得 `systemctl daemon-reload`。
- **不确定的操作先在串口里试**，串口永远能救回来。
