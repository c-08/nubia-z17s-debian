### 2.6 一个指纹：IPA 的 interconnect 消费关系已登记、但永远不会 sync

本次启动 +47.07s 有 5 条：

```
qnoc-msm8998 1500000.interconnect: sync_state() pending due to 1e40000.ipa
（1625000 / 1008000 / 1705000 / 17900000 同样）
```

因为这 5 个 icc provider 在等消费者 `1e40000.ipa` 调 `icc_sync_state()`，而它没有驱动、永远不会调。
**含义**：DTS 里的 icc 接线是**被内核认可**的（否则不会登记消费者）；同时也意味着——
**第一次 probe 成功时，这 5 个 qnoc 会同时丢掉 boot 时的带宽票**，这是首个 probe 值得盯的一个点。

### 2.8 ⚠️ 一个必须记住的坑：`grep -i ipa` 会被 SMMU 骗

精确 grep（`1e40000|ipa_fws|ipa_uc|qmi_ipa`）的结果是：**历史所有启动日志里没有任何 IPA 驱动加载记录** ——
也就意味着**移植作者那次复位没留下任何现场**，这既是坏消息（原因未知），也是好消息（要重新取证，而且不难）。

## 3 上游侧证据

### 3.1 主线原生支持 MSM8998 的 IPA

```c
/* drivers/net/ipa/ipa_main.c */
{ .compatible = "qcom,msm8998-ipa", .data = &ipa_data_v3_1 },
```

由 Alex Elder 于 **2021-06 net-next** 合入（`ipa_data-v3.1.c`，533 行）。原始实现来自
**AngeloGioacchino Del Regno（SoMainline）**，并注明 "Jami has been helpful **testing these changes on his hardware**"
—— 即 **真的在有 MSM8998 的机器上跑过**。

### 3.2 但主线**没有** msm8998 的 IPA 设备节点

抓下主线 `arch/arm64/boot/dts/qcom/msm8998.dtsi`（77940 B）逐行确认：

```
94:  ipa_fw_mem: memory@95200000  { reg = <0x0 0x95200000 0x0 0x10000>; no-map; };   ← 64 KiB
99:  ipa_gsi_mem: memory@95210000 { reg = <0x0 0x95210000 0x0 0x5000>;  no-map; };   ← 20 KiB
104: gpu_mem: memory@95600000     { reg = <0x0 0x95600000 0x0 0x100000>; no-map; };  ← 1 MiB
109: wlan_msa_mem: memory@95700000
```

**`grep "ipa@"` 无结果** —— 主线只预留了内存，没有写 IPA 设备节点。
⇒ **我们这个 `ipa@1e40000` 节点是移植作者手写的**（或从下游改写的），**没有任何上游参照物**。
这是本方案最大的变量，也是 §4 那个嫌疑点为什么值得怀疑的原因。

### 3.3 社区状态：MSM8998 的 modem 是 "Partial"

postmarketOS 芯片页（Qualcomm Snapdragon 835 / MSM8998）：

| 组件 | 状态 |
|---|---|
| **Modem（Calls, SMS, Internet）** | **Partial** ← 有人在 MSM8998 上做到了部分 |
| WiFi | **Works** ← 顺带说明：**我们的 WiFi 崩是移植包的 `key_hw_accel` 补丁，不是 SoC 限制** |
| Bluetooth | Works |

对照：SDM845（同为 IPA 平台）的 POCO F1 页面 `Modem: Calls Partial / SMS Partial / **Mobile data Partial**`。
即 **IPA 平台在主线下的移动数据是"能通但需要手工操作"** —— 这正好符合我们的处境。

### 3.4 有现成配方可抄（SDM845 的实操）

postmarketOS 的 Xiaomi Mi A2 Lite 页记录了 IPA 平台起数据面的关键一步：

```bash
qmicli -d qrtr://0 -p --dpm-open-port="hw-data-ep-type=embedded,hw-data-ep-iface-number=1,hw-data-rx-id=4,hw-data-tx-id=5"
killall ModemManager     # 再重启 ModemManager
```

然后 `rmnet_data0` + 一个虚拟接口出现，用 NetworkManager 配 APN 即可。
**参数里的 `rx-id/tx-id` 来自下游内核的 IPA client 枚举** —— MSM8998 的值需要从
`ipa_data-v3.1.c` 的 endpoint 配置反推（这是 D4 的具体活）。

## 4 头号未知：为什么整机复位

### 4.1 机制候选（按可疑度排序）

| # | 机制 | 与"无日志的整机复位"是否吻合 | 怎么验证 |
|---|---|---|---|
| **A** | **`memory-region` 指错区**：写固件的目标物理区不是 IPA 的固件区 → TZ 的 XPU 违规 / SMMU fault → **立即拉复位**（这类违规由 TZ 处理，内核来不及打印） | ★★★ 高度吻合 | 见 4.2 对照表；改 DTS 后重试 |
| B | SMMU streamid 不对 → IPA 访问触发 SMMU fault → 同上 | ★★ | streamid 6368/6370 已与原厂下游一致，**可能性低** |
| C | IPA 固件本身与本机不匹配（`ipa_fws.mbn` 是"同一份"从别处拷来的）→ uC assert | ★★ | 与本机 `vendor` 分区里的那份做只读比对 |
| D | probe 成功瞬间那 5 个 qnoc 丢带宽票 → 某个关键消费者欠压/时钟停 → 崩溃 | ★ | 串口日志能看到 icc 相关行 |

### 4.2 `memory-region` 对照表（**最需要盯的一行**）

| 来源 | IPA 固件区 | 备注 |
|---|---|---|
| **主线 msm8998.dtsi** | `0x95200000` + 64 KiB（`ipa_fw_mem`），另有 `0x95210000` + 20 KiB（`ipa_gsi_mem`） | 参考设计布局 |
| **本机原厂（Android）保留内存清单** | `pil_ipa_gpu_region@95200000` = `0x95200000` + **1 MiB** | 原厂把 IPA/GPU 的 PIL 镜像放这里 |
| **本机内嵌移植 DT 实际值** | **`0x95600000` + 64 KiB** ← IPA 的 `memory-region` 指这里 | ⚠️ 主线把 `0x95600000` 叫 **`gpu_mem`** |
| 移植 DT 里其它 0x956xxxxx 区 | `95610000`+20 KiB、`95615000`+1 MiB、`95715000`+1 MiB | 尺寸像"抄了主线 ipa_fw/gsi 的大小，但换了基地址" |

> **读法**：`0x95600000` 这个 64 KiB 区的**尺寸**和主线的 `ipa_fw_mem` 一模一样（64 KiB），
> 但**基地址**在主线里属于 `gpu_mem`。这既可能是"照着原厂内存图摆的"（那就是对的），
> 也可能是"抄了尺寸抄错了地址"（那就是 A 机制，一击致命）。
> **光靠静态对比无法定案** —— 这正是需要上机做 §5 的 G1 的原因。
>
> 顺带：本机 DT 的 `memory@95200000` 是 **1 MiB，与原厂 `pil_ipa_gpu_region` 的 base+size 完全一致**，
> 所以"指向 0x95200000"是一个现成的备选目标。

**这张表带来的两条重要修正（§4.2 需要按这个读）**：

1. 🔴 **`memory@95200000` 是 1 MiB，不是 64 KiB。** 主线把它叫 `ipa_fw_mem` 时是 **64 KiB**；本机这块是 1 MiB
   （因为原厂 `pil_ipa_gpu_region` 就是 1 MiB）。⇒ D3-b"把 `memory-region` 改指向 `memory@95200000`"
   **不是原样平替**：要么接受 1 MiB 的窗口，要么在该区里切一个 64 KiB 子块。**改 DTS 时必须显式决定**。
2. ✅ **原厂布局其实"就在眼前"**：`0x95600000`(64K) → `0x95610000`(20K) → `0x95615000`(1 MiB) → `0x95715000`(1 MiB)
   四块**首尾相接、独立成段**，与 `0x95200000` 那一块**不相邻**。这个 `0x956xxxxx` 簇就是原厂 IPA/GPU PIL 的地址段
   ⇒ **本机 DTS 作者是照原厂布局重排的，`0x95600000` 很可能本来就是 IPA 固件区**。
   这**削弱了**"指向错区"这一假设（A），把嫌疑更多地推向别的机制（如 TZ XPU 未授权该区、或 firmware-name/reg-names 不匹配）。

> ⚠️ 另记：设备上还挂着一个**只读**的 `/mnt/persist`（`/dev/sda2`，`ro`）。G1 全程不要碰它。

## 7 风险与止损

| 风险 | 等级 | 处置 |
|---|---|---|
| 🔴 **`ipa.ko` 一旦落进 `/lib/modules/…`，开机时 udev 会按 `MODALIAS=of:NipaT(null)Cqcom,msm8998-ipa` 自动加载它** → 若它复位 → **boot loop** | 高 | **只放 `/root/`，只 `insmod` 全路径**；黑名单**全程留着**；到 G2 通过前不写 `/lib/modules` |
| 硬复位（每次约 1~1.5 min 不可用） | 中 | 一次会话 ≤3 次；每次复位后**立刻回到"黑名单 + 无 ipa.ko"的已知好状态** |
| 刷 boot（D3-b） | 中 | 走既有流程：`.config` 逐行 diff 过闸门 → `abootimg -k` → 37MB 读回校验；刷前先 T1 备份 |
| 数据/分区安全 | **低** | 全程不碰 `persist`/`modem`/`dsp`/`vendor`/`system`；只刷 `boot`；`userdata` 只加文件 |
| 最坏情况（改坏 boot） | 低 | TWRP（音量上+电源）刷回原 boot；备份见 [备份与恢复.md](备份与恢复.md) |
| 高负载敏感（历史 §7.3 RCU stall） | 中 | modem 数据面会引入新的中断/NAPI 负载；**即使跑通也要观察稳定性**，别在数据面刚通时叠加高 IO |

**中止条件**（任一命中就收工、回到现状）：
1. G1 连续 3 次复位且串口无任何输出（说明是 TZ 级保护，静态信息不足以定位）
2. 出现任何一次 `persist`/`modem` 相关写入需求
3. 设备出现新的、与蜂窝无关的不稳定（说明触及了 §7.3 那类整机级故障边界）

## 8 诚实边界：我做不到 / 不建议做的

- **不可能"几天全自动"跑完**：涉及刷 boot、复位后的物理状态、以及串口记录器必须由你双击启动
  （工具后台进程约 10 分钟会被杀）。**关键几步需要你在场或明确授权。**
- **不保证成功**。§0 给的就是 1/3 ~ 1/2（跑通一次），且**没有上游参照物**是最大的不确定因素。
- **不碰任何危险分区**，也不为这件事去 `modprobe -r ath10k_snoc` 之类"顺手试一下"的操作。
- 就算蜂窝通了，**它也不会替代 `usb0`**：这台机器的管理通道（SSH + 串口 + RNDIS）在那根 USB 线上，
  蜂窝最多是"多一条出网路径"。真正省事的方案仍然是外挂一个几十块的 4G 随身 WiFi —— **成本 1/100、风险 0**。

## 9 为什么蜂窝值得试，而 WiFi 不值得

| | **WiFi（WCN3990）** | **蜂窝（IPA / MSS）** |
|---|---|---|
| 根因在哪一层 | **modem Q6 里的 Wi-Fi 固件自己 assert** —— 我们改不了 | **AP 侧的 IPA 驱动 / DTS** —— 我们能改 |
| 上游支持 | 无。主线 6.17 与一加 7T（同款芯片）同样必崩 | **IPA v3.1 已在主线**，且有真机测试记录 |
| 本机存在性证明 | 无 | **有**：本机 Android 下 IPA 数据面初始化成功（§2.4） |
| 失败代价 | MSS 崩溃风暴（负载 1.9、开机活不过 7 分钟），且不可逆 | 一次复位（1~1.5 分钟），可回滚 |
| 结论 | ❌ 已定性，不再投入 | ⚠️ **值得一试** |

> 一句话：**WiFi 的锁在固件里且钥匙不在我们手上；蜂窝的锁在 AP 侧，钥匙就是那份 DTS。**
