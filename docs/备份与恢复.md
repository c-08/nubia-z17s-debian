# 系统备份与恢复

> 目标：**无论搞坏什么，都能回到一个已知可用的状态。**

---

## 一、备份策略（四层，按恢复能力递增）

| 层级 | 内容 | 体积 | 通道 | 能救回什么 |
|---|---|---|---|---|
| **T1 关键分区** | boot + persist + 配置 + 包列表 | ~70 MB | 设备侧脚本 → scp | 开不了机、Wi-Fi MAC 丢失、配置被改乱 |
| **T2a 数据归档** | `/etc` `/root` `/opt` `/usr/local` `/home` `var/lib`(去 docker) 等，**分块 + 限速** | ~0.4–1.7 GB | `host/pull-chunks.sh`（RNDIS） | 系统被搞坏、误删应用数据、想整机迁移 |
| **T2b 整盘镜像** | 根分区整段（只取已用部分） | ~4 GB | **TWRP + adb**（不走 RNDIS） | 文件级恢复失败时的兜底 |
| **T3 全分区镜像** | 全部分区 dd | ~60 GB | TWRP + adb | 分区表都被改坏时（很少需要） |

**日常只需 T1 + T2a。**

⚠️ **重要结论（2026-09-21 两次实测）：不要把整盘数据压到 RNDIS 上搬。**

- `T2b / T3` 请走 **TWRP + adb**（TWRP 用另一套内核与 USB 实现，且那时 Debian 没在跑）
- `T2a` 用 `host/pull-chunks.sh`：**分块 + PC 侧限速**，把最要紧的数据排在前面

### ⚠️ 事故一：为什么"打包根分区"必须放到 PC 侧做

**在设备上就地 `tar czf /root/... /` 会把内核拖进 RCU stall 硬卡死，整机失去 USB，只能强断电。**

那次的事故链完整复盘：

1. 脚本里写了 `--exclude="$OUT"`（`/root/z17s-backup`），本意是别把归档打进自己。
   **但 GNU tar 匹配的是成员名 `./root/z17s-backup`，绝对路径模式匹配不上 → 排除静默失效。**
   （实测：`tar -C . --exclude="/bk" .` 仍然打包 `./bk/`；必须写 `--exclude=bk` 或 `--exclude=./bk`。）
   而脚本把 tar 的 stderr 丢进了 `/dev/null`，所以连 "file changed as we read it" 警告都看不到。
2. 结果是同一个分区上「读整个 `/`」+「写一个正在被读的归档」交错进行，IO 压力翻倍。
3. 约 6 分钟后设备卡死，屏幕上只剩 RCU stall 刷屏
   （同一轮 grace period `g1019837` 永远完不成，`fqs` 从 43 涨到 94551 = 永久性卡死，不会自愈）。
4. USB gadget 因调度停摆而无法枚举 → PC 侧看到设备"物理消失"，必须长按电源 15 秒强断电。

### ⚠️ 事故二：改成"流式拉取"**也没能解决** —— RNDIS 承受不了整盘

把归档改到 PC 侧做之后（设备端 `tar -cf -` 只读、不压缩、不落盘），**仍然卡死**。
于是做了一次对照实验，结论很干脆：

| 实验 | 数据量 | 通道 | 结果 |
|---|---|---|---|
| 设备端 `tar -C / -cf - . > /dev/null` | 读满 3.4 GB | **纯磁盘读，不走网络** | ✅ 完整跑完，设备一切正常 |
| 同一份 tar 走 `ssh \| gzip` 拉出 | 传出 966 MB 时中断 | **RNDIS** | ❌ **128 秒后整机硬卡死**（需断电） |

→ **触发条件是"大量存储读" + "USB/RNDIS 持续满载"的叠加**，不是单纯读盘。
和 `docs/修复记录.md` §13 里 RCU 报告点名的线索也吻合：
`RCU_GP_WAIT_FQS` 的 GP kthread 挂在 `cpu=4` 上等一个不来的定时器，
而 `possible timer handling issue on cpu=4` —— 指向 USB gadget（`dwc3`）与定时器/软中断的交互，
和**故障 12**（SMD RPM / UFS 等待循环）同源。

**防呆规则（四条，记牢）：**

| 规则 | 原因 |
|---|---|
| 归档**永远不要**写到被归档的那个文件系统里 | 同分区读写交错 + 归档自包含 |
| 排除模式要和**成员名形态**对齐：`tar -C / -cf - .` 用 `--exclude=./x`；`tar -C / -cf - root` 用 `--exclude=root/x` | GNU tar 用模式比成员名，写错**静默失效**、不报错 |
| tar/gzip 的 `2>/dev/null` 只该用在"确认无用的噪音"上 | 事故一的警告全被吞了，等于自断取证能力 |
| **上 GB 的数据不要走 RNDIS**；要走就分块、限速，并随时准备断电重启 | 事故二：966 MB 就足以把设备跑死 |

**正确做法**：

- 设备端只 `tar -cf -`（不压缩、不落盘），压缩在 PC 上做
- **分块**（每块几百 MB 以内）+ **PC 侧限速**（`host/net-throttle.py`，默认 2 MiB/s）
  —— 限速会通过 TCP 反压让设备端的 tar 一并慢下来
- 最要紧的数据排在最前面；**第一块失败就停手**，别反复冲击已经出问题的设备
- 整盘镜像改走 **TWRP + adb**

## 二、备份产物说明

运行 `scripts/backup-system.sh` 后（默认输出到 `/root/z17s-backup/<时间戳>/`）：

| 文件 | 说明 | 恢复时的用途 |
|---|---|---|
| `00-partitions.txt` | 分区表、blkid、cmdline、各分区字节大小 | **恢复前先看它**，确认分区布局没变 |
| `10-boot-sde18.img.gz` | boot 分区整段（64 MiB，含内核） | 开不了机时直接 dd 回去 |
| `20-persist-sda2.tar.gz` | persist 内容（文件级） | **Wi-Fi MAC / 蓝牙 NV 唯一来源** |
| `21-persist-sda2.img.gz` | persist 分区整段（32 MiB） | 恢复力比 tar 更强 |
| `30-config.tar.gz` | 全部 z17s 配置与 `/usr/local/{sbin,bin}` | 配置被改乱时 |
| `40-packages.txt` | 340 个已安装包 | 重建系统时批量装回来 |
| `50-rootfs-PLAN.txt` | 根分区备份的执行计划（含可直接粘贴的命令） | 告诉你下一步做什么 |
| `50-rootfs-sda10.tar.gz` | 根文件系统 —— **由 PC 侧生成，不在设备上打** | 整机恢复 |
| `MD5SUMS.txt` | 全部产物的 md5 | **恢复前必须校验** |

PC 侧另有 **分块**产物（`host/pull-chunks.sh` → `<时间戳>/*.tar.gz` + `MANIFEST.md`）：

| 分块 | 内容 | 重要性 |
|---|---|---|
| `10-etc` | `/etc` | ★★★ 配置全在这 |
| `20-usr-local` | `/usr/local`（我们自己的脚本） | ★★★ |
| `30-root-core` | `/root`（排除备份目录与离线安装包） | ★★★ 含青龙数据、SSH 密钥 |
| `40-opt` | `/opt`（1Panel） | ★★ |
| `50-usr-lib-firmware` | `/usr/lib/firmware` **110 MB** | ★★★ **GPU 47KB / ADSP 57MB / 功放 28KB / 蓝牙 188KB** —— 121/125 个文件 apt 装不回来（Wi-Fi 只占 5.3 MB） |
| `55-var-lib-state` | `/var/lib`（去 docker） | ★★ apt/dpkg 状态 |
| `60-home` | `/home` | ★ |
| `65-usr-lib-modules` | `/usr/lib/modules` | ★★ 内核模块 |
| `70-usr-rest` | `/usr` 其余部分 | ★ 可由 apt 重建 |
| `80-var-log` | `/var/log` | ○ 排障用 |
| `90-var-lib-docker` | `/var/lib/docker` | ○ 可由 `docker pull` 重建 |

### ⚠️ persist 为什么最重要

`/dev/sda2`（挂 `/mnt/persist`）只有 32 MiB，里面装着：

- `WCNSS_qcom_cfg.ini` —— Wi-Fi 配置
- `bluetooth/.bt_nv.bin` —— **蓝牙 NV（每台机器唯一）**
- `wlan_mac.bin` —— **Wi-Fi MAC 地址**（`dc:f0:90:xx:xx:xx`）
- camera / display / bms / alarm 等模块的校准数据

**这些东西一旦丢失无法再生**（是出厂校准值）。所以备份里**必须有它**，而且恢复时**最需要小心**。

（好消息：本机 persist 里 `.bt_nv.bin` 的值 `01 00 06 a5 40 1e 90 f0 dc` 与设备树硬编码一致，
所以即使丢了也有一定冗余。但 `wlan_mac.bin` 没有退路。）

## 三、把备份拉到 PC（强烈建议）

**设备坏了，设备上的备份也一起没了。** 所以备完立刻拉到 PC。

### 3.1 拉 T1（关键分区，直接在 PC 侧跑一条命令）

```bash
# 从 PC（Git Bash 或任意带 scp 的终端）执行
STAMP=$(ssh z17s 'ls -t /root/z17s-backup | head -1')
mkdir -p /d/z17s-backup/$STAMP
scp -r z17s:/root/z17s-backup/$STAMP/* /d/z17s-backup/$STAMP/
```

或者用仓库里的辅助脚本（如果你在 Windows 上）：

```cmd
host\windows\pull-backup.cmd
```

### 3.2 拉 T2a（数据归档）—— **分块 + 限速**

⚠️ **不要用 `pull-rootfs.sh` 一把梭把整盘拉出来**：实测 966 MB 就把设备跑死了（见上）。

```bash
host/pull-chunks.sh                      # 默认 profile=core：/etc /usr/local /root核心 /opt（最小、最重要）
host/pull-chunks.sh --profile fw         # 只拉 /usr/lib/firmware（块 50）—— 见下，价值与 Wi-Fi 无关
host/pull-chunks.sh --profile data       # + 固件 / var状态 / home / 内核模块（实测 231 MB）
host/pull-chunks.sh --profile full       # + 整个 usr + var/log + docker（最大，风险最高）
host/pull-chunks.sh --rate 1m            # 限速更狠（默认 2 MiB/s）
host/pull-chunks.sh --chunks 10,20,30    # 只拉指定块
```

特性：

- **已存在且 gzip 完好的分块自动跳过** → 中断后直接重跑即可续传
- 每块之间 sleep 5 秒（`--settle`），让设备缓一缓
- **第一块失败就停手**，不反复冲击已经出问题的设备
- 结束生成 `MANIFEST.md`（含每块的成员名形态与恢复示例）+ `MD5SUMS.txt`

它做的事：设备端 `nice -n 19 ionice -c3 tar -C / <排除项> -cf - <路径>`（**只读、不压缩、不落盘**）
→ 管道经 PC 侧 `net-throttle.py` 限速 → `gzip -1` → 落盘 → 逐块校验。

> `pull-rootfs.sh` 保留在仓库里，供"设备已接**充电器**、并且你愿意承担一次断电重启风险"时
> 一把拉全盘使用。默认别用它。

**T2b 整盘镜像请走 TWRP + adb**（`adb pull` 或 `dd`；那时 Debian 没在跑，也就不存在这个卡死问题）。
具体命令见 `docs/修复记录.md` 与 `flash/` 下的刷机笔记。

**✅ 实测：`core` 档跑通了（2026-09-21 14:19）**

| 块 | 内容 | 大小 | 成员数 | 耗时 |
|---|---|---|---|---|
| `10-etc` | 全部系统配置 | 0.4 MiB | 897 | 1s |
| `20-usr-local` | 自装工具 | 56.8 MiB | 41 | 78s |
| `30-root-core` | root 家目录（已排除大 tar/img） | 49.5 MiB | 128 | 46s |
| `40-opt` | 1Panel 本体 | 14.5 MiB | 475 | 25s |

合计 **121 MiB / 约 150 秒**，4 块 `gzip -t` 全通过，设备 load 全程 0.12–0.21、无任何异常。

⚠️ 对照「一、备份策略」里那次事故：**966 MB 不限速直冲 SSH/RNDIS → 128 秒后整机硬卡死**。
这次 2 MiB/s + 分块 + 块间 settle 5s → 平安跑完。**限速就是那条生死线，别擅自改 `--rate 0`。**

**✅ 实测：`fw` 档跑通了（2026-09-21 16:23）**

```
[拉取] 50-usr-lib-firmware  (路径: usr/lib/firmware)
       ✓ 72747519 字节 / 140 个成员 / 65s
```

110 MB / 125 文件 → 压缩后 **69 MiB**，65 秒，设备 load 0.17、串口心跳全程正常。
12 个关键文件与设备侧 **md5 逐一相同（差异 0）**。

#### 🔑 为什么 `/usr/lib/firmware` 值得单独备 —— **它的价值与 Wi-Fi 无关**

`/usr/lib/firmware` 110 MB 里，**Wi-Fi 只占 5.3 MB（约 5%）**。真正被内核加载的是：

| 类别 | 文件 | 体积 | 内核日志证据（`journalctl -k`） |
|---|---|---|---|
| **GPU**（Adreno 540） | `qcom/a530_pfp.fw` `a530_pm4.fw` `a540_gpmu.fw2` | **47 KB** | `[drm:adreno_request_fw] loaded qcom/a530_pm4.fw` |
| **ADSP**（音频子系统） | `qcom/msm8998/nubia/adsp.mdt` + `adsp.b00…b11` | ⊂ 57 MB | `remoteproc1: Booting fw image qcom/msm8998/nubia/adsp.mdt` |
| **扬声器功放** | `tas2555_uCDSP.bin` `tas2555_cal.bin` | 28 KB | `tas2555 1-004c: tas2555_fw_ready: FW Size = 23560` |
| **蓝牙** | `qca/crbtfw21.tlv` `crnv21.bin` | 188 KB | `hci0: QCA Downloading qca/crbtfw21.tlv` |
| Wi-Fi（**用不上**） | `ath10k/` `bdwlan/` | 5.3 MB | 开了约 7 分钟必崩，见 §WiFi 定性 |

> **注意体积的反差**：撑着显卡的那 3 个文件一共 **47 KB**，"没用"的 Wi-Fi 固件反倒有 4.8 MB。
> 光看"110 MB 固件包"这个数字会严重误判 —— 别因为它大就以为主要是 Wi-Fi。

🔑 **125 个文件里只有 4 个属于 Debian 包**（`wireless-regdb` 的 `regulatory.db`），
**其余 121 个是从 Z17S 原厂 ROM 手工提取的** → `apt install linux-firmware` **装不回来**。
这就是它和 `/usr` 里其他可重建文件（`full` 档那 973 MB）的本质区别。

其余目录：`qcom/msm8998/nubia/` 57 MB（ADSP + modem，不可再生）、
`nubia-stock/` 48 MB（原厂副本存档、未加载）、`xiaomi/ipa_fws.mbn` 40 KB（IPA 已禁用）。

💡 **顺带确认：蓝牙是好的**（2026-09-21）—— `hci0` 存在、`bluetoothctl show` 为
`Powered: yes`、MAC `DC:F0:90:xx:xx:xx`。**与 Wi-Fi 崩不崩无关**：BT 走 UART，
不经过那条会崩的 WLAN 固件路径。项目此前把蓝牙列为"未验收"，现可结案。

**恢复方法**：`tar -C / -xzf 50-usr-lib-firmware.tar.gz`（成员名带 `usr/` 前缀），
然后查 `/dev/dri/`、`/proc/asound/cards`、`bluetoothctl show` 三处。
面向使用者的完整步骤在交付包 `D:\z17s-backup\备份恢复教程.md` §7.4。

⚠️ **`--out` 传 Windows 形式路径（`C:/...`）曾让脚本静默退出** —— 第 1 块拉完就没了，
既不报错也没后续输出（Git Bash 的 GNU tar 不认 `C:/...`，`set -e` 下直接死）。
已在 `pull-chunks.sh` 里用 `cygpath` 修掉，见 `docs/修复记录.md` §15.8。
**以后改这个脚本，别把那两处 `cygpath` 删掉。**

### 3.3 校验

拉完在 PC 上再校验一遍：

```bash
cd /d/z17s-backup/$STAMP && md5sum -c MD5SUMS.txt
```

## 四、恢复：按场景选方法

### 场景 A：系统能启动，只是配置被改乱了

最简单，用仓库的部署脚本覆盖回去：

```bash
ssh z17s
cd /root/z17s-debian-ops && bash scripts/install-on-device.sh
```

或者从备份里恢复配置包：

```bash
tar xzf 30-config.tar.gz -C /
systemctl daemon-reload
udevadm control --reload-rules
```

---

### 场景 B：开不了机（boot 分区坏了）

**这是最常见、也最好修的场景。**

#### B-1 进 TWRP

关机 → 按住 **音量上 + 电源** 进 TWRP。

#### B-2 用 adb 把 boot 镜像推上去

⚠️ **TWRP 是 toybox，`dd` 不支持 `bs=1M`、`conv=fsync`，只有 gzip 也没有 `zcat`。**
命令要按 toybox 的写法：

```bash
adb shell
# 在 TWRP 的 shell 里：
mkdir -p /tmp/restore
# 先解压（toybox 的 gzip 支持 -dc）
gzip -dc /sdcard/10-boot-sde18.img.gz > /tmp/restore/boot.img

# 写入 boot 分区 —— 用 bs=4096（toybox 认）
dd if=/tmp/restore/boot.img of=/dev/block/sde18 bs=4096
```

#### B-3 验证（重要）

```bash
# 回读比对（分区 64M，只比写入的长度）
dd if=/dev/block/sde18 bs=4096 count=$((37283112 / 4096)) | md5sum
```

⚠️ **绝不能比整盘 md5** —— 镜像 19 MB、分区 64 MB，整盘 md5 必然不同。

#### B-4 或者用最简单的办法：刷现成的 boot 备份

`flash/boot_prev_before_debian.img`（64 MiB，刷 Debian 前的原始 boot）也可以直接 dd 回去。

---

### 场景 C：整机重装

#### C-1 重建分区与系统

按上游 [huanhuangyun/z17s-debian](https://github.com/huanhuangyun/z17s-debian) 的说明重刷 boot + rootfs。

**重刷前先看 `00-partitions.txt`**，确认：

- `sda10` 的大小（51.9 GiB）没变
- `sde18`（boot，64 MiB）位置没变
- 内核 cmdline 里的 `z17s.rootfs=userdata` 还在

#### C-2 恢复 persist（**最需要小心的一步**）

系统能启动后，把 persist 恢复回去：

```bash
# 方式一：文件级（推荐，风险低）
tar xzf 20-persist-sda2.tar.gz -C /mnt/persist

# 方式二：整段写入（只在文件级恢复失败时用）
# ⚠️ 先确认 /dev/sda2 没被挂载！
umount /mnt/persist
gzip -dc 21-persist-sda2.img.gz | dd of=/dev/sda2 bs=4096
mount /mnt/persist
```

恢复后验证：

```bash
ls -la /mnt/persist/
cat /mnt/persist/wlan_mac.bin        # Wi-Fi MAC 回来了
ls /mnt/persist/bluetooth/           # 蓝牙 NV 回来了
```

#### C-3 恢复根文件系统

⚠️ **不能从正在运行的系统里恢复 `/` 自己**（文件正在被使用，会写坏）。
两个办法：

**办法 1（推荐）：从 TWRP 里恢复**

```bash
# TWRP shell 里
mount /dev/block/sda10 /mnt   # 挂上根分区
cd /mnt
# 清掉旧内容（保留挂载点）
rm -rf ./* 2>/dev/null
# 解压备份（先把 tar.gz push 到 /sdcard）
tar xzf /sdcard/50-rootfs-sda10.tar.gz -C /mnt
```

**办法 2：先重启到另一个系统再恢复** —— 比较麻烦，不推荐。

#### C-4 恢复包（可选）

如果只想装回软件包而不是整盘恢复：

```bash
dpkg --set-selections < 40-packages.txt
apt-get dselect-upgrade
```

## 五、恢复后必做的检查

```bash
# 1. 系统
systemctl is-system-running       # → running
systemctl --failed                # → 0 failed
systemd-analyze time              # → userspace 约 1 分钟

# 2. USB 网络
systemctl is-active z17s-usbnet.timer                    # → active
nmcli dev show usb0 | grep -E "NM-MANAGED|REASON"        # → yes / 0
head -3 /etc/resolv.conf                                 # → nameserver 192.168.137.1

# 3. 容器
docker run --rm alpine:3.20 echo CONTAINER_OK            # → CONTAINER_OK

# 4. persist（关键）
cat /mnt/persist/wlan_mac.bin                            # MAC 地址在
```

PC 侧再验一次：

```cmd
ping 192.168.137.2
```

`ssh z17s` 能进去就说明全链路恢复了。

## 六、做危险操作前的检查清单

在**改分区表 / 刷分区 / 改内核 / 动 persist** 之前，逐条确认：

- [ ] 刚跑过一次 `backup-system.sh`，并且**已经拉到 PC**
- [ ] PC 上 `md5sum -c MD5SUMS.txt` 全部 OK
- [ ] `00-partitions.txt` 已看过，知道当前分区布局
- [ ] **串口能连上**（`host/windows/serial/_z17s_serial_passive.ps1` 能读到输出）
- [ ] 知道怎么进 TWRP（音量上 + 电源）
- [ ] `flash/` 里有可用的 boot 备份

**串口和 TWRP 是你最后的两条退路。动手前确认它们都好用。**

## 七、建议的备份节奏

| 时机 | 做什么 |
|---|---|
| 刚装好、验证通过 | 跑一次完整 T1+T2，拉到 PC |
| 每次改完配置/装完新服务 | 只备份 T1（20 秒的事） |
| 每月一次 | 完整 T1+T2，覆盖到 PC |
| 任何危险操作前 | 无条件完整备份 + 校验 |
