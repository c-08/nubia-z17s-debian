## 1. 容器全都起不来：内核缺 `CONFIG_CGROUP_BPF`

### 现象

装好 Docker，`systemctl status docker` 一切正常，`docker info` 也正常，但**任何容器都起不来**：

```
$ docker run --rm alpine:3.20 echo OK
docker: Error response from daemon: failed to create task for container:
  ... runc: ... bpf_prog_query(BPF_CGROUP_DEVICE) failed: invalid argument
```

⚠️ **最容易走的弯路**：以为是镜像问题 / 容器配置问题，于是去"重装青龙"。
**实测过：`alpine:3.20` 同样失败** —— 只要换最小镜像一试就知道是全盘性故障，跟具体应用无关。

### 取证

```bash
# 1. 用最小镜像验证是不是全盘性
docker run --rm alpine:3.20 echo CONTAINER_OK

# 2. 确认内核配置
zcat /proc/config.gz | grep -E "CONFIG_CGROUP_BPF|CONFIG_BPF_SYSCALL"
# 原版输出：CONFIG_BPF_SYSCALL=y ，CONFIG_CGROUP_BPF 完全不存在
```

### 根因

cgroup v2 的 device controller 需要 `BPF_PROG_TYPE_CGROUP_DEVICE` 程序，这个程序类型由 **`CONFIG_CGROUP_BPF`** 提供。上游的 `z17s_defconfig` 没有打开它，于是 runc 在挂载 device cgroup 时查询 BPF 程序失败，容器创建直接失败。

### 修法

重编内核，只需在 defconfig 里加：

```
CONFIG_CGROUP_BPF=y
```

**闸门只差 3 行**（另外还带上了 `CONFIG_BPF_STREAM_PARSER`）。

```bash
# 生成 .config 后，与"设备上正在跑的内核真实配置"逐行 diff
# 取真值（比 abootimg + extract-ikconfig 方便）：
ssh z17s 'zcat /proc/config.gz' > running.config
diff -u running.config new.config | grep "^+CONFIG"
```

### 验证

```bash
docker run --rm alpine:3.20 echo CONTAINER_OK     # 期望输出 CONTAINER_OK
```

**产物校验值**（本次构建）：

| 文件 | 大小 | md5 |
|---|---|---|
| `boot-nx595j-debian13-cgroupbpf-signed.img` | 37283112 B | `272f07c471ebcf0b52dcf6754e60afbb` |
| `modules-6.12.95+-cgroupbpf.tar.gz` | — | `61ede3aa6e2ca7cd0db424939c86317b` |

刷写方式（在设备上运行，`sde18` 未挂载，可安全直写）：

```bash
# 备份 → 写入 → 回读校验 → 装模块 → depmod
scripts/flash-boot-cgroupbpf.sh
```

⚠️ 脚本里的**回读校验**不能省：写 37283112 字节后回读同样长度比 md5。注意**不能比整盘 md5**（镜像 37MB、分区 64MB，整盘 md5 必然不同）。

## 2. USB 复合 gadget 从零搭起来

目标：**一根 USB 线同时提供"网卡 + 串口控制台"**。Android 内核里 `g_serial` / 现成的复合 gadget 都是现成的，但这条主线内核上四处碰壁。

### 2.1 坑一：`g_multi` 永久不可用

```
$ modprobe g_multi
modprobe: ERROR: could not insert 'g_multi': Invalid argument
```
dmesg: `failed to start g_multi: -22`

**根因**：这棵树的 `drivers/usb/gadget/legacy/multi.c:307` 无条件调用 `can_support_ecm()`，而它依赖 `gadget_is_altset_supported()`，**在本树恒为 false** → 直接返回 `-EINVAL`。

**修法**：放弃 legacy gadget，改用 **configfs** 手工组装。

### 2.2 坑二：串口函数必须用 `acm`，不能用 `gser`

| 函数 | USB 类 | Windows 能认吗 |
|---|---|---|
| `acm` | `USB_CLASS_CDC_DATA`（标准） | ✅ 自带 `usbser.inf` |
| `gser` | `USB_CLASS_VENDOR_SPEC`（厂商自定义） | ❌ 没有驱动，得手动装 |

**结论：串口一律用 `acm`。**

### 2.3 坑三：RNDIS 的 IAD 类码必须是 `ef/04/01`

Windows 有个内置的 RNDIS 驱动 `rndiscmp.inf`，它靠**接口关联描述符（IAD）的三个类码**来匹配。写成别的值，Windows 就认不出这块网卡。

```
bDeviceClass = ef   (Miscellaneous)
bDeviceSubClass = 04
bDeviceProtocol = 01
```

⚠️ **configfs 的类码属性是"两位十六进制字符串"接口**：

```bash
# 正确
printf 'ef' > .../bDeviceClass
# 错误 —— 会静默存成 00，不报错！排查时极难发现
echo '0xef' > .../bDeviceClass
```

### 2.4 坑四：OS 描述符双保险

为了兼容更多 Windows 版本，再加一组 Microsoft OS 描述符：

```bash
echo 0xcd     > os_desc/b_vendor_code     # MS OS 描述符的厂商码
echo MSFT100  > os_desc/qw_sign           # 注意：是 qw_sign，不是 qwSignature
echo RNDIS    > interface.rndis/compatible_id
echo 5162001  > interface.rndis/sub_compatible_id
```

⚠️ 属性名在不同内核版本里改过（`qw_sign` vs `qwSignature`），写错会报"文件不存在"。

### 2.5 坑五：改描述符后必须递增 serial number

Windows 按 **VID/PID/序列号**三元组缓存设备信息。只改描述符、不换序列号的话，Windows 会拿旧的缓存来认设备，**改了个寂寞**。所以每次改描述符都要把序列号往上加（当前值 `Z17SNET0005`）。

### 最终结果

- VID:PID = `0525:A4A2`
- 设备侧：`usb0` = `192.168.137.2/24`，串口 = ttyGS0
- Windows 侧：自动识别为 RNDIS 网卡 + COM 串口，**不用装任何驱动**

## 3. 开机卡死 82 分钟：串口阻塞了 systemd PID1

> 这是最凶、也最有洞察价值的一个。

### 现象

屏幕/串口长时间停在开机过程中，看起来"死机"。但**放足够久，它最终会起来**。

### 取证（关键是**用单调时钟，别用墙上时钟**）

设备时钟会乱跳，所以一切时间判断都基于 `-o short-monotonic`：

```bash
journalctl -b -u z17s-early.service -o short-monotonic
```

结果触目惊心：

| 单元 | 开始 | 结束 | 耗时 |
|---|---|---|---|
| `z17s-early.service` | t=15.6s | t=4969.1s | **4953 秒 ≈ 82.6 分钟** |
| 前 4 次开机的同一个服务 | — | — | 1.19s / 1.40s / 1.25s / 1.25s |

以及：

```bash
systemd-analyze time
# → kernel 3.3s + userspace 1h24min
```

**两个决定性线索**：
1. **同一个服务前面 4 次都只跑 1.3 秒，唯独这次跑了 82 分钟** → 不是代码问题，是"这一次整机停摆"
2. **默认 `TimeoutStartSec=90s` 竟然一次都没触发** → 连 systemd 的超时机制都失效了，说明卡住的是 PID1 自己

进一步定位：卡住前的最后一条日志是 `Starting z17s-early.service...`，下一条 `Finished` 出现在 4969 秒后 —— **卡的位置就是"往控制台写这一行"这个动作**。

### 根因

`console=ttyGS0` 是 **USB gadget 虚拟串口**。当 PC 侧没有人打开这个串口读数据时：

```
tty 缓冲区填满 → 任何往控制台 write() 的操作永久阻塞
```

systemd PID1 恰好在写 `Starting z17s-early.service...` 这一行 → **PID1 卡死在 `write()` 里** → 整个系统的启动流程停摆。

`TimeoutStartSec=90s` 救不了，因为**超时计时和超时处理本身就跑在 PID1 里**。

### 决定性验证

我在 23:24 打开那个 COM 口读了 40 秒 —— **卡了 82 分钟的开机当场恢复**，时间点与 t=4969s 精确吻合。

前 4 次开机正常，是因为当时调试会话一直在读串口。

### 修法

关掉 systemd 的状态行播报（只关这一项，**内核日志照常输出**）：

```ini
# /etc/systemd/system.conf.d/10-z17s-quiet.conf
[Manager]
ShowStatus=no
```

然后：

```bash
systemctl daemon-reexec
```

**为什么这样能修好**：systemd 的 `[ OK ]` / `Starting ...` 状态行是**普通 write**，会阻塞；而内核 printk 走的是**原子路径**（`console_unlock` 里有特殊处理），不会无限期阻塞。所以关掉状态行，串口照样能看内核日志，只是不再有 systemd 那些花哨的行。

### 验证

在一次**完全没有人读串口**的重启里实测：

```
systemd-analyze time → kernel 2.6s + userspace 1min0.4s
z17s-early.service   → 1.24s
```

### ⚠️ 急救口诀

> **开机"卡住"时，先打开串口终端读一下 —— 往往立刻解卡。**

这条在没修复之前救过命；修复之后仍然值得记着，因为任何"控制台输出被阻塞"的场景都适用。

## 4. `usb0` 每次开机都不受 NetworkManager 管

### 现象

`z17s-usb0` 这个 NM 连接配置**完全正确**（静态地址、DNS、metric 都对），但每次开机 `usb0` 都是 `unmanaged`，永远不会自动激活 → `resolv.conf` 只剩一个注释头 → **DNS 全废**。

⚠️ **最容易误判的点**：手工 `nmcli con up z17s-usb0` 能立刻救活 → 于是你以为"配置没问题，是偶发问题" → 白查半天。

### 取证

```bash
nmcli dev show usb0 | grep -E "NM-MANAGED|REASON"
# GENERAL.NM-MANAGED:  no
# GENERAL.REASON:      77 (The device is unmanaged via udev rule)
```

**`REASON=77` 直接点名了凶器是 udev 规则。**

### 根因

NetworkManager 自带的**上游规则**：

```
/usr/lib/udev/rules.d/85-nm-unmanaged.rules:36
ENV{DEVTYPE}=="gadget", ENV{NM_UNMANAGED}="1"
```

**NM 默认拒绝管理一切 USB gadget 网卡** —— 而 `usb0` 正是 configfs 造出来的 gadget 网卡。这跟我们的配置无关，是上游行为。

### 修法

加一条**文件名排序靠后**的规则去覆盖它（udev 按文件名字典序合并，`99-` 在 `85-` 之后）：

```bash
# /etc/udev/rules.d/99-z17s-usb0-managed.rules
ACTION=="add|change", SUBSYSTEM=="net", ENV{INTERFACE}=="usb0", ENV{NM_UNMANAGED}="0"
```

```bash
udevadm control --reload-rules
```

> 顺带一个教训：之前曾用"一个 `z17s-usb0-nm.sh` 脚本手工 `nmcli con up`"来绕过这个问题，结果那个脚本**从来没有真正安装到设备上**，所以一重启就退化。**声明式的规则（udev）比命令式脚本可靠得多。**

### 验证（经真实重启）

```bash
nmcli dev show usb0 | grep NM-MANAGED     # → yes
nmcli dev status | grep usb0              # → connected
head -3 /etc/resolv.conf                  # → nameserver 223.5.5.5（2026-09-21 起；原因见 §15）
```

### 通用教训

> **"配了但没生效"，先读 `GENERAL.REASON`，别急着重写配置。**

## 5. USB 网卡自启把整个开机卡死

### 现象

加了 `z17s-usbnet.service`（挂 `WantedBy=multi-user.target`）想让 USB 网络开机自启，结果**整个开机卡死**，屏幕停在 `Starting z17s-early.service`。

### 根因

`z17s-usbnet.sh` 要**卸载 `g_serial` 并重建 configfs gadget**。而作者自己的 `z17s-early.service` 也在启动关键路径上碰 USB 资源 —— 两者抢同一份 USB 控制器资源，**形成启动死锁**。

### 修法（v3 方案）

改成**定时器驱动，彻底脱离启动关键路径**：

```ini
# z17s-usbnet.service
[Unit]
After=multi-user.target      # 等系统完全起来之后
# 没有 [Install] —— 故意如此，不要 systemctl enable 这个 service

[Service]
Type=oneshot
ExecStart=/usr/local/sbin/z17s-usbnet.sh
TimeoutStartSec=150          # 硬超时，防止再次挂死
```

```ini
# z17s-usbnet.timer
[Timer]
OnBootSec=45                 # 开机 45 秒后触发
AccuracySec=1s
Unit=z17s-usbnet.service

[Install]
WantedBy=timers.target
```

再加两道保险：

1. 脚本里**每个步骤都套 `timeout`**，单步卡住不会拖死整体
2. 失败时调 `restore_gserial()` 回退到 `g_serial`，**至少保证串口控制台还在**（这样还能进去救）

### 验证

```bash
systemctl is-active z17s-usbnet.timer                    # active
systemctl show -p Result --value z17s-usbnet.service     # success
# 实测：开机后 14 秒跑完，boot 完全不受影响
```

## 6. ICS 每次设备重启后失效

### 现象

PC 上开了 Internet 连接共享（ICS），手机能上网。**设备重启后**：

- 手机还能 ping 通 PC
- 但**上不了公网**
- RNDIS 适配器上 `192.168.137.1` 这个地址**还在**

特别能骗人 —— 看起来网络是好的。

### 取证

```powershell
Test-Path 'HKLM:\SYSTEM\CurrentControlSet\Services\SharedAccess\Parameters\Interfaces'
# → False（键整个消失了）
Get-NetNat
# → 空
Get-Service SharedAccess
# → Running（服务在跑，但没绑任何接口）
```

### 根因

USB 重新枚举后，Windows 会给 RNDIS 适配器分配新的接口标识，**ICS 的绑定记录（注册表 `...\SharedAccess\Parameters\Interfaces` 下的键）随之消失** → NAT 不再对这块网卡生效。适配器上的 `192.168.137.1` 只是残留地址，不代表共享还在工作。

**这是 Windows 侧的行为，不是设备的错。**

### 修法

重新绑定。脚本 `host/windows/setup-rndis.ps1` 做成了幂等的：

1. `Restart-Service SharedAccess`
2. 清掉旧的共享绑定
3. 重新 `EnableSharing`
4. **校验注册表键真的建立了**
5. `Get-NetNat` 兜底（如果 ICS 没建 NAT，手动建）
6. 验证端口

```cmd
:: 双击（自动弹 UAC 提权）
host\windows\setup-rndis.cmd
```

### 教训

> **以后每次设备重启都要重跑一次。** 这是已知的、无法在设备侧解决的问题。
> 如果某天你发现"手机 ping 得通但上不了网"，第一反应就应该是它。

## 7. 容器拉镜像报 EOF：代理转发被截断

### 现象

用自己写的用户态代理，`docker pull alpine:3.19` 拉到一半报：

```
unexpected EOF
```

但**小请求（比如 curl 一个网页）完全正常**。

### 根因

代理的转发实现一开始是 `select()` + 非阻塞 socket。在非阻塞 socket 上：

```python
sock.sendall(data)   # → BlockingIOError
```

`sendall` 在**非阻塞** socket 上遇到缓冲区满时会抛 `BlockingIOError` 而不是等待，于是**大响应的后半段被直接丢弃** → 客户端看到 EOF。

小响应装得进缓冲区，所以看不出问题 —— **典型的"小数据正常、大数据出错"型 bug**。

### 修法

改成**阻塞 socket + 每个方向一个线程**：

```python
# 方向 1：客户端 → 上游
threading.Thread(target=pipe_forever, args=(client, upstream)).start()
# 方向 2：上游 → 客户端
threading.Thread(target=pipe_forever, args=(upstream, client)).start()
```

阻塞模式下 `sendall` 会老老实实等缓冲区腾出空间，不会再丢数据。

### 验证

```bash
docker pull alpine:3.19    # 实测 12.3 秒完成
```

### 通用教训

> **凡是"短请求正常、长响应截断"，优先怀疑非阻塞 socket + `sendall` 的组合。**

## 8. 用户态代理连不上（curl 返回 000）

### 现象

代理进程在跑、端口在监听，但设备侧 `curl -x 192.168.137.1:3128 ...` 直接失败（`code=000`，连 TCP 都握不上手）。

### 根因

Windows 把 RNDIS 网卡归到 **Public 配置文件**，而 Public 的**入站默认是拦截**的。所以设备发往 PC 的连接请求被防火墙丢掉。

### 修法

用**已经带放行规则的那个 Python 解释器**来跑代理：

```
<python.exe 的完整路径>
```

只有**已经带 RNDIS 网卡入站放行规则**的程序才能被设备连上。用管理员权限加规则：

```
netsh advfirewall firewall add rule name="z17s-proxy" dir=in action=allow program="<python.exe 的完整路径>" protocol=TCP
```

`start-proxy.cmd` 支持用 `set Z17S_PYTHON=<路径>` 指定解释器。

**为什么不用加防火墙规则？** 因为本机 PowerShell 会话**不是管理员**，加规则需要提权。用现成的放行条目是零权限成本的解法。

## 9. `resolv.conf` 被 NetworkManager 冲成空

### 现象

手工写好了 `/etc/resolv.conf`，重启（或 NM 重载）后**内容被冲掉**，只剩一行注释头 → DNS 全废。

### 根因

试过在 NM 配置里写 `dns=none`（告诉 NM 别管 resolv.conf），**但这个镜像忽略了它** —— 手写的文件仍然被覆写。

### 修法

**别跟 NM 抢 `resolv.conf`，让 NM 自己生成。** 给 `usb0` 的连接配置里带上 DNS：

```ini
# /etc/NetworkManager/system-connections/z17s-usb0.nmconnection
[ipv4]
address1=192.168.137.2/24
dns=192.168.137.1;
gateway=192.168.137.1
method=manual
route-metric=1000
```

这样 NM 生成的 `resolv.conf` 里会自带一条 `nameserver`；Wi-Fi 上线时 NM 还会自动把路由器的 DNS 合并进去。

> 🔄 **2026-09-21 更新**：具体填哪台 DNS 变了 —— 不再是 PC 的 `192.168.137.1`，
> 而是公共 DNS `223.5.5.5;114.114.114.114`（ICS 的 DNS 代理会静默失效，详见 [§15](#15-能-ping-通-ip域名全部解析失败ics-的-dns-代理静默失效)）。
> 结论没变：**DNS 由 NM 的 `ipv4.dns` 提供，谁都不许手写 `resolv.conf`。**

⚠️ 改完用 `nmcli general reload`，**不要 `systemctl restart NetworkManager`** —— 后者会把你自己的 SSH 连接一起弹掉。

## 11. 发布包里可执行文件没有 +x 权限

### 现象

Wi-Fi（当时还没定性）持续崩溃，`MSS crash` 计数飙到 65 次。最后发现是两个用户态守护进程反复崩：

```
/usr/bin/diag-router
/usr/bin/pd-mapper
```

它们**没有可执行权限**（`664`），所以每次 execve 都失败。

### 根因

发布包里的文件权限是 `664`，而部署时用的 `rsync -a` **原样继承了权限**（`-a` = `-rlptgoD`，保留权限位）→ 部署到设备上依然是不可执行的。

### 修法

```bash
chmod +x /usr/bin/diag-router /usr/bin/pd-mapper
```

### 通用判据（值得记）

> 扫整个 rootfs，找出**"有 ELF magic（`\x7fELF`）或 `#!` 开头，但没有 u+x 位"**的文件。
> 这类文件一定会在将来某个时刻静默失败。

```bash
# 简版扫描
find / -type f -perm -u+r ! -perm -u+x -size +4k 2>/dev/null | while read f; do
  head -c4 "$f" | grep -q $'\x7fELF' && echo "NO+X: $f"
done
```

## 12. 内核 `RPMSG_QCOM_SMD=m` 导致卡死在 UFS 等待循环

### 现象

用改过的 defconfig 走一遍 `olddefconfig` 后编出来的内核，**开机卡死在 UFS 初始化**，一直等驱动。

### 根因

`CONFIG_RPMSG_QCOM_SMD` 在 Kconfig 里是多个关键驱动的 `depends on` 上游。它被设成 `=m`（模块）后，`olddefconfig` 会**连带**把一批驱动也压成模块：

```
QCOM_SMD_RPM
QCOM_RPMPD
REGULATOR_QCOM_SMD_RPM
INTERCONNECT_QCOM_*
...
```

而这些是 **UFS 的 supplier（供电/时钟/互连）驱动**。它们变成模块 → 挂在 UFS 上的驱动等到天荒地老也等不到 supplier → **卡死在 UFS 等待循环**。

### 修法

```
CONFIG_RPMSG_QCOM_SMD=y      # 必须是 =y，不能是 =m
```

### 通用教训

> **改 defconfig 后必须逐行 diff。** `olddefconfig` 会因为 `depends on` 关系**静默地**改掉一批你没碰过的选项 —— 而且 `=m` / `=y` 的差异在 diff 里很不起眼，后果却是开不了机。

## 13. 高 IO 任务（备份/编译）跑到一半整机硬卡死（RCU stall），设备从 USB 上消失

> 本节共记录 **三次复现**（09-21 上午备份、09-21 22:51 编译+绘图脚本、以及更早的一次）。
> 越往后证据越全：从"只剩屏幕照片"到"串口全量 + UFS 供电调压超时"。如果只看结论，
> 直接跳到本节的 **[第三次复现](#-第三次复现2026-09-21-2251没有-usb-满载照样-stall--并且第一次抓到硬件侧证据)**。

### 现象

- 根文件系统 tar 打包跑到约 6 分钟（归档 398 MB）时，SSH 突然超时
- PC 侧：`ping` 100% 丢包、22/5700/28888 全 CLOSED、**串口列表只剩 COM1**、
  `Get-PnpDevice -PresentOnly` 里找不到 `0525`/`1D6B`、`192.168.137.1` 也消失
  → 看起来完全像"设备掉电/被拔线"
- **但设备屏幕还在刷内核日志** —— 这是排除"掉电/硬件损坏"的决定性证据

### 取证（**只剩屏幕照片**——日志侧全部不可用）

先说一件对以后很重要的事：**这次卡死的证据不在磁盘上，只在屏幕上。**

- `journalctl -k -b <那次> ` 的内核日志**停在 09:41:22**（青龙容器起来的时刻），
  而备份是 09:58 开始的 —— **整段卡死窗口 journald 一条都没写进去**
  （不奇怪：journald 是用户态进程，调度都停了就没法落盘）
- 本机 **没有 `CONFIG_PSTORE` / `CONFIG_PSTORE_CONSOLE` / ramoops**
  → 控制台输出也没有任何持久化落点，重启即丢

所以下面的读数是**从用户拍的屏幕照片里读出来的**，也是这次唯一的原始证据。
配 `CONFIG_HZ=1000`（1 jiffy = 1 ms）和 `CONFIG_RCU_CPU_STALL_TIMEOUT=21`（每 21 秒报一次）。

```
rcu: INFO: rcu_preempt detected stalls on CPUs/tasks:
rcu:    0-...0: (1 GPs behind) idle=3bc4/1/0x4000000000000000 softirq=379429/379430 fqs=43
      (detected by 6, t=34012 jiffies, g1019837, q=343 ncpus=8)
rcu_preempt kthread timer wakeup didn't happen for 73002 jiffies! g1019837 f0x0 RCU_GP_WAIT_FQS(5) ->state=0x402 ->cpu=4
      possible timer handling issue on cpu=4 timer-softirq=22505
rcu_preempt kthread starved for 73005 jiffies! g1019837 f0x0 RCU_GP_WAIT_FQS(5) ->state=0x402 ->cpu=4
      All rcu_preempt kthreads starving?
rcu: RCU grace-period kthread stack dump:      ← 标题打了，内容为空
rcu: Stack dump where RCU GP kthread last ran: ← 同样为空
```

后续每隔 21 秒重复一轮，`fqs` 从 43 一路涨到 **94551**、`q` 在几百到两万多之间波动。

**判据**（区分"永久卡死"和"瞬时抖动"）：

| 观察 | 含义 |
|---|---|
| `g1019837` **每一轮都完全一样** | grace-period 序号**从未推进** → 那一轮 GP 永远完不成 = 永久卡死，不会自愈 |
| `softirq=379429/379430` **始终不变** | 整个窗口里 CPU0 **只处理了 1 个软中断** → CPU0 实质上停摆 |
| `fqs` 43 → 94551 / `q` 持续波动 | RCU 反复强制静默态扫描、回调不断入队却无人回收 → 内核还在，只是 GP 推不动 |
| `->cpu=4` 且 `possible timer handling issue on cpu=4` | 🔑 **RCU GP kthread 睡在 cpu4 的定时器上，而 cpu4 的 timer softirq 不触发** |
| `->state=0x402` = `TASK_IDLE`、`RCU_GP_WAIT_FQS` | GP kthread 正常休眠等"强制静默态"，**没人来唤醒它** |
| 两个 stack dump **只有标题、内容为空** | 给它发取栈 IPI 也没响应 → 目标 CPU 处于**关中断**状态 |

> ⚠️ **更正**：本节早期版本写过"`t=34012 jiffies` = 开机后 34.0 秒"，
> 并据此推断"设备重启后第 34 秒就卡住"。**这个推断不成立、已删除。**
> `t=` 与 `starved for` 用的是不同的时间基准（同一次报告里前者 34012、后者 73002），
> 不能简单当"开机后多少秒"读。**本次事故发生在开机后约 9.5 小时、备份进行到 6 分钟时**，
> 这一点由 `journalctl --list-boots` 和归档文件的 mtime 实锚，不需要靠 `t=` 推。

**最值得注意的一条**是 `->cpu=4` + `possible timer handling issue on cpu=4`：
GP kthread 本身没坏，它是**在等一个永远不来的定时器唤醒**。
这把矛头从"某个自旋锁"转向了**定时器/软中断在某几个 CPU 上不工作** ——
与本机 `CONFIG_QCOM_SMD_RPM=y`（时钟/带宽调节要走 SMD RPM 与 RPM 通信）这条路径吻合，
和**故障 12** 同源。

### 根因（两层：诱因 + 缺陷）

**诱因（脚本 bug）**：`backup-system.sh` 里 `--exclude="$OUT"` 想排除备份目录，
但 **GNU tar 拿模式去比成员名 `./root/z17s-backup`，绝对路径模式匹配不上 → 静默失效**，
归档把正在增长的自己打进去了。实测（tar 1.35）：

```bash
tar cf - --exclude="/bk" -C . .   # → 仍然打包 ./bk/   ❌ 静默失效
tar cf - --exclude="./bk" -C . .  # → 正确排除         ✅
tar cf - --exclude="bk"   -C . .  # → 正确排除         ✅
```

于是同一分区上"读整个 `/`"和"写正在被读的归档"交错进行，IO 压力翻倍；
而脚本把 stderr 丢进 `/dev/null`，连 `file changed as we read it` 都看不到。

**缺陷（内核/驱动侧）**：内核本身**不该**被 IO 压力搞成永久 stall。本机
`CONFIG_QCOM_SMD_RPM=y` / `CONFIG_QCOM_CLK_SMD_RPM=y` / `CONFIG_INTERCONNECT_QCOM_SMD_RPM=y`
（msm8998 走 **SMD RPM**，不是 RPMh），存储做时钟/带宽调节时要与 RPM 通信；
同类路径在**故障 12** 已暴露过一次（`CONFIG_RPMSG_QCOM_SMD=m` → 卡死在 UFS 等待循环）。
某处自旋等待不返回 → CPU 关中断死等 → 全局 RCU stall。

### ⚠️ 为什么这次连栈都拿不到

本机内核**没开**这几个看门狗/取证开关：

| 选项 | 状态 | 后果 |
|---|---|---|
| `CONFIG_DETECT_HUNG_TASK` | 未开 | 没有 "task blocked for more than 120 seconds" 报告 |
| `CONFIG_SOFTLOCKUP_DETECTOR` | 未开 | 没有软锁检测 |
| `CONFIG_MAGIC_SYSRQ` | 未开 | **不能用 SysRq 主动打印卡住任务的调用栈** |
| `CONFIG_STACKTRACE` | 已开 | 但 RCU 的 dump 要 IPI 被响应，CPU 关中断就没救 |

所以 RCU stall 报告是**唯一**信号，而且它连栈都打不出来 —— 这就是为什么只能看到刷屏、
无法定位到具体函数。

### 修法

1. **根分区只在 PC 侧打包**（治诱因）：设备端 `tar -cf -`（不压缩、不落盘），压缩在 PC 做。
2. **排除模式要和成员名形态对齐**（治那个静默失效）：
   - `tar -C / -cf - .` → 成员名 `./root/...` → 用 `--exclude=./root/x`
   - `tar -C / -cf - root` → 成员名 `root/...` → 用 `--exclude=root/x`
   写反了**不报错、直接失效**（实测 tar 1.35）。
3. tar/gzip 的 `2>/dev/null` 不要滥用（它吞掉了本次唯一的告警）。
4. **想真正定位到函数**：重编内核打开 `CONFIG_DETECT_HUNG_TASK` +
   `CONFIG_SOFTLOCKUP_DETECTOR` + `CONFIG_MAGIC_SYSRQ`（+ 建议加
   `CONFIG_PSTORE` / `CONFIG_PSTORE_CONSOLE`，把控制台落盘，重启也不丢），
   下次卡死时用 SysRq 或 hung-task 报告拿调用栈。
   （重编成本很低：上次改 `CONFIG_CGROUP_BPF` 只花 3 分 53 秒。）

### 后续实测（2026-09-21 12:46）：改到 PC 侧流式拉取**仍然卡死**

改完方案后做了对照实验，结论是**通道本身才是瓶颈**：

| 实验 | 数据量 | 通道 | 结果 |
|---|---|---|---|
| 设备端 `tar -C / -cf - . > /dev/null` | 读满 3.4 GB | **纯磁盘读，不走网络** | ✅ 完整跑完，设备一切正常 |
| 同一份 tar 走 `ssh \| gzip` 拉出 | 传出 **966 MB** 时中断 | **RNDIS** | ❌ **128 秒后整机硬卡死** |

- 两次卡死的 PC 侧签名完全一致：ping 100% 丢包、22/5700/28888 全 CLOSED、
  **連 COM 口和 RNDIS 适配器都消失**、`192.168.137.1` 也没了 → 就是"USB gadget 因调度停摆而无法枚举"
- 说明**「大量存储读」+「USB/RNDIS 持续满载」的叠加**才是触发条件；单纯读盘不会
- 与本节 RCU 报告点名的线索吻合：GP kthread 挂在 `cpu=4` 等一个不来的定时器，
  而 `possible timer handling issue on cpu=4` → 指向 USB gadget（`dwc3`）与定时器/软中断的交互
  （与**故障 12** 的 SMD RPM / UFS 等待循环同源）
- **对策**：
  - 上 GB 的数据**不要走 RNDIS**；要走就**分块 + PC 侧限速**（`host/pull-chunks.sh`
    + `host/net-throttle.py`，默认 2 MiB/s，靠 TCP 反压让设备端 tar 一起慢下来）
  - 整盘镜像改走 **TWRP + adb**（那时 Debian 没在跑，不涉及这个路径）
  - 关键分区（boot / persist / 配置）本来就只有几十 MB，**走 RNDIS 完全没问题** —— 也已拉取成功

### 🔴 第三次复现（2026-09-21 22:51）：没有 USB 满载，照样 stall —— 并且第一次抓到硬件侧证据

当晚为验证一个青龙脚本在设备上跑了编译/绘图任务（scp 两个小文件 + `g++` 编译 + canvas 绘图），
设备再次整机停摆。**这次没有任何大流量 USB 传输**，推翻了"必须叠加 USB 满载"的判断。

串口记录器留下了完整时间线（`uptime` 为设备秒数）：

| uptime | 事件 |
|---|---|
| 9532 → 9542 | `load` 从 0.27 跳到 0.59（任务开始） |
| 9596.9 | RCU stall #1：`4-...0: (1 GPs behind) idle=705c/… softirq=203620/203621 fqs=3654`，`t=21005, g=562913, q=782` |
| 9606.9 | `rcu_preempt kthread starved for 9995 jiffies! … ->cpu=1` |
| 9612 → 9712 | **`load` 单调爬升 1.23 → 3.72，而心跳仍在正常打**（内核还活着） |
| 9669.9 / 9742.9 | stall #2 / #3（`q` 涨到 1864 / 2672） |
| 9748.4 | ⭐ `l26: failed to set load 560000: -ETIMEDOUT` |
| 9748.4 | ⭐ `ufshcd-qcom 1da4000.ufshc: ufshcd_config_vreg_load: vccq set load (ua=560000) failed, err=-110` |
| 9752.9 | GP kthread starved，`->cpu=0` |
| 9712 之后 | 心跳消失 → COM 口丢失 → PC 侧 `未知 USB 设备(设备描述符请求失败)`(ProblemCode 43) |

**这次抓到的三条新判据**：

1. ⭐ **UFS 供电调压超时**：`ufshcd_config_vreg_load: vccq set load … err=-110`（`-ETIMEDOUT`）。
   存储控制器要把 vccq 调到 560 mA 档，走 RPM 通道发出后**等不到回应** →
   这正是"存储 IO 触发"的直接接线，也把本节的怀疑（SMD RPM 路径）从推断变成了证据。
   与**故障 12**（`CONFIG_RPMSG_QCOM_SMD=m` → 卡死在 UFS 等待循环）同源嫌疑。
2. **`g=`（GP 号）与 `softirq=` 全程冻结不变** —— 同一轮 grace period 永不完成；
   同时 `q=`（回调队列）单调堆积 782 → 1864 → 2672。这三者一起看才是"死等"的签名。
3. **`load` 只增不减**（0.27 → 3.72）：不是瞬时尖峰，而是 workqueue 越堆越多 —— 典型"某个
   关键 kthread 卡住、后续任务全部排队"的形态。**它是前兆，不是原因**；看到 load 单调爬升
   就该主动停手。

与 19:22 那次（完全静默、连设备侧 kmsg 采样器都不再落盘）不同，**这次内核还能打印** ——
说明是"部分停摆"：部分 CPU 卡在等 RPM 响应，printk 仍能走。**"还能打印"不等于"还健康"。**

**对策更新**：
- 触发条件从「大量存储读 **+** USB 持续满载」修正为 **「大量存储 IO / 高负载」即可**，USB 满载只是放大器。
- 跑重 IO/编译类任务前先掂量；分批做，别和 scp/ssh 大输出叠加。
- 若想闭环：重编内核开 `CONFIG_SOFTLOCKUP_DETECTOR` + `CONFIG_PSTORE`；
  另可实验性关掉 UFS runtime PM（`/sys/.../ufshc` 的 `rpm_lvl`/`spm_lvl`）对着 vccq 那条证据试。

### 恢复（卡死时怎么办）

1. **长按电源键 15 秒**强断电 —— 内核已死等，软重启没有意义
2. 能开机就先开机，**第一件事**取上次开机的日志：

   ```bash
   journalctl -k -b -1 | grep -A40 "RCU grace-period kthread stack dump"
   ```

3. 如果新开机又在 30–40 秒左右卡死（很可能是崩溃留下的脏日志/文件系统所致），
   进 TWRP 对根分区做一次 `e2fsck -f /dev/block/sda10` 再开机。

### 教训

> **"设备从 USB 上消失" ≠ 掉电或硬件损坏。** 先看屏幕：**还在刷日志 = 内核活着，但调度停了。**
> 一个在刷日志的设备和一台掉电的设备，取证方向完全相反 —— 前者要抓内核栈，后者要查供电。

## 14. 卡死那一整段日志"凭空消失"：journald 自己也是用户态进程

### 现象

承接 §13。设备卡死时屏幕上 RCU stall 报告刷了好几屏（有照片为证），
强断电重启后去翻日志，**那一段一条都没有**：

```
$ journalctl -b -1 --no-pager | tail -3
[  5783.529396] systemd-timesyncd[285]: Timed out waiting for reply from ...
[  5793.779284] systemd-timesyncd[285]: Timed out waiting for reply from ...
[  5804.029215] systemd-timesyncd[285]: Timed out waiting for reply from ...

$ journalctl -b -1 -k | grep -c -i "stall"
0
```

最后一条日志停在 `[5804s]`，而卡死就在那之后。

### 取证

**第一步：先排除"没开持久化"这个最常见解释。**

```
$ ls -la /var/log/journal/
drwxr-sr-x+ 3 root systemd-journal 4096 Apr 14 03:38 .
drwxr-sr-x+ 3 root systemd-journal 4096 Apr 14 03:38 6056bedfe6f94a629886afd28775da5e

$ journalctl --list-boots
-4 7f3c2c7b... Sun 2026-09-20 14:25:29 CST Sun 2026-09-20 17:47:40 CST
-3 a4d6425f... Sun 2026-09-20 17:49:06 CST Mon 2026-09-21 00:20:30 CST
-2 940487d6... Mon 2026-09-21 00:20:28 CST Mon 2026-09-21 10:05:10 CST
-1 480132de... Mon 2026-09-21 10:04:38 CST Mon 2026-09-21 12:47:11 CST
 0 a96afd23... Mon 2026-09-21 12:47:23 CST ...
```

`/var/log/journal/<machine-id>/` 目录存在、`--list-boots` 能列出 -4…0 →
**journald 早就是 persistent 的，跨重启的日志一直都在。**

**第二步：确认 journald 确实记下了别的内核消息。**

boot -1 里共 2830 行，其中内核消息 917 行 —— 不是"整个内核通道断了"。
包括 `KERN_INFO` 级的：

```
[   48.394592] eth0: renamed from vethe638027
[   63.308367] WARNING: CPU: 3 PID: 1394 at drivers/usb/gadget/function/u_serial.c:691 gs_close+0x144/0x260
```

所以问题**只出在卡死那一段**。

### 根因

> **RCU stall / 关中断死等期间，内核不再调度用户态进程。
> journald 是用户态进程 —— 它连 `/dev/kmsg` 都读不了，自然什么都写不出来。**

内核的 printk 走的是原子路径（直接进 ring buffer 并打到 console），
所以**屏幕和串口照刷不误**；而"从 `/dev/kmsg` 搬运到 `/var/log/journal` 文件"
这一步需要用户态调度，就彻底停了。

顺带把 `printk` 的四个字段讲清楚，避免以后误判：

```
$ cat /proc/sys/kernel/printk
4	4	1	7
↑
├─ 第 1 位 console_loglevel = 4
│    只有级别 < 4（即 0=EMERG / 1=ALERT / 2=CRIT / 3=ERR）才输出到 console
│    ⚠️ 所以 WARNING(4) 和 INFO(6) 都不会出现在屏幕/串口上
│    这解释了为什么 RCU stall（KERN_ERR）看得见，而 gs_close WARNING 看不见
├─ 第 2 位 无级别消息的默认级别
├─ 第 3 位 minimum_console_loglevel
└─ 第 4 位 default_console_loglevel
```

注意：这个 4 **不影响** `/dev/kmsg`/`dmesg`/journald 的收集范围
（它们读的是 ring buffer，不受 console_loglevel 限制）——
`eth0: renamed` 这类 INFO 消息能进 journald 就是证据。
它只决定"哪些能上屏幕和串口"。

**所以别把第 1 位改成 7 去"多收日志"** —— 那只会让串口刷屏，
还会把 §3 那个"串口写阻塞拖死 PID1"的雷重新埋回来。

### 修法：三层日志体系（详见 [日志与取证.md](日志与取证.md)）

| 层 | 组件 | 覆盖场景 |
|---|---|---|
| L1 | PC 侧串口持续记录器 `z17s-serial-log.ps1` | **整机停摆**（唯一有效） |
| L2 | 设备侧 `z17s-logwatch.py` | 停摆前 0.25 秒以内 + 现场快照 |
| L3 | journald 加固（`SyncIntervalSec` 300s→5s 等） | 日常排错 + 崩溃前几分钟 |

L1 之所以有效：console 输出不依赖设备端用户态，**PC 只要一直趴在那儿读就行**。
附带好处是串口始终有人读，写缓冲不会填满 —— 顺手拆掉了 §3 那颗雷。

L2 的关键设计是**心跳**：每 10 秒一句 `z17s-hb uptime=NNNN`，
**直写 `/dev/ttyGS0` 串口**。于是重启后：

- 心跳停在 `uptime=NNNN` → 卡死发生在**开机后第 NNNN 秒**
- 心跳还在 → 设备活着，日志断只是因为没有内核消息

> ⚠️ 心跳最初是走 `/dev/kmsg`（`KERN_ERR` 级）发的，靠 printk 广播到串口 —— 这依赖
> `console_loglevel=4` 那套规则。但本机 cmdline 里的 **`console=tty0` 让手机屏幕也是 console**，
> 于是心跳把屏幕刷满、冲掉了 `agetty` 的登录提示符，被误判成"设备卡死"（09-21 实际发生）。
> 现改为**直写串口** + kmsg 侧留 `<7>`(DEBUG) 副本，屏幕恢复干净。
> 详见 [日志与取证.md](日志与取证.md) 的"心跳为什么直写串口"。

### 验证

```
$ cat /var/log/z17s-kmsg/boots.tsv
# boot_id	release	first_seen	uptime_at_start
a96afd23-3161-...	6.12.95+	2026-09-21T14:02:01+08:00	3307.4

$ ls -la /var/log/z17s-kmsg/
kmsg-a96afd23-20260921-140201.log    179059
snapshot-a96afd23.log                  5470
latest -> kmsg-a96afd23-20260921-140201.log
```

PC 侧串口记录器收到的内容（`_z17s/serial-log/serial-*.log`）。
心跳改直写串口后，行首**不再有 `[ 3350.885301]` 这种内核时间戳**：

```
[PC 2026-09-21T15:56:23.025 data]
z17s-hb uptime=10175 load=0.10/0.12/0.09

[PC 2026-09-21T15:56:33.052 data]
z17s-hb uptime=10185 load=0.08/0.11/0.09
```

心跳稳定每 10 秒一次，PC 侧时间戳锚点也对上了 —— 链路打通。

### 教训

> **"日志丢了"要先分清是配置问题还是调度问题。**
> 判据很简单：**看同一次开机里别的日志在不在**。
> 如果在，只有出事的那个窗口是空的 —— 那就不是配置，是那一刻没人能被调度。
> 这种情况下任何"在设备上加脚本"的方案都是徒劳的，
> **取证链路的末端必须放在设备之外。**

> **心跳比日志本身更重要。** 一堆日志断在哪里都可以解释成"当时没消息"，
> 只有周期性的心跳才能把"停摆时刻"钉死。设计任何长时间跑的东西，
> 都值得配一个带序数的心跳。

### 顺带发现（非本次根因，但记一笔）

每次开机都会出现两次这个 WARNING，以及一段 console 切换：

```
[   49.469551] WARNING: CPU: 0 PID: 1 at drivers/usb/gadget/function/u_serial.c:691 gs_close+0x144/0x260
[   51.600057] dwc3 a800000.usb: request 0000000078f8f3cd was not queued to ep1in
[   51.601085] printk: legacy console [ttyGS0] disabled
[   59.760073] printk: legacy console [ttyGS0] enabled
```

是 `u_serial.c` 关闭路径的已知竞争，PID 1 和 `(agetty)` 各触发一次。
内核被标成 `Tainted: G  W`。目前没有观察到它导致功能故障，
但**如果将来出现 USB gadget 相关的诡异问题，这是第一个该回来看的地方**。
（把内核重编成 `ttyGS0` 只做 console、不挂 getty 可以减少触发面。）

## 15. "能 ping 通 IP、域名全部解析失败"：ICS 的 DNS 代理静默失效

### 现象（2026-09-21）

青龙面板装 npm 依赖（`crypto-js` / `prettytable` / `dotenv` / `jsdom-g` / `jsrsasign`）**全部安装失败**：

```
WARN GET https://registry.npmjs.org/crypto-js error (EAI_AGAIN). Will retry in 10 seconds. 2 retries left.
ERR_PNPM_META_FETCH_FAIL GET https://registry.npmjs.org/crypto-js: request to ... failed,
  reason: getaddrinfo EAI_AGAIN registry.npmjs.org
```

**`EAI_AGAIN` = DNS 解析临时失败**，不是"网络不通"，也不是 npm 源的问题。

### 取证：把"不通"拆成四层

```bash
# 设备侧
ping -c 2 -W 2 192.168.137.1     # 网关          → 0% 丢包 0.5ms ✅
ping -c 2 -W 2 8.8.8.8           # 绕过 DNS      → 0% 丢包 60ms  ✅ NAT 在工作
getent hosts registry.npmjs.org  #               → 失败           ❌
cat /etc/resolv.conf             #               → nameserver 192.168.137.1
```

再把"哪台 DNS 活着"逐台问一遍（`_z17s/dnsprobe.py`，最小 A 查询）：

| DNS 服务器 | 结果 |
|---|---|
| `192.168.137.1`（PC 侧 ICS / 代理） | **超时，完全无响应** |
| `223.5.5.5` | ✅ rcode=0，12 个答案 |
| `114.114.114.114` | ✅ rcode=0，12 个答案 |
| `8.8.8.8` | ✅ rcode=0，12 个答案 |

### 根因

**PC 侧 ICS 的 DNS 代理挂了，而 NAT 还活着。** 二者本是同一套共享机制的不同组件，但可以单独失效
→ 症状极具欺骗性：**链路正常、路由正常、能 ping 通公网 IP，只有域名解析全灭。**

> ⚠️ 这和"ICS 绑定失效"（整条路都不通，要重跑 `setup-rndis.cmd`）是**两种不同故障**。
> 一句话判据：**`ping 8.8.8.8` 通 → DNS 层；不通 → NAT 层。**

### 修法

DNS **不要指向 PC**，固定用公共 DNS 走 NAT 的 UDP 53：

```bash
nmcli con mod z17s-usb0 ipv4.dns "223.5.5.5,114.114.114.114"
nmcli device reapply usb0        # 不断链地应用（别 restart NM，会弹掉 ssh）
head -3 /etc/resolv.conf         # → nameserver 223.5.5.5
```

⚠️ **容器要单独改一次**：Docker 只在容器**启动那一刻**从宿主复制 `resolv.conf`，
之后宿主再变它也不跟（容器里那份的文件头写着 `Based on host file: '/etc/resolv.conf' (legacy)`）。

```bash
docker exec <容器> sh -c 'printf "nameserver 223.5.5.5\nnameserver 114.114.114.114\n" > /etc/resolv.conf'
# 或者 docker restart <容器> —— 会重新从宿主拷一份（青龙首次起来要等 ~2 分钟属正常）
```

改完容器内 `curl -o /dev/null -w '%{http_code}' https://registry.npmjs.org/` → `200`。

### 顺带修掉的隐患

`z17s-netwatch.sh` 里有一段老逻辑：Wi-Fi 网关不可达时**手写** `/etc/resolv.conf` 指向 `192.168.137.1`。
这与 [§9](#9-resolvconf-被-networkmanager-冲成空) 的结论直接冲突（NM 与脚本互相踩），
而且写的正是这次失效的那个地址 → **已删除**，DNS 统一交给 NM 的 `z17s-usb0` 连接管。
（该脚本当时处于 `inactive`，不是本次元凶，但属同类隐患。）

### 教训

1. **"能 ping 通 IP" ≠ "网络正常"**。见到 `EAI_AGAIN` / `getaddrinfo` 报错一律先查 DNS，别急着换源。
2. **判 DNS 必须分层**：网关 → NAT（用 IP ping 目标）→ DNS（逐台问）。断在哪层，修法完全不同。
3. **别把 DNS 依赖挂在 PC 的共享服务上** —— ICS 的 DNS 代理、用户态代理进程，都是会静默死的单点。
   只有"公共 DNS 走 NAT"这条依赖最少。
   （例外：走 `z17s-proxy.py` 的无 NAT 模式时必须指回 `192.168.137.1`，靠它自带的 DNS 中继。）
4. **容器有自己的 `resolv.conf`** —— 宿主改了不等于容器改了，Docker 是**复制**语义不是引用语义。

## 16. ttyGS0 上的 agetty 反复重启，把 USB gadget 串口打成 `gs_close` WARN

**现象**：设备运行中整个消失 —— PC 侧串口断流、`ping usb0` 全丢、RNDIS 网卡从 Windows 消失；
Windows 设备管理器里出现 `未知 USB 设备(设备描述符请求失败)`（`ProblemCode 43`）。
**不会自愈，只能长按电源 15 秒断电重启。**

**取证（三条独立证据指向同一时刻）**：

| 来源 | 证据 |
|---|---|
| PC 侧串口记录器 | 最后心跳 19:22:07 → 19:22:41 `read error` → `port lost` |
| Windows PnP | `USB\VID_0000&PID_0002\5&C454196&0&10` 的 `DEVPKEY_Device_LastArrivalDate = 19:22:43`，**就是手机原来那个物理口** |
| 设备侧 kmsg 采样 | 最后一行 `[ 22520.435291]`，**此后连采样器自己都没再落过一行**，无 Oops / 无 panic / 无 RCU stall |

**注意取证顺序**：设备侧的 `/var/log/z17s-kmsg/kmsg-*.log` 是**跨重启保留**的，
重启后回来第一件事就是读上一轮的 `kmsg-<bootid>.log` 尾部 —— 本次就是靠它确认
"死亡瞬间没有任何内核输出"（＝整机停摆，而不是某个驱动报错）。

**根因（可稳定复现的 bug，不是猜测）**：

```
WARNING: CPU: 0 PID: 1393 at drivers/usb/gadget/function/u_serial.c:691 gs_close+0x144/0x260
CPU: 0 UID: 0 PID: 1393 Comm: (agetty) Tainted: G W 6.12.95+ #1
Call trace: gs_close ← tty_release ← __fput ← __fput_sync ← __arm64_sys_close
```

`u_serial.c:691` 处 `gs_close()` 发现 `port->port.count` 已经是 0（引用计数被关多了）。
**WARN 成对出现**，进程名固定是 `Comm: systemd` 和 `Comm: (agetty)`：

```
13:07:40 systemd 关一次 → 13:07:54 (agetty) 关一次
15:41:54 systemd       → 15:41:54 (agetty)
15:42:27 systemd       → 15:42:27 (agetty)
```

⇒ 这是 **`serial-getty@ttyGS0` 反复重启**的签名：systemd 关掉它替服务持有的 tty，
新的 agetty 再关一次自己继承的 → 多关一次。
一个 6h15m 的运行期内出现 **32 次**，旁边总是跟着 `dwc3 a800000.usb: request ... was not queued to ep1in`。

**为什么偏偏是 ttyGS0**：这个 tty 同时被**三方**占用 ——
① 内核 printk console（`console=ttyGS0,115200n8`）；
② agetty 登录提示符；③ 我们 10 秒一次的心跳直写（`z17s-logwatch`）。
agetty 每次看到 tty 状态变化/hangup 就退出并被 systemd 重启 → 反复 open/close。

**处置**：

```bash
systemctl mask serial-getty@ttyGS0.service
```

- 🔴 **必须 mask，不能只 disable**：cmdline 里有 `console=ttyGS0,115200n8`，
  `systemd-getty-generator` 会**每次开机**自动重新生成这个 unit（`disable` 活不过重启）。
  mask 之后连手动 `systemctl start` 都会被拒（`Unit ... is masked`），才真正稳。
- 代价：**失去串口登录 shell**。串口**输出**完全不受影响（内核日志 + 心跳照旧）。
  需要串口 shell 时临时放开：
  `systemctl unmask serial-getty@ttyGS0 && systemctl start serial-getty@ttyGS0`
- 已并入 `scripts/install-logwatch.sh`（幂等，重刷系统后自动生效）。

**回滚**：`systemctl unmask serial-getty@ttyGS0.service`

**⚠️ 未验证**：mask 只是消除了**唯一能看见的那个 bug**，还**没有**证明它就能防住整机停摆。
死亡瞬间没有任何内核输出，所以真实死因仍可能另有其因（与 §13 的 RCU stall 同族）。
要真正闭环，下一步应重编内核打开
`CONFIG_SOFTLOCKUP_DETECTOR` + `CONFIG_PSTORE`（当前都没有），
让下一次停摆能变成可留证的 panic，而不是"照片是唯一证据"。
（可用 `z17s-hb` 心跳断点做时间锚，验证 mask 后是否还复发。）

## 17. 第三种死法"半死态"：网络全通、老服务正常，但任何新会话都建不起来

2026-09-21 23:31 ~ 09-22 00:50（≥80 分钟，不自愈），现场是"看起来全好、其实已经废了"。

### 17.1 现象

```
ping 192.168.137.2          → 0ms，0% 丢包          ← 内核网络正常
Test-NetConnection -Port 22 → TcpTestSucceeded=True  ← 22/5700/28888 全部握手成功
curl http://…:5700/         → HTTP 200，0.03s        ← 青龙页面秒回
curl http://…:28888/…       → HTTP 200，0.01s        ← 1Panel 页面秒回
curl -X POST :5700/api/user/login
                            → {"code":410,"失败次数过多，请20秒后重试"}
                                                        ← **SQLite 读得动！磁盘没坏**
ssh z17s                    → 2m15s 后 "Timeout, server … not responding"
ssh -T z17s (不要 pty)      → 一样卡
```

`ssh -vv` 把真相摊开了：

```
debug1: Server accepts key: …z17s_ed25519 …
Authenticated to 192.168.137.2 ([192.168.137.2]:22) using "publickey".   ← 认证成功！
debug1: channel 0: new session [client-session] (inactive timeout: 0)
debug2: channel 0: send open            ← 发出 CHANNEL_OPEN
…（此后服务端再没回过一个字节，也从不发 CHANNEL_OPEN_CONFIRMATION）
```

1Panel 的表现同源：网页打得开，但**所有 API 返回 `Access Temporarily Unavailable`**
（core 活着、由 systemd 托管的 `1panel-agent` 起不来）。

### 17.2 判据表（照这个顺序打，10 秒定性）

| 层次 | 命令 | 结果 | 说明 |
|---|---|---|---|
| L3 内核网络 | `ping 192.168.137.2` | **通** | 排除掉电 / gadget 死 |
| L4 端口 | `Test-NetConnection -Port 22,5700,28888` | **全 True** | 内核 backlog 会替"没人 accept 的监听 socket"完成三次握手，**所以端口通 ≠ 服务活** |
| 已起进程 | `curl -m10 :5700/` | **200 / 毫秒级** | node、nginx 都在跑 |
| 读盘能力 | `curl -X POST :5700/api/user/login` | 回**业务 JSON** | 能读 SQLite ⇒ **磁盘、文件系统、页缓存都正常** |
| **新建会话** | `ssh`（带/不带 `-T`） | 卡在 `channel open` | ← 唯一坏掉的一层 |
| 新建单元 | 1Panel agent | 起不来 | 佐证是 PID1 那一层 |

### 17.3 根因：卡的是 **systemd(PID1) / logind**，不是 sshd、不是磁盘、不是网络

- SSH **通过认证之后**要 `pam_systemd` 建会话 → D-Bus 找 `systemd-logind` →
  logind 要 PID1 创建一个 scope → **PID1 不响应** → 会话永远建不起来（客户端 `LoginGraceTime` 120s 后断开，
  正好对上实测的 2m15s）
- **已经跑起来的** nginx / qinglong(node) 完全不依赖 PID1，文件又大多在 page cache 里 → 照常服务
- 1Panel v2 的 agent 是 **systemd 托管的独立进程** → PID1 卡住就起不来 → core 只能吐 "Access Temporarily Unavailable"
- 与 §3 是**同族死法**（PID1 被挂住），区别是 §3 卡在 `console=ttyGS0` 的 `write()` 上，
  而这次**串口一个字都没有**，见下。

### 17.4 这次取证链在"开机第 45 秒"就被自己打断了

- PC 侧记录器 `total_bytes` **冻在 56187 @ 23:27:06**，之后再没收到任何字节
- 手动抢读 COM15 30 秒 → **0 字节**。§3 的急救口诀"打开串口读一下往往立刻解卡"**这次无效**，
  说明不是"缓冲满没读"。更可能是 **USB IN 端点（ep1in）已经废了**：设备侧的 write 被 tty 正常收下
  （否则 logwatch 会往 stderr 报 `EAGAIN`），但**一个字节都没送到 PC** ——
  开机日志里正好有 `dwc3 a800000.usb: request … was not queued to ep1in`
- 时间线对得上：
  - `22:53:31`（开机 +45s）`z17s-usbnet.sh` **拆掉并重建 gadget** → ttyGS0 被销毁重建

### 17.5 修法 / 待办

1. **止血（设备侧）**：`z17s-logwatch` 写 tty 失败必须**捕获异常并重开设备**，不能 SEGV。
   现在它一崩就永久退化成 kmsg，等于把心跳监测废掉。
2. **止血（PC 侧）**：串口记录器**不允许"开着口却不读"**。它这次 23:27 掉线重连后就一直
   `state=idle`、`last_data` 不动，却还在报"设备可能卡死"——**记录器自己才是那个卡死的**。
   重启记录器后必须核对 `last_data` 在往前走。
3. **消除诱因**：开机 +45s 重建 gadget 会**销毁 console tty**。要么改成分步加函数（不拆已有 acm），

5. **别拿 SSH 当存活探针**：SSH 不通 ≠ 设备挂了。先跑 §17.2 的判据表，能立刻分开
   "网络断 / 整机停（ping 也不通）/ 半死态（ping 通但新会话建不起来）"。

机理（与 §7.1 同源，只是触发者换成了我们自己）：
内核 console 就挂在 `ttyGS0` 上，而 `z17s-usbnet.sh` 的 teardown 会 `modprobe -r g_serial`
+ unbind UDC，把 `ttyGS0` 整个销毁。此刻只要还有进程攥着这个口（主机开着 COM 口、
`z17s-logwatch` 握着 `/dev/ttyGS0` 的 fd），`gs_close()` 就会等 port 空闲 —— 而阻塞
一旦落在 console 路径上，就会传染到往 `/dev/console` 写状态行的 PID1。
脚本里 `timeout 12 systemctl stop serial-getty@ttyGS0` 那段的注释早就写了这句风险
（"gs_close waits on the port while the gadget is being torn down"），只是没人把它和 PID1 联系起来。

**已落地的两处修法（入库）**：
1. `z17s-usbnet.sh` 新增**快速路径**：只要 `$G/UDC` 已 bind、`usb0` 在、`/dev/ttyGS0` 在，
   **什么都不拆**，只补 IP 就退出 —— 把"能拆的场合"压到最小。
2. `z17s-usbnet.sh` 拆之前先 `systemctl stop z17s-logwatch.service`（松开 ttyGS0 的持有者），
   装完 `ttyGS0` 回来后再 `start`；`restore_gserial()` 回滚路径同样补上。

#### 17.10.1 顺带修掉两个 PC 侧 bug

1. **`start-serial-log.cmd` 的 banner 被 cmd 当成命令执行**（截图里那两行
   `'port' is not recognized as ...`）。根因不是引号也不是语法，而是
   **`chcp 65001` + 批处理文件里有中文**：cmd.exe 按字节偏移重读批处理文件来解码，
   多字节中文会让它把行切碎/合并，碎片被当命令执行。
   **修法：`.cmd` 与 `.ps1` 一律纯 ASCII**（PS 5.1 无 BOM UTF-8 那套坑同源），
   并去掉 `chcp 65001`。校验方式：
   `python -c "..."` 逐行扫 `byte>126 or byte<32`，必须为空。

2. **记录器会去打开"幽灵 COM 口"。** 设备重建 gadget 后，旧 COM 号在
   `Get-PnpDevice` 里变成 `Status=Unknown` 的僵尸条目，但**注册表 `SERIALCOMM` 还留着**，
   于是记录器按"猜的端口列表"打开了已经不存在的 **COM11**，读一块就 `read error`，
   然后一直 `still no port` —— 而真正该读的 COM15 没人管。
   **修法：只认 `Status -eq 'OK'` 且 `InstanceId` 属 `USB\VID_0525&PID_*` 的口**
   （`A4A2` 优先于 `A4A7`），**删掉 SERIALCOMM 扫描与猜测列表**。顺带把
   `port_pid / port_mi / port_node`、`hb_uptime_s`、`dev_boot_at` 写进
   `serial-log.status`，并把"设备换了 COM 号 = gadget 被重建"显式打成日志标记
   （`device RE-ENUMERATED: COM11 (PID A4A7) -> COM15 (PID A4A2)`）。
   > 教训：**"能打开"不等于"是那台设备"**。判据必须落在"当前在场 + 硬件身份"上。

#### 17.11.2 为什么这次能把因果钉死：早期 gadget 只有 ACM，没有 RNDIS

这是本次最值钱的一条推理。之前的实验一直被一个混淆因素卡住：设备插在 PC 上时，
主机侧同时存在 **① COM 口句柄** 和 **② RNDIS 网卡**，无法区分是谁把 teardown 顶死的。

但 `z17s-early.service` 里的 `modprobe g_serial` 建出来的早期 gadget
（`VID_0525&PID_A4A7`）**是纯串口的，没有 RNDIS**。也就是说：

> **开机 0~45s 这段窗口里，主机侧唯一能"攥住"设备的东西，就是那个 COM 口。**

这次把线拔了 → 主机侧**零持有者** → 重建干净通过。
而设备侧的 `z17s-logwatch`（旧版，握着 `/dev/ttyGS0` 的 fd、并且 21:22:55~21:24:05
一直在报 `serial hb write failed: [Errno 11]`）**反而全程在场**，却完全没影响。
⇒ **设备侧持有者不是充要条件，主机侧持有者才是。**

顺带得到一个副产品：**早起日志不会因为"晚插线"而丢**。插回线后，PC 侧在
21:25:03 收到的是设备 uptime 20~26s 的**内核启动日志**（`tas2555` 那几条）。
即内核 console 是带 `CON_PRINTBUFFER` 注册的，**没人读时消息留在 printk 环形缓冲里，
等有人开始 drain 时整段补发**。所以"记录器不要早接"这个代价其实接近于零。

#### 17.11.4 `z17s-ufs-quiet` 实际只关掉了 2 个开关（第 2 个这个内核没有）

```
z17s-ufs-quiet: runtime PM  power/control = on (runtime_status=active)      ← 生效
z17s-ufs-quiet: 跳过时钟缩放（没有 clkscale_enable，可能内核没编译 UFS devfreq）
z17s-ufs-quiet: auto_hibern8 .../1da4000.ufshc/auto_hibern8 = 0            ← 生效
```

`/sys/class/scsi_host/host*/clkscale_enable` 在本内核（6.12.95+）**不存在**，
所以"关时钟缩放"这条待办要么放弃、要么重编内核时补 UFS devfreq。剩下两个开关

##### 17.14.4 动数据库前先备份：`db.backup()` 不可用，用 `VACUUM INTO`

改 `Dependences` 之前把 `database.sqlite` 备了一份。这个 build 上
**`sqlite3` 的 `db.backup()` 是回调式的、不是 Promise**，当 Promise 用直接
`TypeError: ... is not a function`；改成回调写又撞 `SQLITE_BUSY`（panel 的
WAL 连接正开着）。最后用一条 SQL 解决，原子且不碰 WAL：

```sql
VACUUM INTO '/ql/data/db/database.sqlite.bak-2026-09-22T14-33-42';
```

⚠️ 备份文件名里的时间是**设备时钟**（这台机器没有可靠 RTC，联网后才被 NTP 拨正，
所以名字里的 `14-33` 与本地 `22:33` 差 8 小时）。同一个坑在 §14 已经吃过一次，
判时间一律用单调时钟、别信文件名和 journal 日期。

##### 17.14.5 这一节的通用教训

- **"面板说已安装" ≠ "能用"。** 判据永远是 `require()` 一次 / 真调用一次。
  `pnpm ls -g | grep` 是字符串匹配，`canvas` 那条就是被
  `jsdom@30.1.0_canvas@3.2.3` 这种 peer 目录名误命中的（老账，§17.12）。
- **降级比升级安全，但要看 `engines`。** 三个包的问题全是"包自己的元数据与内容不一致"
  或"要的 Node 比容器新"，换版本都能绕开，不用动容器运行时。
- **在设备上装 npm 包也是重 IO。** `pnpm add -g` 会拉网络 + 解包写磁盘，
  和 §17.3 的 UFS 抖动是同一类负载 —— 所以这次特意挑同一个健康窗口一次做完、做完就停手，
  没有分散到多天反复刺激。
- **SQLite 热备就用 `VACUUM INTO`**，简单、原子、不依赖驱动的 Promise 风格，
  比 `db.backup()` 稳。

##### 17.15.3 两条"看着吓人其实是假警报"，必须学会区分

**a) `dwc3 … request was not queued to ep1in`（+51.37s）不是死亡信号。**
它和 `printk: legacy console [ttyGS0] disabled` **同一毫秒**发生 —— 就是内核往**正在下线的
旧 tty** 写最后一笔失败了。§17.4 当时也是这条消息，但那时它**后面什么都没有**（串口彻底静默）；
这次它后面紧接着就是新 tty 上线 + 心跳恢复。**判据是"这条消息后面还有没有后续"，
不是这条消息本身。**

**b) 用 grep 数错误一定会被骗，必须看上下文。** 这次统计出来
`ufshcd=2`、`RCU stall=2`，看着像复发了，实际分别是：

- `ufshcd` 两条 = `scsi host0: ufshcd`（就是驱动名）和自检打点 `Z17S_INIT ufs_drv=ufshcd-qcom`
- `RCU stall` 两条 = `z17s-ufs-quiet.service` 的**描述文字**
  （"…suppress UFS runtime-PM and clock-scaling jitter (RCU stall mitigation)"），
  是 unit 的 Description 字段，跟内核无关

> ⚠️ 所以体检脚本/复盘时数关键词，**必须把命中的原行打出来看**，
> 否则自己的 unit 描述字符串会把"0 次 stall"报成"2 次 stall"。
> （这条已经进 `MEMORY.md` 的判据清单。）

##### 17.15.4 PC 侧记录器在整次重启里的表现（符合设计）

记录器（`z17s-serial-log.ps1`，只认 `A4A2`）日志：

```
23:03:56 → 23:04:26  [PC] port lost (COM15 PID A4A2), device uptime ~6050s - waiting to reconnect  ×6
                     （控制台同时打 "still no port, retrying..."）
23:04:33             [PC] port reopened （reconnect #1）
23:04:33 起          data: [0.339811] … 一直到心跳
```

- **`still no port, retrying...` 是正常现象**，不是错误：设备重启瞬间 USB gadget 消失，
  COM15 从系统里摘掉，新 gadget 要等 +59s 才枚举出来。这个 ~60 秒的空窗就是设计里
  说的"重连是正常的"。
- **它抓到了从 `[0.339811]` 开始的完整开机日志** —— 因为新 `ttyGS0` console 注册时，
  内核会把 printk ring buffer **回放**给新 console。所以**晚挂记录器也不会丢开机日志**，
  不用为了抓 +0s 而提前开机。

`serial-log.status` 同刻读数：
`state=idle port=COM15 port_pid=A4A2 port_mi=02 reconnects=1 last_data=23:05:03 hb_uptime_s=93`。
⚠️ `state=idle` 单独看没有意义（§17.9 那个坑），**必须和 `last_data` 是否在动一起看** ——
这里 `last_data` 每 10 秒刷新，说明记录器本身没卡。

##### 17.15.5 顺带记录：`z17s-wifi-load.service` 每次开机都失败（既有行为，非本次引入）

`RTNETLINK answers: Operation not possible due to RF-kill` → 服务 `status=2/INVALIDARGUMENT`。
查了 `boot -1/-2/-3`，**每次都是 1 条同样的失败**，说明是老账不是新回归：
当前 `rfkill` 里 `phy0: Wireless LAN` 是 `Soft blocked: yes`（NM 日志也写

真要清理就是把开机流程里那段 rfkill/加载逻辑去掉，属于"消噪音"而非"修功能"。

##### 17.15.6 顺手挖出并修掉：记录器把"积压数据"当成实时数据，开机时刻算错 69 分钟

复盘这次日志时，第 8 行有一句很别扭：

```
[PC 2026-09-22T23:03:07.374 device boot @ 22:31:56 (uptime 1871s) - gadget rebuild expected @ 22:32:41]
```

可设备**真开机是 21:22:13**（`journalctl --list-boots` 与 `uptime` 双重确认），
而且 22:39 我还 SSH 进去看到 `up 1:16`。差 **69 分钟**。

再往下看日志开头就明白了 —— 记录器一打开端口收到的**不是实时数据，是积压**：

```
z17s-hb uptime=1871 load=0.09/0.19/0.27      ← 21:53 的心跳（上一条记录器在 21:53 停了）
...
z17s-hb uptime=2022 load=0.72/0.37/0.32      ← 21:55
z17s-hb uptime=4094 load=0.28/0.41/0.40      ← 直接跳到 22:30（中间那段被缓冲丢弃）
```

**成因**：`logwatch` 每 10 秒往 `/dev/ttyGS0` 写一条心跳，**没人读的时候这些字节不会消失**，
它们堆在 tty 缓冲里；记录器一 `Open()`，整段 18 条心跳在**同一毫秒**涌出来。
而旧代码拿到第一条 `uptime=1871` 就立刻算 `devBootAt = now − 1871s` →
`22:31:56`，还顺手推了个毫秒不差的"gadget rebuild expected @ 22:32:41"。
**它不是"坏"了，是"信了不该信的数据"。** 这一行是给人当时间锚点用的，
错了 69 分钟，事后复盘会被带偏；写入 `serial-log.status` 的 `dev_boot_at` 同样有毒
（后来收到重启后的新鲜心跳才自我纠正）。

**修法**（`README` 里的三层取证文档 `日志与取证.md` 也同步了）：

1. 开端口（含每次重连）后设一个 **排空窗口** `-DrainSeconds`（默认 4 秒），
   窗口内收到的心跳一律按积压处理。
2. 再加一条不依赖时间的判据：**一块数据里挤了 ≥2 条心跳 = 积压**
   （积压是整段涌出来的，新鲜心跳 10 秒才一条）。
   ⚠️ 计数用**本块 `$text`** 而不是拼了尾巴的 `$probe` —— 否则尾巴正好停在
   `z17s-hb` 上时，一条新鲜心跳会被数成两条、被误判成积压。
3. 只有"新鲜"心跳才写 `device boot @ … (fresh)` 并更新锚点；积压只标注。
   `serial-log.status` 新增 **`hb_src=fresh|backlog`**：**只有 `fresh` 时 `dev_boot_at` 才可信**。
4. 日志正文里插一行
   `NOTE everything below until the next 'device boot @ ... (fresh)' line is BACKLOG …`，
   翻旧日志时先找它。
5. 参数与注释**全 ASCII**（见下面那条编码坑）。

**验证**（`Parser::ParseFile` 语法检查 + 用真日志回放分类逻辑）：

```
ParseErrors: 0
真实积压块(18 条心跳) -> backlog(burst)  (命中 18 条)
单条新鲜心跳          -> fresh  (命中 1 条)
单条心跳但落在排空窗口 -> backlog(drain)  (命中 1 条)
已 fresh 后再来积压块  -> fresh  (命中 18 条)  <- 一旦拿到可信锚点，后续内容不再覆盖它
积压块取到的 uptime = 1871 -> 推算开机 22:31:56   （旧代码就是这么错的）
```

> 🎁 **副产品，值得记住**：正因为积压会补发，**晚开记录器不会丢前面的输出**。
> 这次重启后记录器是 23:04:33 才重连上的，却拿到了**从 `[0.339811]` 开始的完整开机日志**
> （新 `ttyGS0` console 注册时内核把 printk 环形缓冲回放给它）。
> 所以"必须提前把记录器挂上才能抓到开机"这个顾虑是多余的 —— 但代价是**必须能区分积压**，
> 否则时间线会错。这两件事是同一个机制的两面。

##### 17.15.7 编码坑复现：往 `.ps1` 里加中文，PS 5.1 直接把它读崩

这次给记录器加注释和日志文案，中文写得很自然，结果一跑语法检查：

```
PSVersion: 5.1.26100.9444
ParseErrors: 16
  L432: 表达式或语句中包含意外的标记"閲岄潰鐨?uptime"     ← 典型乱码
  L527: 字符串缺少终止符: "
  L336: 语句块或类型定义中缺少右"}"
  ...
```

**原因**：`.ps1` 是 **UTF-8 无 BOM**，Windows PowerShell 5.1 会按**系统 ANSI 代码页（CP936）**
解码源文件。UTF-8 的多字节中文被当 CP936 解，某些字节序列会解出 `0x5C`（`\`）或引号，
于是字符串提前"闭合"→ 后面全线崩。**文件名是 `.ps1` 时，脚本会静默挂掉，不看语法检查根本发现不了。**

**做法**（已写进技能与 `MEMORY.md`）：

- 新增/修改 `.ps1` 的**代码与字符串一律 ASCII**；注释里的中文只保留原有的、已经验证过能解析的。
- 改完 `.ps1` **必须过一遍 AST 语法检查**（这才是 `.ps1` 的真"编译"）：

```powershell
$tokens = $null; $errors = $null
$null = [System.Management.Automation.Language.Parser]::ParseFile($path, [ref]$tokens, [ref]$errors)
$errors.Count   # 必须是 0
```

- ⚠️ 别用"跑起来看着没事"当判据：错误的字符串终止符可能只在**某个分支**才炸，
  而这次是**解析期**就炸（整个脚本都不执行）。
- 修完后本次记录器 `ParseErrors: 0`，参数列表也能正常解析出 `DrainSeconds`。

## 18. 附录：诊断方法论

这几条是跨问题通用的，比单个修复更值钱。

### 15.1 时间判断一律用单调时钟

设备时钟会乱跳，`journalctl` 里带日期的输出不可信。用：

```bash
journalctl -b -u <unit> -o short-monotonic
systemd-analyze time
systemd-analyze blame | head -20
```

### 15.2 "卡住"先分三层判

| 卡在哪 | 判据 |
|---|---|
| 内核还没起来 | PC 上**完全看不到任何 USB 设备**（连串口都不枚举） |
| systemd 启动阶段 | 串口有日志但停在某一行 |
| 系统起来了但服务挂 | `systemctl is-system-running` 返回 `degraded`，串口能登录 |

### 15.3 服务"配了但没生效"→ 先读状态里的 reason 字段

`nmcli` 的 `GENERAL.REASON`、`systemctl` 的 `ActiveState` / `Result` —— **优先读它们，而不是重写配置**。

### 15.4 用副作用验证而不是看输出

当输出通道不可靠（终端输出被吞、编码乱了）时，**让远端产生一个可观测的副作用**，再独立读取：

```bash
ssh dev 'touch /tmp/probe-X'    # 副作用
ssh dev 'ls /tmp/probe-*'       # 独立验证
```

### 15.5 块设备写入校验不能比整盘 md5

镜像 4GiB、分区 52GiB 时，整盘 md5 必然不同。必须**只比写入的那一段**：

```bash
dd if=/dev/sda10 bs=4194304 count=1024 | md5sum    # 只比前 4GiB
```

且**写之前必须 umount**。

### 15.6 串口是最后一道保险

任何改动 USB / 网络 / systemd 的操作，**动手前先确认串口能连**。改挂了还能从串口进去回滚 —— 这个习惯救过很多次。

### 15.7 先判"活着但卡住"还是"真的死了"（决定取证方向）

"设备从 PC 上消失"至少有三种完全不同的原因，取证方向**相反**：

| 现象 | 判据 | 结论 | 该做什么 |
|---|---|---|---|
| 屏幕**还在刷日志** | 手机拍照能看到新行出现 | 内核活着，只是**调度停摆**（RCU stall / 死锁） | 抓内核栈：SysRq、`journalctl -b -1`、hung-task 报告 |
| 屏幕黑、但插上时有 USB 枚举声 | `Get-PnpDevice -PresentOnly` 里有 `0525`/`1D6B` | 内核没在跑（正在重启 / 崩溃） | 读串口 `ttyGS0` 看有没有输出 |
| 连串口都不见了 | `SERIALCOMM` 只剩 `COM1` | 供电/硬件层断开（掉电、线、USB 口） | 换线换口、接充电器、查供电 |

2026-09-21 那次，`ping` 全丢 + 端口全 CLOSED + 串口消失，**每一项都指向"掉电"**，
所以第一版结论确实是"疑似供电不足"。**是用户拍的屏幕照片推翻了它** —— 设备其实一直在刷 RCU stall。

> **教训：别只看网络层"消失"就下结论，一定要让用户看一眼屏幕（或读一次串口）。**
> "还在刷日志"这一个事实，就能把方向从"查供电"整体掰到"抓内核栈"。

### 15.8 Git Bash 下 GNU tar 不认 `C:/...`，配合 `set -e` 就是"静默退出"

Windows 上跑 Linux 风格脚本时，**路径形式**是个反复咬人的坑：

```
$ tar tzf "C:/Users/<用户名>/.../10-etc.tar.gz" ; echo $?
2                      ← file not found
$ tar tzf "/c/Users/<用户名>/.../10-etc.tar.gz" ; echo $?
0                      ← 正确
```

Git Bash 的 `/usr/bin/tar`（GNU tar 1.35）只认 **MSYS 形式** `/c/Users/...`；
`gzip`、`stat`、`ls` 这些 MSYS 工具同理。

危险之处在于**它不报错，只返回非零**。如果这行处在 `set -e` + `set -o pipefail` 下，
脚本会**当场静默退出：零输出、零报错，看起来像"卡住了"**：

```bash
set -euo pipefail
CNT=$(tar tzf "C:/.../10-etc.tar.gz" 2>/dev/null | wc -l)   # ← 死在这里
echo "不该看到这行"
```

2026-09-21 实测：`pull-chunks.sh` 第一块拉成功后就不动了 ——
`10-etc.tar.gz` 明明完好（`gzip -t` 通过、897 个成员），但既没有后续输出也没有任何报错。

**两面修法（都要做）**：

```bash
# ① 入口统一规范化：Windows 形式 → MSYS 形式
if command -v cygpath >/dev/null 2>&1; then
    OUTROOT="$(cygpath -u "$OUTROOT")"
fi

# ② 所有"不该致命"的命令替换都兜底
SZ=$(stat -c %s "$ARCHIVE" 2>/dev/null || echo 0)
CNT=$( { tar tzf "$ARCHIVE" 2>/dev/null || true; } | wc -l ) || CNT="?"
```

给用户展示路径时再用 `cygpath -w` 转回 `C:\...`，否则他在资源管理器里找不到。

> **这是"静默失败"家族的第 N 次复发。** 同一类脚本里已经栽过：
> `--exclude` 与成员名形态不匹配（静默不排除，把备份目录自己打进去）·
> `X="$( [ ... ] && echo x )"` 在 `set -e` 下静默退出 ·
> `set -e`+`pipefail` 让 `RC=${PIPESTATUS[0]}` 永远执行不到（错误提示打不出来）。
>
> **规律：凡是"命令替换里带管道"或"赋值里带条件判断"的地方，在 `set -e` 下都默认可疑。**
> 审这类脚本时，把每一个 `$( )` 都当成潜在的静默退出点过一遍。
