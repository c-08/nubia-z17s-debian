# 硬件现状：哪些能用、哪些不能用、为什么

> 这份文档的存在意义：**别在已经定性的事情上重复投入时间。**
> 所有结论都有实测依据，不是猜测。

---

## 一、Wi-Fi（WCN3990）—— ❌ 主线内核下无法稳定使用

### 结论先说

**能连上，但每次开机活不过约 7 分钟**（实测：开机后 103 秒 Wi-Fi 起来 → 441 秒崩溃）。
**崩溃后唯一的恢复手段是重启。** 而且**这不是本移植引入的 bug，主线内核同样存在**。

### 崩溃长什么样

```
qcom-q6v5-mss: fatal error: EX:wlan_process:1:WLAN RT:1078:PC=b00c0098
```

这是**基带处理器（modem Q6）内部固件自己 assert** —— 不是 Linux 侧驱动报错，是 Wi-Fi 固件（跑在 modem 里）自己崩了。Linux 只是接收到了这个致命错误通知。

### 三种表象（判错形态会白花一整天）

同一根因会演化成三种看起来完全不同的形态：

| 形态 | `ip -br link` | `iw scan` | 关键日志 |
|---|---|---|---|
| ① 接口消失 | wlan0 不存在 | — | 重载驱动后 wlan0 再也不出现 |
| ② 下行卡死 | `UP` 且有 IP | **成功**（扫到 6 个 BSS） | `failed to extract amsdu: -11` |
| ③ 崩溃风暴 | **`DOWN`/`NO-CARRIER`** | **返回 0** | `firmware crashed!` 反复刷屏 + `handling crash #N` 递增 |

⚠️ **形态 ② 最具欺骗性**：接口状态是 `UP`、有 IP、扫描还能成功，**光看 `nmcli` 或 `ip link` 会以为 Wi-Fi 好着**，实际上数据面已经死了。所以探活必须用 `ping` 真实网关。

### 根因

> ⚠️ **2026-09-25 更正**：下面这条"自研钩子 `key_hw_accel` 强制硬件解密"是**误判**。
> `key_hw_accel` 只是 `net/mac80211/key.c` 里的 **6 条 `pr_info` 日志插桩**，外层逻辑与上游一字不差，
> 而上游**本来就**支持"驱动返回 1 → 走软件解密"。真正的软解开关在 **`ath10k`**（`ath10k_core.ko`）。
> 详见 [WiFi与蜂窝修复方案 §2](WiFi与蜂窝修复方案.md)。

其中 `cipher=0xfac04` 是 **CCMP-128**，也就是标准 WPA2 —— 这是最常见的加密方式，所以几乎所有现代路由器都会踩中。

（⚠️ 早前笔记里写成"CCMP-256"是**错的**；CCMP-256 是 `0x000FAC0A`，两者不同。）

### 已经穷尽的尝试（不要再重复）

| 方向 | 尝试 | 结果 |
|---|---|---|
| 软件侧 | 设 `cryptmode=1` 强制走软件解密 | ❌ 原样被驱动 probe 阶段拒绝（固件不报 `RAW_MODE_SUPPORT`）|
| 固件侧 | 换 `WLAN.HL.2.0` 新固件 | ❌ MSS 崩溃循环，更糟 |
| 上游内核 | 查 6.17 与一加 7T 的情况 | ❌ 同样必崩 → **无可移植修复** |
| 驱动重载 | `modprobe -r ath10k_snoc` 再加载 | ❌ wlan0 之后再也不出现 |

**目前唯一能用的固件 = 原厂 `HL1.0-01352`**，备份在设备 `/root/fwbackup/`。

### ✅ W1（改 `ath10k` 走软解）—— 2026-09-25 已实测，**仍未修好，但把结论钉死了**

打两处补丁（绕过 `cryptmode=1` 的 `RAW_MODE_SUPPORT` 门槛 + 放宽 `add_interface` 守卫）后
编出 `ath10k_core.ko`（`e46e8e82…`），已刷进 boot 并持久化。实测结果：

| 环节 | 结果 |
|---|---|
| 软解是否生效 | ✅ **是** —— `hwcrypto 0` + `key_hw_accel SW ok (drv ret=1)` |
| 密钥是否还下发给固件 | ✅ 不再下发（这才是原来崩溃的诱因） |
| WPA2 四次握手 | ✅ **成功**（`PTK=CCMP GTK=CCMP`，三次重试全成功） |
| 能不能传数据 | ❌ **不能** —— `unhandled tx completion status 5` ×9，我们的加密帧被固件丢弃 |
| 结果 | AP 以 `4WAY_HANDSHAKE_TIMEOUT` 踢人 → 拆除站点时固件仍 assert（`RT:207a:PC=b00c0098`） |

👉 **新结论**：软解路径本身能通，但 **HL1.0 固件不认 `NO_ENCRYPT` 标记、不肯发软件加密的帧**。
唯一没试的形态是"RAW 数据面 + 软解"（`frame_mode=0`，顺带关 A-MSDU），要再放宽一道门槛 ——
见 [WiFi与蜂窝修复方案 §2.4.2](WiFi与蜂窝修复方案.md) 与 [W1实验结果.md](W1实验结果.md)（含 E1–E5 实验清单）。

**判断：收益仍然不高。USB 有线网络已稳定可用（ping 0ms），Wi-Fi 只值得做零成本实验。**

### 缓解措施（推荐做）

既然 Wi-Fi 只会带来麻烦，可以**直接关掉它止损**：

```bash
nmcli radio wifi off
```

效果（实测）：

- 崩溃计数归零
- **系统负载从 1.9 降到 0.28**（崩溃风暴一直在吃 CPU）
- 不再刷屏内核日志
- 该状态写入 NM 的 state 文件，**重启后仍然保持关闭**（想恢复用 `nmcli radio wifi on`）

⚠️ **执行这条命令时设备可能会当场重启一次** —— 实测发生过，前一个 boot 的日志停在 scan 失败、没有 panic 记录。疑似在"固件已经崩掉"的状态下动 `wlan0` 会触发整机复位。
**所以：不要在固件崩溃态反复操作 wlan0。**

### 另外一个已知限制：只能信道 1–11

- 这棵树的 `regulatory.db is malformed`，ath10k 退到自管理域 `country 99`
- 结果是 **ch12/ch13 被标记为 `disabled`**（中国允许 1–13，但驱动不认）
- `iw reg set CN` 无效
- **解法：把路由器的 2.4G 固定到 ch6 或 ch11。**

⚠️ 顺带一个容易误判的点：`iw dev wlan0 scan freq <MHz>` 在**允许的频率**上会返回**全量 BSS 列表**，不能当定点扫描用。
另外实测扫不到自家的 `999` 2.4G AP，而 `999-5G` 是 -38 dBm、其他 2.4G 都 ≤-60 dBm —— **说明那个 AP 根本没在广播 2.4G**，不是设备扫不到。

## 二、蜂窝（手机卡）—— ❌ 不可用（数据面被 IPA 卡住）

> ⚠️ **2026-09-25 改判**：本章"被 IPA 卡住"的判断成立，但"**无解**"的推论**不成立**。
> 新证据：主线**原生支持** `qcom,msm8998-ipa`（IPA v3.1）；本机设备树 IPA 节点**接线完整**、
> `firmware-name` 指的固件就在设备上；modem 已在 QRTR 上广播 **IPA control service**；
> **本机 Android 下 IPA 数据面初始化成功过**（日志仍在）。
> ⇒ 蜂窝改判为 **值得一试**：见 **[蜂窝可行性评估.md](蜂窝可行性评估.md)**。

### 结论先说

**不是"主线内核不支持蜂窝"。** modem 其实是**活的**（QMI 控制面能查到服务、SIM 也认得出来），
被卡住的是**数据面**。上游把它们摘掉，是"这块板子上 IPA 跑不通"的**结果**，不是随手的取舍。

> 完整分析（含"为什么高通 410 随身 WiFi 能、这台不能"、以及"换 OpenWrt 也没用"）
> 见 [项目总览.md §5](项目总览.md)。

### 分三层看，就知道问题在哪一层

| 层 | 内容 | 状态 |
|---|---|---|
| **AP 侧系统**（rootfs + init） | Debian / OpenWrt / Android | 🔄 想换就换，**换了不解决蜂窝** |
| **内核与驱动层**（数据面） | `ipa` · `qcom-q6v5-mss` · `rmnet` | 🔴 **真正卡在这里** |
| **硬件通路** | IPA 加速器 · 片内 MSS · SMEM / GSI | 🔴 本机 IPA 一加载即整机复位 |

关键认知：**MSM8998 的 modem 数据必须经过 IPA（IP Accelerator）** ——
一个独立的硬件 DMA 引擎，需要自己的固件 + SMEM/GSI 配置 + 一长串 probe 前提。
**没有 IPA 就没有 `rmnet_data0`**，蜂窝数据在物理上无处可走。
（QMI 控制面走共享内存、**不经 IPA**，所以"能查到服务却没流量"这个假象很常见。）

### 上游具体摘掉了什么

1. **`ipa.ko` 被列入黑名单**（`/etc/modprobe.d/10-z17s-unsafe-modules.conf`）：

   ```
   blacklist ipa
   install ipa /bin/false
   ```

   原因：加载它会**直接把这台 NX595J 重启**（boot loop）。配置注释原文：
   `# IPA resets this NX595J with the current 6.12 device tree`

   ⚠️ "resets" 是**整机复位**，不是普通 probe 失败 —— 所以表现是 boot loop，不是一条错误日志。

2. **`rmtfs` 与 `tqftpserv` 被 mask** —— 这两个是 modem 从文件系统取固件/校准数据所必需的服务，
   被停掉后基带无法完整起来。

3. 上游作者的移植定位就是 **Wi-Fi-only**（**整体摘除**，不是漏配）。

### 已经做对的事：危险分区一个字节没动

`modem`(`sde10`) / `persist`(`sda2`) / `dsp`(`sde11`) **全程没写过一个字节** ——
modem 固件与 EFS 校准数据都还在。所以问题**不在"东西没了"**，在"通路断了"。


### 想恢复需要做什么（高风险）

| 步骤 | 内容 | 风险 |
|---|---|---|
| 1 | 让 IPA 驱动 probe 成功（正确的固件名 + DTB 里 IPA 节点 + GSI 配置 + 一堆依赖同时正确） | **高** —— 这正是导致 boot loop 的部分 |
| 2 | 让 remoteproc 正确加载 modem 镜像（`qcom-q6v5-mss` + `mba.mbn` / `modem.mdt`） | 高 |
| 3 | 恢复 `rmtfs` / `tqftpserv` 服务 | 中 |
| 4 | 用户态用 `libqmi` / ModemManager 手工建 PDP（APN、鉴权） | 中 —— **没有 Android 的 `rild` + vendor blobs 可依赖**，全得自己搭 |
| 5 | 确认 modem 固件在 `modem` / `dsp` 分区里的完整性 | 中 —— 涉及**禁止直接写入**的分区 |

⚠️ **任何涉及 `persist` / `modem` / `dsp` 分区的操作都极度危险**，写错就丢校准数据（Wi-Fi MAC、蓝牙地址都在 persist 里）。

### ❌ 有一条路先排除掉：换 OpenWrt

**把 AP 侧系统换成 OpenWrt 对蜂窝毫无帮助。** OpenWrt 不是"另一个厂商的系统"，
它只是 **rootfs + 打包体系**；数据面用的是**同一个内核驱动**（`ipa`），
换 rootfs 改不了 IPA 对这块板子 DTS 的 probe 结果。

⚠️ 随身 WiFi 的"AP 侧"经验**不能照搬**：那些机器的 modem 是**外挂/独立一颗芯片**，
AP 真的是"另一个世界"，所以换 AP 系统不影响 modem；
本机的 modem 是**同一颗 SoC 里的 MSS**，与 AP 共享 SMEM / IPA / 时钟 / 电源域，
AP 侧内核驱动**必须参与**建通路 —— "AP 只当遥控器"这个前提在本机不成立。


**判断：不建议投入。** 这台机器的网络需求已经由 USB 有线通道完全满足（稳定、低延迟、还兼带串口控制台）。

真要**插卡上网**，务实做法是：**几十块钱买一个 4G 随身 WiFi，用 USB 插在这台机器上**
（当作标准 USB QMI 网卡用）。这比让内置 modem 跑起来靠谱得多，且完全不碰危险分区。

## 四、一句话总结

> **这台机器的联网方式就是那根 USB 线。**
> Wi-Fi 是"能用但不该用"（7 分钟必崩，根因在 modem 固件 + 内核里的硬件解密钩子，**无法移植修复**）；
> 蜂窝是"**数据面被 IPA 卡住**"（modem 活着、分区没动，换系统、换 OpenWrt 都救不了）。
> 与其纠结它们，不如把 USB 通道用得更好 —— 它已经能提供 0ms 延迟的稳定网络 + 一条永远可用的串口救援通道。
