## 3 G3 第一枪：失败 + 整机失联

### 3.1 `--wds-start-network` → `InvalidOperation`

```
$ qmicli -d qrtr://0 --wds-start-network="apn=3gnet,ip-type=4" --client-no-release-cid
error: couldn't start network: QMI protocol error (70): 'InvalidOperation'
[qrtr://0] Client ID not released:
	Service: 'wds'   CID: '1'
```

- QMI error **70 = `QMI_PROTOCOL_ERROR_INVALID_OPERATION`**
- 含义：**modem 认为当前状态不允许发起数据呼叫**
- ⭐ **最可能的解释**：这是 **IPA 数据路径未建立**的直接表现 —— 在 Android 上，modem 发起/接受数据呼叫前，必须先与 AP 侧的 IPA 完成 QMI 握手（"IPA ready / set up WAN endpoint"）。主线 `ipa` 驱动 **probe 成功但可能没有实现这套与 modem 的 QMI 交互**，于是 modem 拒绝。
- 次可能：需要先 `--nas-set-system-selection-preference` 或设置 `--wds-create-profile` 的 autoconnect；也可能与 SIM 所在 profile 绑定有关。

后续查询全部"无呼叫"：

```
--wds-get-current-settings  → error: Unknown client 1 for service wds
--wds-get-packet-service-status → Connection status: 'disconnected'
--wds-get-current-data-bearer-technology → QMI error (15) 'OutOfCall'
```

### 3.2 🔴 `ip link set rmnet_ipa0 up` → 整机失联

```
=== E4 rmnet_ipa0 up 尝试 ===
Read from remote host 192.168.137.2: Connection reset by peer
client_loop: send disconnect: Connection reset by peer
```

随后：

```
ping 192.168.137.2  → 3/3 丢包（100% loss）
ssh                 → Connection timed out
```

再等约 5 s 后 `ping` **恢复**（说明设备确实回到了网络），但**本轮未能通过 SSH 复核**（会话末尾 SSH 权限被沙箱拦截，用户要求停止）。

🔴 **未定性关键问题：这是"复位重启"还是"卡死又恢复"？** 下次第一件事就是取 `boot_id` 比对：
- `boot_id` **变了** ⇒ 复位（`ip link set rmnet_ipa0 up` 触发，等价于 `modprobe ipa` 那类危险操作的同一族）
- `boot_id` **没变** 且 uptime 连续 ⇒ 只是 RNDIS gadget 重枚举/短暂内核卡顿，不是复位

## 4 🔴 取证结论：**pstore 通道不存在**（纠正前提）

计划里"第三取证通道 = `ramoops@aff00000` → `/sys/fs/pstore/`"**是错的**：

```
$ zcat /proc/config.gz | grep CONFIG_PSTORE
# CONFIG_PSTORE is not set           ← 决定性

$ ls -ld /sys/fs/pstore
ls: cannot access '/sys/fs/pstore': No such file or directory
```

但 **DT 里节点确实在**：`/proc/device-tree/reserved-memory/ramoops@aff00000` 存在。

⚠️ **教训（已记入技能）**：**DTS 提供节点 ≠ 内核启用该功能**。查 pstore 可用性必须看 `CONFIG_PSTORE` + `/sys/fs/pstore/`，不能只看 DT。
→ 若要真开 pstore，需重编内核（`CONFIG_PSTORE` + `CONFIG_PSTORE_RAM`）并**刷 boot**（`ramoops` 已在 DT，无需改 DTS）。列入待办。

### 4.1 ✅ 实际可用的第三通道（比 pstore 更强）：`z17s-logwatch`

源码实测：

```python
FLUSH_SEC   = 0.25             # 最长 0.25 秒强制 fsync
FLUSH_BYTES = 8192
self.fh = open(path, "ab", buffering=0)   # 无缓冲
os.fdatasync(self.fh.fileno())            # 真落盘，不是只进 page cache
```

- 服务 `z17s-logwatch.service` = **active + enabled**，PID 1415
- 当前文件 `/var/log/z17s-kmsg/kmsg-8947fe68.log`（`latest` 软链指向它）
- **每次开机自动新建 `kmsg-<bootid 前8位>.log`**，另有 `snapshot-*.log` 与 `boots.tsv`
- ⇒ **硬复位的丢失窗口 ≤ 0.25 s**，且跨开机保留 ⇒ 比 pstore 更适合本项目

**取证通道最终盘点（三条，全部已验证）：**

| 通道 | 状态 | 说明 |
|---|---|---|
| A 串口记录器 | ⚠️ **未运行** | `serial-log.status` 的 `pc_time` 停在 `2026-09-23 00:20`（现在 09-26）⇒ 需用户双击 `host/windows/serial/start-serial-log.cmd`。COM 口本身 OK（`COM15 = USB\VID_0525&PID_A4A2&MI_02`）；`/proc/sys/kernel/printk = 15 4 1 7` ⇒ 全级别上串口，价值高 |
| B SSH `dmesg -w` | 可用但受限 | 后台任务读不了 `~/.ssh` ⇒ 只能前台短跑；复位瞬间断连 |
| C pstore | ❌ **不存在** | `CONFIG_PSTORE is not set` |
| D `z17s-logwatch` | ✅ **一直在跑** | 0.25 s + fdatasync，跨开机保留 —— **本次实际靠它** |

**根分区挂载是 `rw,relatime`（无显式 `commit=`，即默认 5 s）**，但 D 通道自己 `fdatasync`，不受此影响。

## 5 下一步（按优先级）

1. **先取证再动手**：设备回来后立刻比对 `boot_id`，读 `kmsg-8947fe68.log` 尾部 70 行（死前现场）+ `boots.tsv`，定性 §3.2。

   - 具体查：`drivers/net/ipa/` 里有没有 `ipa_qmi*`；`ipa_modem.c` 是否依赖 smp2p

5. **`InvalidOperation` 的旁证实验**（零风险，可先做）：
