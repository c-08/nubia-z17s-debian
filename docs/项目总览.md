## 2 设备信息

| 项 | 值 |
|---|---|
| 机型 | **努比亚 Z17S**（型号 **NX595J**） |
| SoC | **高通骁龙 835 / MSM8998** |
| Wi-Fi / 蓝牙 | **WCN3990**（802.11ac + BT 5.0）——⚠️ 固件跑在 **modem Q6** 上，这一点是 Wi-Fi 问题的关键 |
| 基带 | **片内 MSS**（Q6 modem，X16 LTE）——⚠️ 不是外挂芯片，这一点是手机卡问题的关键 |
| 操作系统 | **Debian 13 (trixie) arm64** + **主线内核 6.12.95+** |
| 根文件系统 | `userdata` = `sda10`，51 GB |
| 关键分区 | `boot`=`sde18`(64M) / `recovery`=`sde19` / `persist`=`sda2` / `modem`=`sde10` / `dsp`=`sde11` / `vendor`=`sde41` / `system`=`sda9` |
| 网络入口 | **USB configfs 复合 gadget**：RNDIS 网卡 `usb0` = `192.168.137.2/24` **＋** ACM 串口控制台，同一根线 |
| 恢复入口 | TWRP（**音量上 + 电源**） |
| 时钟 | ⚠️ **无可靠 RTC**：每次开机时间都是错的，联网后 NTP 一跳到正确值 → journal 里会出现日期重叠/倒流，**别用它算时间线** |

### 绝对不能碰的分区

🔴 **只允许刷 `boot`（`sde18`）与 `userdata`（`sda10`）。**
`persist` / `modem` / `dsp` / `vendor` / `system` **一个字节都不能写** ——
里面是校准数据（Wi-Fi MAC、蓝牙地址）与基带固件，写错就永久性损坏。

## 3 现在能干什么

| 能力 | 状态 | 说明 |
|---|---|---|
| **USB 有线网络** | ✅ **主力** | RNDIS 网卡 `192.168.137.2`，开机自启，PC 侧 ping 延迟 **0ms** |
| **USB 串口控制台** | ✅ 主力 | 同一根线，**系统卡死时唯一救命通道** |
| Docker / 容器 | ✅ | 需内核开 `CONFIG_CGROUP_BPF`（上游默认没开，见 §5） |
| 1Panel 面板 | ✅ | `:28888/z17s_panel` |
| 青龙面板 | ✅ | `:5700`，定时任务已落地（依赖自检每天 09:30） |
| 蓝牙 | ✅ | `hci0 UP RUNNING`；persist 内的 NV 与设备树硬编码完全一致 |
| 音频 | ✅ | `card 0: Nubia-Z17S` 已注册 |
| **Wi-Fi** | ❌ | 能连上，但**每次开机活不过约 7 分钟**（§4） |
| **蜂窝（手机卡）** | ❌ | 数据通路被 IPA 卡住（§5） |
| 摄像头 / NFC / 指纹 / 传感器 | ❓ | 未验证 |
| 显示 | ⚠️ | 下半屏重叠（上游已知缺陷）；本机定位是服务器，**不影响用途** |
| 关机 | ⚠️ | 干净关机其实只要 **~11 秒**，但 **94% 的时间在等 `docker.service` 停**；关完约 3.3 秒可能又自己上电（§6） |

**一句话：这是一台"USB 连着用"的机器。** 网络走 USB，屏幕当辅助，服务稳定性不依赖 Wi-Fi。

## 4 Wi-Fi 为什么修不好（WCN3990）

### 4.1 结论

**能连上，但每次开机活不过约 7 分钟**（实测：开机后 103 秒 Wi-Fi 起来 → 441 秒崩溃）。
**崩溃后唯一恢复手段是重启。** 而且**这不是本移植引入的 bug —— 主线内核同样存在**。

### 4.2 崩溃长什么样，根因是什么

```
qcom-q6v5-mss: fatal error: EX:wlan_process:1:WLAN RT:1078:PC=b00c0098
```

注意报错方是 `qcom-q6v5-mss` —— **是跑在 modem（Q6）里的 Wi-Fi 固件自己 assert**，
不是 Linux 侧驱动报错，Linux 只是收到了这个致命错误通知。

根因链条：

1. 这棵内核的 `mac80211.ko` 里有个**自研钩子 `key_hw_accel`**，它**强制 Wi-Fi 走硬件解密**
   （等价于 `sw_crypto=0`）。
2. 它命中的 `cipher=0xfac04` 是 **CCMP-128，也就是标准 WPA2** ——
   这是最常见的加密方式，**几乎所有现代路由器都会踩中**。
3. 硬件解密路径上 modem 侧固件 assert → 崩溃。
4. `remoteproc` 会去**重启整个 MSS**（重新加载几十 MB modem 固件）→ 这就是"崩溃风暴"如此昂贵的原因
   （`kworker/u33:*` 吃满 CPU、load 从 1.9 一路爬）。

> 崩溃会演化成三种看起来完全不同的形态（接口消失 / 下行卡死 / 崩溃风暴），
> 其中"下行卡死"最具欺骗性：`ip link` 是 `UP`、有 IP、`iw scan` 还能成功，
> **但数据面已经死了**。所以探活必须 `ping` 真实网关，不能看接口状态。
> 详见 [硬件现状.md §一](硬件现状.md)。

### 4.3 已经穷尽的尝试（**不要再重复**）

| 方向 | 具体尝试 | 结果 |
|---|---|---|
| 软件侧 | 设 `cryptmode=1` 强制走软件解密 | ❌ 被驱动在 probe 阶段直接拒绝 |
| 固件侧 | 换 `WLAN.HL.2.0` 新固件 | ❌ MSS 崩溃循环，**比原来更糟** |
| 上游内核 | 查主线 6.17 与一加 7T（同款 WCN3990） | ❌ 同样必崩 → **没有可移植的修复** |
| 驱动重载 | `modprobe -r ath10k_snoc` 再加载 | ❌ `wlan0` 之后再也不出现 |
| 监管域 | `iw reg set CN` 想解掉信道限制 | ❌ 无效（`regulatory.db is malformed`，退到自管理域 `country 99`） |

**目前唯一能用的固件 = 原厂 `HL1.0-01352`**，备份在设备 `/root/fwbackup/`。

### 4.4 唯一还没试的路，以及为什么不做

理论上可以**改内核源码把 `key_hw_accel` 钩子禁用**，让 mac80211 回退软件解密。代价：

- 要改 `mac80211.ko` 源码并重编内核（这台机器重编一轮约 4 分钟，但要反复验证）；
- **软件解密显著吃 CPU**，骁龙 835 跑 WPA2 软解吞吐会掉不少；
- **不保证不再崩** —— 崩溃是 modem 侧固件 assert，硬件解密钩子只是诱因之一；
- 需要"改完连续跑几小时看是否复现"的验证流程。

**判断：性价比不高。USB 有线网络已经稳定可用（ping 0ms），没必要为 Wi-Fi 再投入。**

### 4.5 当前处置

```bash
nmcli radio wifi off     # 直接关掉止损
```

实测效果：崩溃计数归零、**系统负载从 1.9 降到 0.28**、不再刷屏内核日志，且状态持久化（重启仍关闭）。

⚠️ 执行这条命令时设备**可能当场重启一次**（实测发生过）——不要在"固件已经崩掉"的状态下反复动 `wlan0`。

### 4.6 还有个小限制：只能信道 1–11

`regulatory.db` 损坏导致 ch12/ch13 被判 `disabled`（中国允许 1–13）。
**解法：把路由器的 2.4G 固定到 ch6 或 ch11。**

## 5 手机卡（蜂窝）为什么上不了网

### 5.1 结论：不是"主线不支持蜂窝"

modem 其实是**活的**（QMI 控制面能查到服务、SIM 也认得出来），被卡住的是**数据面**。
换句话说：**电话线接着、对方在说话，只是这边听筒的插孔堵了。**

### 5.2 分三层看，就知道问题在哪一层

| 层 | 内容 | 状态 |
|---|---|---|
| **AP 侧系统**（rootfs + init） | Debian / OpenWrt / Android | 🔄 **想换就换，但换了不解决蜂窝** |
| **内核与驱动层**（数据面） | `ipa` · `qcom-q6v5-mss` · `rmnet` | 🔴 **真正卡在这里** |
| **硬件通路** | IPA 加速器 · 片内 MSS · SMEM / GSI | 🔴 本机 IPA 一加载即整机复位 |

关键认知：**MSM8998 的 modem 数据必须经过 IPA（IP Accelerator）**——
一个独立的硬件 DMA 引擎，需要它自己的固件 + SMEM/GSI 配置 + 一长串 probe 前提。
没有 IPA **就没有 `rmnet_data0`**，蜂窝数据在物理上无处可走。

### 5.3 上游具体摘掉了什么

| 项 | 现状 | 为什么 |
|---|---|---|
| `ipa.ko` | **黑名单**（`/etc/modprobe.d/10-z17s-unsafe-modules.conf`：`blacklist ipa` + `install ipa /bin/false`） | 加载它会**直接把这台 NX595J 重启**（boot loop）。配置注释原文：`# IPA resets this NX595J with the current 6.12 device tree` |
| `rmtfs` / `tqftpserv` | **masked** | 这两个服务负责 modem 从文件系统取固件/校准数据；停掉后基带无法完整起来 |
| 上游定位 | **Wi-Fi-only** | 作者是**整体摘除**蜂窝，不是漏配 |

**用户已经做对的事**：只刷 `boot` + `userdata`，`modem`(`sde10`) / `persist`(`sda2`)
**一个字节没动** —— modem 固件与 EFS 校准数据都还在。

### 5.4 为什么"高通 410 随身 WiFi 刷 OpenWrt 就能插卡上网"，这台不行

别拿"都是高通"做类比。差别不在装什么系统，在**modem 的包上到 CPU 必须过哪条通道**：

| | MSM8916（高通 410 随身 WiFi） | MSM8998（本机） |
|---|---|---|
| 数据面通路 | **BAM-DMUX**（朴素 DMA，无独立固件、无 IPC 协商）；或外挂 modem 经 USB → 对系统就是一块标准 `qmi_wwan` 网卡 | **IPA 加速器**（独立固件 + SMEM/GSI + 一堆 probe 前提，脆） |
| modem 位置 | 常是**外挂** MDM9x07，AP 真的"是另一个世界" | **片内 MSS**，与 AP 共享 SMEM / IPA / 时钟 / 电源域 |
| 主线成熟度 | msm8916-mainline 社区打磨多年，有现成 DTS / target | 只有零星上游支持，这个机型组合**没人做过** |
| 原厂固件血统 | 多半本就是 QSDK / 精简 Linux（≈OpenWrt 同源） | Android（RIL + vendor blobs 一整套） |
| 换系统的工作量 | Linux → Linux，"换个壳" | Android → Linux，等于把整个 RIL 生态推倒重建 |
| 分区处置 | 同样只刷 boot/rootfs，modem / EFS 不动 | 本机同样如此，**原则一致** |

**所以"410 行、这台不行"不是玄学，是三代硬件架构的差异。**

#### 那换成 OpenWrt 行不行？—— 不行，而且一点用都没有

**OpenWrt 不是"另一个厂商的系统"**，它只是 **rootfs + 打包体系**；
数据面用的是**同一个内核驱动**（`ipa`）。换 rootfs 改不了 IPA 对这块板子 DTS 的 probe 结果。

⚠️ 随身 WiFi 的"AP 侧"经验**不能搬过来**：那些机器的 modem 是**外挂/独立芯片**，
所以换 AP 系统不影响 modem；本机的 modem 是**片内 MSS**，
AP 侧内核驱动**必须参与**建通路，"AP 只当遥控器"这个前提不成立。

> 若真实需求是**路由器功能**（NAT/DHCP/中继/插件生态），OpenWrt 确实比 Debian 合适；
> 但要如实告知：上游**没有 NX595J 的 OpenWrt target**（要自建 DTS + 板级支持），
> 且本机 Wi-Fi 已定性无解 → 刷完只会得到一个**没有无线也没有蜂窝**、
> 只能靠 USB 线共享网络的路由器，**比现状更差**。

### 5.5 想恢复需要做什么（高风险，不建议）

| 步骤 | 内容 | 风险 |
|---|---|---|
| 1 | 让 IPA 驱动 probe 成功（正确固件名 + DTB 里 IPA 节点 + GSI 配置 + 一堆依赖同时正确） | **高** —— 这正是导致 boot loop 的部分 |
| 2 | 让 remoteproc 正确加载 modem 镜像 | 高 |
| 3 | 恢复 `rmtfs` / `tqftpserv` | 中 |
| 4 | 用户态用 `libqmi` / ModemManager 手工建 PDP（APN、鉴权） | 中 —— 没有 Android 的 `rild` + vendor blobs 可依赖 |
| 5 | 确认 modem 固件在 `modem` / `dsp` 分区里的完整性 | 中 —— 涉及**禁止直接写入**的分区 |

⚠️ **任何涉及 `persist` / `modem` / `dsp` 分区的操作都极度危险**，写错就丢校准数据。

### 5.6 建议

**不建议投入。** 网络需求已由 USB 有线通道完全满足（稳定、低延迟、还兼带串口控制台）。

真要**插卡上网**，务实做法是：**几十块钱买一个 4G 随身 WiFi，用 USB 插在这台机器上**
（当作标准 USB QMI 网卡用），比自己让内置 modem 跑起来靠谱得多，也不碰任何危险分区。

## 6 其它两件容易误判的事

### 6.1 "关机很慢，还以为是死机"

实测一次**干净关机全程约 11 秒，其中 10.7 秒在等 `docker.service` 停** —— 这就是"关机慢"的唯一来源。

```bash
systemctl stop docker     # 关机前先停它，能把 11 秒压到 1~2 秒
```

### 6.2 "按电源键怎么变成强制关机了"

实测 logind 配置是 `HandlePowerKey=poweroff` + **`HandlePowerKeyLongPress=ignore`** ——
**按下那一刻就开始干净关机，"按多久"软件层完全不管**。按住不放等于把时间白送给 PMIC 的硬件逻辑
（Qualcomm PON 长按复位是 10~12 秒级，和 11 秒的关机刚好撞上）。

**正确姿势：点一下，立刻松手。**

## 7 一句话总结

> **这台机器的联网方式就是那根 USB 线。**
> Wi-Fi 是"能用但不该用"（7 分钟必崩，根因在 modem 固件 + 硬件解密钩子，无法移植修复）；
> 蜂窝是"数据面被 IPA 卡住"（换系统、换 OpenWrt 都救不了）。
> 与其纠结它们，不如把 USB 通道用得更好 —— 它已经能提供 0ms 延迟的稳定网络，
> 外加一条永远可用的串口救援通道。
