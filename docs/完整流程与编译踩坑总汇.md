## 1 环境总览

### 1.1 硬件

| 项 | 值 |
|---|---|
| 机型 | Nubia Z17S，`NX595J` |
| SoC | Qualcomm MSM8998（Snapdragon 835） |
| 基带 | 内置，IPA **v3.1**，固件 `NX595J_Z0_CN_VNG1N_V332 1 [Sep 14 2017]` |
| Wi-Fi | WCN3990（挂在 **ADSP** 上，HL1.0） |
| 存储 | UFS（`1da4000.ufshc`） |
| 显示 | 1080×2040 DSI，面板 `mdss_dsi_jdi_nt35596s_1080x2040_video` |
| 音频 | TAS2555 功放，`card 0: Nubia-Z17S` |

### 1.2 软件栈（都是实测版本，别照抄网上的）

| 组件 | 版本 | 备注 |
|---|---|---|
| 内核 | **6.12.95+**（主线，非 Android 内核） | `uname -r` |
| 发行版 | Debian 13 (trixie) aarch64 | rootfs 在 `userdata` |
| 启动 | `abootimg` 打包的 boot 镜像，**有签名校验** | 见 [boot镜像签名与恢复.md](boot镜像签名与恢复.md) |
| ModemManager | **1.24.0** | 1.24 删了 `Modems` 属性，很多老教程在这版失效 |
| libqmi / `qmicli` | **1.36.0** | WMS 只有 5 个命令，**没有 list/get/send** |
| 1Panel | v2.3.1 | `:28888`，路径 `/z17s_panel` |
| 青龙 | `whyour/qinglong:2.21.0` | `:5700` |

### 1.3 三套构建环境 —— 搞混会浪费半天

| 环境 | 位置 | 干什么 | 不能干什么 |
|---|---|---|---|
| **设备本机** | `ssh z17s` | 跑服务、装 `.ko`、编译 `DbusSmsForwardCPlus`（3.5 min） | 不要在这上面编内核/IPA（太慢，且容易触发 RCU stall） |
| **WSL（`NxBuild`）** | Windows 侧，root | **编内核 / ath10k / ipa.ko**（交叉编译 aarch64） | 不要在这边直接改设备文件 |
| **Windows** | 本机 | 编辑文档、`git push`、`scp` 传文件 | 不要用 Windows 的 `md5sum` 去比设备的（结果不同） |

★ **跨环境传文件的两个坑**：
- **heredoc 传中文/引号到设备会丢**。正确做法：本地写好 `.sh` / `.py` → 去 CRLF →
  `ssh z17s 'cat > /path' < file` 或 `tar czf - files | ssh z17s 'tar xzf - -C /tmp'`。
- **WSL / Windows / 设备三边的 md5 不一定一致**（换行与文件系统差异），
  要比 md5 就在**同一环境内**比。

### 1.4 分区与「绝对不能碰」

| 分区 | 用途 | 风险 |
|---|---|---|
| `boot` | 内核 + 签名 | 改错 = 开不了机，需 `abootimg` 重打并保持签名 |
| `userdata` | **根文件系统**（`z17s.rootfs=userdata`） | 系统全在这 |
| `persist` | 蓝牙/Wi-Fi 的 NV | 一个字节都别动 |
| modem 相关 | 基带固件 | 别动 |

## 2 完整流程（按依赖顺序）

每一步都给了**验收判据**，没通过不要往下走。

### 2.1 阶段 0：刷机 → 首次开机

```sh
# 产物：boot.img + rootfs
bash kernel/build-kernel.sh <内核源码路径>
bash kernel/build-boot.sh   <内核源码路径>
bash kernel/build-rootfs.sh
# 用 fastboot 刷 boot；rootfs 走 userdata
```

**验收**：串口（`ttyGS0`, 115200）能看到启动日志，最终落到登录提示。

**坑**：见 §5.2 内核配置两项必改项 —— 不改这两项，后面「容器全崩」和「卡死在 UFS」会
伪装成完全无关的故障。

### 2.2 阶段 1：USB gadget + 网络

USB 复合设备提供三样东西：RDP/网络（`usb0`）、串口（`ttyGS0`）、ADB。

**验收**：
```sh
ip -4 addr show usb0        # 有 192.168.137.2
ping -c3 192.168.137.1      # PC 侧网关通
```

**坑**：`usb0` 每次开机不被 NetworkManager 管、USB 网卡自启会把开机卡死、
ICS 重启后失效、`resolv.conf` 被冲成空 —— 见 §5.3。

### 2.3 阶段 2：容器

```sh
docker run --rm alpine:3.20 echo OK     # 这条不过，别查应用，查内核
```

**验收**：打印 `OK`。失败 ⇒ 100% 是 `CONFIG_CGROUP_BPF` 没开（§5.2）。

### 2.4 阶段 3：Wi-Fi（WCN3990）

```sh
# 1) 编 ath10k（WSL，约 30 秒）
bash scripts/wifi/build-ath10k-eagain.sh

# 2) 上机
scp /root/ath10k-out/ath10k_core.ko.eagain z17s:/root/
ssh z17s 'cp /root/ath10k_core.ko.eagain /lib/modules/6.12.95+/kernel/drivers/net/wireless/ath/ath10k/ath10k_core.ko'
ssh z17s 'systemctl restart z17s-ath10k-ko.service'   # 或直接断电重启

# 3) 验收
ssh z17s 'dmesg | grep "Z17S ath10k"'     # 应看到 split-A-MSDU tolerance active
ssh z17s 'iw dev wlan0 link'
```

**验收**：`firmware crashed` 计数为 0，下行 15–18.5 MB/s（§6）。

**坑**：`/lib/modules` 每次开机被引导镜像还原、`rmmod ath10k_snoc` 会崩 modem —— 见 §5.4。

### 2.5 阶段 4：蜂窝（IPA）

```sh
# 1) 编 ipa.ko（WSL，见 §4.3）
bash <ipa 构建脚本>

# 2) 上机 + 开机自启
scp ipa-new-147.ko z17s:/root/
# z17s-late.service 里 Environment=KO=/root/ipa-new-147.ko

# 3) 一键上线（手动调试用）
ssh z17s 'sh /root/z17s-up.sh'

# 4) 验收（三层，缺一不可）
ssh z17s 'grep tx_pkts_ok /root/z17s-call.log | tail -1'   # 必须非 0
ssh z17s 'ping -I rmnet0 -c5 223.5.5.5'
ssh z17s 'ip route get 223.5.5.5'                          # 必须显示 rmnet0
```

**验收**：开机 172 秒全自动上线（`TARGET=90`），下行 2.85–3.0 Mbit/s（卡限速）。

**坑**：这条线是全项目最难的一段，坑单独列在 §5.5，红线在 §7。

### 2.6 阶段 5：短信

```sh
sh scripts/sms/install-dbussms.sh 1102     # 设备上跑，约 3.5 分钟编译
```

装完自动起 `dbussms.service`（网页 + API `:1102`）+ `z17s-sms-replay.timer`（补发）。

**验收**：
```sh
curl "http://127.0.0.1:1102/api?telnum=10086&smstext=test"    # 回 ok
cat /root/sms/sms.log                                          # 收信有记录
tail /root/sms/forward.log                                     # [时间] wecom: ok
```

**坑**：原版 3 个 bug（modem 路径、match 规则、共享连接）—— 见 §5.6。

### 2.7 阶段 6：息屏

```sh
z17s-screen off      # 关背光
z17s-screen on       # 恢复
```

开机由 `z17s-screen.service` 自动执行。**不要用 `fb0/blank`**（§5.7）。

### 2.8 阶段 7：稳定性

高 IO（备份 / 编译）会把整机拖进 RCU stall 然后从 USB 上消失；
硬卡死时 journald 也是用户态进程，日志会**凭空消失**。

处置：`z17s-logwatch`（kmsg 落盘到 `/var/log/z17s-kmsg/`）+ 备份错峰。
见 [日志与取证.md](日志与取证.md) 与 [修复记录.md](修复记录.md) §13/§14。

## 4 逐个编译详解

### 4.0 交叉编译环境（WSL）

```sh
# 在 WSL（NxBuild）里，root
apt install -y gcc-aarch64-linux-gnu binutils-aarch64-linux-gnu \
               libssl-dev libelf-dev bc bison flex \
               device-tree-compiler

aarch64-linux-gnu-gcc --version     # 确认存在
```

**约定路径**（脚本里写死的，改路径要同步改脚本）：

```
内核源码   /root/z17s-kbuild/linux-6.12.95
构建输出   /root/z17s-debian/build/kernel-out        ← O=
设备侧产物 /root/*.ko
```

### 4.1 内核 + boot 镜像

```sh
bash kernel/build-kernel.sh <源码路径>
bash kernel/build-boot.sh   <源码路径>
```

**编译前必做：配置闸门**

用设备**正在运行**的配置做基准，逐行 diff：

```sh
ssh z17s 'zcat /proc/config.gz' > config-running.txt
diff -u config-running.txt .config | grep -E '^[+-]CONFIG'
```

仓库里存了 `kernel/config-6.12.95-running.txt`（真值）。

**为什么必须做**：`olddefconfig` 会静默改掉一堆选项，其中两项直接决定「能不能开机」和
「容器能不能跑」（§5.2）。`=m` 和 `=y` 在 diff 里只差一个字符，后果是开不了机。

**O= 构建的硬闸门**：`O=` 目录构建要求源码树「干净」（无本地改动 / 无未跟踪产物）。
先把改动做成 patch 再应用，否则会报错或产物不一致。

### 4.2 `ath10k_core.ko`（Wi-Fi 补丁）

```sh
SRC=/root/z17s-kbuild/linux-6.12.95
OUT=/root/z17s-debian/build/kernel-out
ATH=$SRC/drivers/net/wireless/ath/ath10k

make -C "$SRC" O="$OUT" ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
     M="$ATH" modules
```

★ **产物在源码树里，不在 `O=` 里**：

```
$ATH/ath10k_core.ko          ← 真正的新 ko
$OUT/...                     ← 不要在这里找
```

★ 补丁只改 `htt_rx.c` 一处（`-EAGAIN` 不再置 `rx_confused`），
完整脚本 `scripts/wifi/build-ath10k-eagain.sh`，补丁 `scripts/wifi/z17s-ath10k-eagain.patch`。

**部署（必须做开机复制）**：

```sh
scp $ATH/ath10k_core.ko z17s:/root/ath10k_core.ko.eagain
# 开机复制单元：z17s-ath10k-ko.service
ssh z17s 'systemctl enable --now z17s-ath10k-ko.service'
```

原因见 §5.4.1。

### 4.3 `ipa.ko`（蜂窝数据面）

★ **必须 WSL**，设备上编不动（也容易触发 RCU stall）。

```sh
SRC=/root/z17s-kbuild/linux-6.12.95
IPA=$SRC/drivers/net/ipa
OUT=/root/z17s-debian/build/kernel-out

make -C "$SRC" O="$OUT" ARCH=arm64 CROSS_COMPILE=aarch64-linux-gnu- \
     M="$IPA" modules
# 产物：$IPA/ipa.ko
```

**流程与 `ath10k` 一样的三个要点**：

1. 先把改过的源文件**逐个 `cp` 进内核树**（`ipa_table.c` / `ipa_main.c` / `ipa_endpoint.c` /
   `ipa_qmi*.c` / `gsi*.c` 等一整套，缺一个就 `MISSING` 退出）；
2. 编译后校验「旋钮是否在」——`module_param_cb` 定义的参数**不会出现在 `modinfo`**，
   要用 `strings ipa.ko | grep -qx z17s_aggr_reg` 验证；
3. 产物重命名成 `ipa-new-NNN.ko` 再上机，**别覆盖正在用的那个**。

★ **改动源文件后必须把新文件名加进构建脚本的 `for` 列表**，否则不会被拷进内核树，
编出来的还是旧代码 —— 这个坑非常容易中，症状是「改了没效果」。

### 4.4 `DbusSmsForwardCPlus`（短信）

★ **在设备本机编**（3.5 分钟），不要交叉编译（依赖 `dbus-1` / `openssl` / `curl` 的本机头文件）。

```sh
apt install -y --no-install-recommends g++ libdbus-1-dev libssl-dev \
               libcurl4-openssl-dev pkg-config

g++ -O2 -std=gnu++17 -Wno-error=format-security -Wno-unused-parameter \
    -Wno-sign-compare -Wno-missing-field-initializers -Wno-mismatched-new-delete \
    $(pkg-config --cflags dbus-1 libcurl openssl) \
    main.cpp mail.cpp -o DbusSmsForwardCPlus \
    $(pkg-config --libs dbus-1 libcurl openssl) -lpthread
```

**一键**：`sh scripts/sms/install-dbussms.sh 1102`（装依赖 → 下载 → 打补丁 → 编译 → 部署 → 装单元）。

★ **apt 走的是蜂窝（default route metric 50），约 57 KB/s**。装依赖要好几分钟，
**必须后台跑**。第一次用前台跑被 120 s 超时掐断，进程却没死、继续占着
`/var/lib/dpkg/lock-frontend`，第二次直接 `Could not get lock`（§5.1.4）。

## 5 坑总汇（症状 → 根因 → 修法）

> 按「你看到的现象」分类。每条都是**真实踩过**的，不是推测。

### 5.1 构建类

#### 5.1.1 `O=` 构建报源码树不干净
- **症状**：`make` 报错说源码树有本地改动 / 未跟踪文件。
- **根因**：`O=` 目录构建有硬闸门。
- **修法**：把改动做成 patch，`git checkout .` 清干净后再 `git apply`。

#### 5.1.2 改了源码，编出来的 ko 没变化
- **症状**：行为跟改之前一模一样。
- **根因**：改的文件**没被 `cp` 进内核源码树**（构建脚本靠一个 `for` 文件列表拷贝）。
- **修法**：把新文件名加进脚本的 `for` 列表；编完用 `strings` / `grep` 验证旋钮或日志串在不在。

#### 5.1.3 模块产物找不到
- **症状**：`O=` 目录里翻不到 `ath10k_core.ko` / `ipa.ko`。
- **根因**：`M=` 外部模块构建的产物落在**源码树**的对应目录。
- **修法**：去 `$SRC/drivers/net/.../` 下找。

#### 5.1.4 apt 被超时掐断后锁死 dpkg
- **症状**：`Could not get lock /var/lib/dpkg/lock-frontend`，但没别的 apt 在跑。
- **根因**：前台命令被 `SIGTERM` 后，`apt-get` 子进程**没死**，继续下载并持锁。
- **修法**：`ps -ef | grep apt` 找到它，等它跑完（别 kill，会留半装状态）。
  **以后长 apt 一律后台跑**。

#### 5.1.5 脚本上机后报「找不到解释器」
- **症状**：`bad interpreter: /bin/sh^M`。
- **根因**：Windows 编辑产生 CRLF。
- **修法**：`sed -i 's/\r$//' file`；或 `git config core.autocrlf false`。

#### 5.1.6 可执行文件没有 +x
- **症状**：`Permission denied`。
- **根因**：打包/解包（`tar`、网盘、git）丢权限位。
- **修法**：`chmod 755`。仓库里的安装脚本都会显式 `chmod`。

#### 5.1.7 用 md5 比对，三边结果不一样
- **根因**：WSL / Windows / 设备三处换行与文件系统不同。
- **修法**：只在**同一环境内**比 md5；跨环境比 `sha256sum` 或直接比大小+行为。

### 5.2 内核配置类（最贵的一类：伪装成无关故障）

#### 5.2.1 所有容器都起不来
- **症状**：`docker run --rm alpine:3.20 echo OK` 失败，
  `runc` 报 `bpf_prog_query(BPF_CGROUP_DEVICE) failed: invalid argument`。
- **根因**：缺 `CONFIG_CGROUP_BPF=y`。cgroup v2 的 device controller 需要
  `BPF_PROG_TYPE_CGROUP_DEVICE`。
- **修法**：打开该项重编内核。
- **教训**：容器起不来**先用最小镜像验证是不是全盘性故障**，别去重装应用。

#### 5.2.2 开机卡死在 UFS 等待循环
- **症状**：内核日志停在 UFS 探测，永远等 supplier。
- **根因**：`CONFIG_RPMSG_QCOM_SMD=m`（应该是 `=y`）。它是 `QCOM_SMD_RPM` /
  `QCOM_RPMPD` / `REGULATOR_QCOM_SMD_RPM` / `INTERCONNECT_QCOM_*` 的 `depends on`，
  一旦 `=m`，`olddefconfig` 会**连带**把这些压成模块；而这些是 UFS 的供电/时钟/互连 supplier，
  UFS 永远等不到 → 卡死。
- **修法**：改成 `=y`。
- **教训**：`=m` 与 `=y` 在 diff 里只差一个字符，后果是开不了机。**改完 defconfig 必须逐行 diff**。

### 5.3 启动 / 系统类

| 症状 | 根因 | 修法 |
|---|---|---|
| 开机 82 分钟 | 串口上的 `agetty` 阻塞了 systemd PID1 | 给 `ttyGS0` 的 agetty 加 `--noreset --noclear`，或直接不用 |
| `usb0` 开机没 IP | NetworkManager 不管这个接口 | 显式 `nmcli` 托管或写 `ipv4.method manual` |
| USB 网卡自启把开机卡死 | 自启脚本在等一个还没起来的接口 | 加 `After=`/重试，别在 `ExecStart` 里死等 |
| 设备重启后 ICS 失效 | ICS 是运行时状态，不持久 | 开机脚本重建 |
| `resolv.conf` 变空 | NetworkManager 覆盖 | 写 `/etc/NetworkManager/conf.d/` 或禁用其 DNS 管理 |
| 能 ping IP、域名全解析失败 | ICS 的 DNS 代理静默失效 | 见 [修复记录.md](修复记录.md) §15 |
| 高 IO 整机硬卡死、从 USB 消失 | RCU stall | 备份/编译错峰；见 [日志与取证.md](日志与取证.md) |
| 卡死那一段日志「凭空消失」 | **journald 也是用户态进程**，一起死了 | 用 `z17s-logwatch` 把 kmsg 落盘 |
| 「半死态」：网络通、老服务正常、新会话建不起来 | 见 [修复记录.md](修复记录.md) §17 | 同上 |
| `ttyGS0` 上 agetty 反复重启打 `gs_close` WARN | 串口被 agetty 和 gadget 抢 | 关掉串口 agetty |

### 5.4 Wi-Fi 类

#### 5.4.1 换了 `/lib/modules` 里的 ko，重启后又变回原厂
- **症状**：拷进去 md5 是对的，重启后 mtime 回到 1970、大小回到 549312。
- **根因**：**`/lib/modules` 每次开机被引导镜像还原**。
- **修法**：加开机复制单元 `z17s-ath10k-ko.service`（形状照抄项目里已有的 QMI helper 单元）。

#### 5.4.2 「高传输就卡死」，而且连带把 modem 打死
- **症状**：跑几十 MB 后 Wi-Fi 死，接着 modem 也没了，只能物理断电。
- **根因**：固件把一个 A-MSDU **拆到两条 in-order 指示**里 →
  `extract_amsdu()` 返 `-EAGAIN` → `in_ord_ind()` 当成致命错误置 `rx_confused`
  → 之后每条指示 `-EIO` → NAPI 空转 → RX 环枯竭 → 固件崩 → **ADSP 崩（WCN3990 挂在 ADSP 上）
  → modem 跟着崩**。
- **修法**：`-EAGAIN` 只丢这一小段、**不置 `rx_confused`**、返 0。只改 `htt_rx.c`。
- **教训**：「硬加密必崩」和「软解是唯一出路」两条旧结论**都作废** —— 硬件加密完全正常，
  软解反而连不上。

#### 5.4.3 `rmmod ath10k_snoc` 之后 modem 死了
- **根因**：WCN3990 在 ADSP 上，卸载会把 ADSP 一起带走。
- **修法**：**永远不要 `rmmod ath10k_snoc`**。要换 ko 就断电重启。

#### 5.4.4 判断不了当前跑的是哪个 ko
- **症状**：`coresize` 两个版本一样（页对齐），`modinfo` 也看不出来。
- **修法**：看补丁自带的 `pr_info("Z17S ath10k: split-A-MSDU tolerance active")`。

#### 5.4.5 测速「Wi-Fi 不通」
- **症状**：`curl --interface 192.168.1.132 …` 全部 `000`，超时。
- **根因**：按**源 IP** 绑定不限制出接口，而 `default dev rmnet0 metric 50` 抢先匹配路由，
  源地址与出接口不一致 → 连接失败。
- **修法**：`curl --interface wlan0`（按**设备名**绑定）。

### 5.5 蜂窝 / IPA 类（最难的一段）

#### 5.5.1 「假连接」：`rmnet0` 有 IP，但根本不通
- **症状**：`ip -4 addr show rmnet0` 有地址，`ping` 却 100% 丢包。
- **根因**：残留状态 / 呼叫没真正建立 / insmod 太早。
- **判据**：**只看 `tx_pkts_ok`**（modem 侧计数）。
  `grep tx_pkts_ok /root/z17s-call.log | tail -1` 非 0 才算真连接。
  AP 侧的 ch5 TX 完成事件即使 modem 没建呼叫也会正常回环，会骗人。
- **修法**：按 §2.5 顺序重来；必要时物理断电。

#### 5.5.2 `insmod` 太早 → 假连接
- **根因**：必须晚于 modem `online` **且** `registered`。早加载会让 modem 侧 GSI 通道不启动。
- **修法**：`z17s-up.sh` 里先等 `--nas-get-serving-system` 报 `registered`，再 `POSTREG=30` 后 insmod。
- **注意**：**不是「必须等固定时间」**，只是顺序依赖。所以 `TARGET` 从 410 降到 90 完全没问题（§6.3）。

#### 5.5.3 下行只有 2.3 KB/s（只上送 38%）
- **根因**：**ep16 聚合**。IPA 硬件把下行多包聚合成一帧，但只写第一个包的 QMAP 长度，
  `rmnet_map_ingress_handler()` 只 trim 到该长度就上送，**其余整段丢弃**。
- **修法**：`echo "16 0" > /sys/module/ipa/parameters/z17s_aggr_reg`（关聚合）。
  改后 2.3 KB/s → 332–374 KB/s。
- **固化**：`z17s-up.sh` 的 `[5c]`（建呼叫前）和 `[10]`（呼叫活着时二次确认）。
  ★ `[10]` 里取 `dmesg | grep Z17SAGGRREG | tail -2 | head -1` —— `tail -1` 拿到的是
  `wrote=` 那行，会误报。

#### 5.5.4 换卡后 modem 初始化不了
- **结论**：**新卡不兼容这版固件**（2017 年的固件）。只能换回旧卡。
- **换卡纪律**：必须**断电换**，不能热插。

#### 5.5.5 modem 卡在 `shutting-down`
- **修法**：先发一次 `--dms-set-operating-mode=online`，它会自己走完。
- **另一形态**：online 却一直 `not-registered-searching` / `limited` ⇒
  `--dms-set-operating-mode=low-power` → 等 8 s → `online`，实测 75 s 内恢复。
  （`low-power` ≠ `offline`，可用。）

#### 5.5.6 同一 mux 建第二条呼叫 → 崩 mss
- **症状**：`ds_rmnet_meta_sm.c:5285 Assertion 0`，只能物理断电。
- **根因**：`pkill qmi87.py` **不会** `stop_network`，旧 bearer 还留在 modem 里。
- **修法**：一个 boot 内**绝不**对同一 mux 建第二条呼叫。`rmnet0` 每 boot 必须重建。

#### 5.5.7 `ipa.ko` 三个版本别搞混
| 文件 | md5 | 结论 |
|---|---|---|
| `ipa-new-147.ko` | `9acc6dc6` | ✅ 在用 |
| `ipa-new-148.ko` | `7a6a94ec` | ❌ 实测不可用（§5.5.8） |
| `ipa-z17s-148.ko` | `73bae150` | ❌ `z17s_aggr_reg` 任何 ep 都 EINVAL |

#### 5.5.8 `ipa-new-148.ko`：文件大小一样，但 ABI 错位
- **症状**：insmod 成功、`ipa_setup` 打出与 147 逐字相同的
  `filter_count=14 route_count=15 filtered=0x228 rt_base=16`，但
  `[5b]/[5c]` 全 `EINVAL`、`ping` 100% 丢包、**`tx_pkts_ok=0`**。
- **根因**：`z17s_aggr_reg` 参数存在但只接受 `ep=0`；处理函数第一道检查是
  `if (ep >= ipa->endpoint_count) return -EINVAL;` ⇒ **`endpoint_count` 读出 1**。
  两个 ko 大小完全一样（591152 B），只能是 `struct ipa` 与运行内核的头文件/配置不一致，
  字段偏移全错。
- **教训（两条反直觉）**：
  1. 「文件大小相同 + md5 不同」**不能**当作「只改了一点点」的证据；
  2. `ipa_setup` 那行 QMI 规则日志与 `struct ipa` 内存布局**无关**，一致不代表没问题。

#### 5.5.9 极易误判的假象
| 现象 | 真相 |
|---|---|
| `ridx=249 / avail=0` | 正常残留 |
| `Slot[2] no-atr` | 空槽 |
| `tre_reserve FAIL` | RX ring 满的正常表现，**不是错误** |
| `Z17SMEM` | AP 自己的 staging |
| `--wds-get-packet-service-status` | per-client，不代表整机 |
| `--wds-get-current-settings` 报 `OutOfCall` | 这版固件不支持，正常 |
| `--wds-get-data-bearer-technology` 报 `InvalidQmiCommand (71)` | 同上 |
| `dmesg -c` 之后 `grep -c "dropped partial A-MSDU"` = 0 | **清环假象**（`z17s-up.sh [10]` 会 `dmesg -c`），判崩看 `firmware crashed` |

### 5.6 短信类

#### 5.6.1 必须用 `mmcli`，`qmicli` 不行
- `qmicli` 1.36.0 的 WMS 只实现了 `get-supported-messages` / `get-routes` / `set-routes` /
  `reset` / `noop`，**没有 list / get / send**。

#### 5.6.2 `mmcli -s N` 显示 `text: ??`
- **不是解码问题**，是终端 locale。`busctl get-property … Sms Text` 返回正确 UTF-8。

#### 5.6.3 原版 DbusSmsForwardCPlus 在 MM 1.24 上完全不可用（3 个 bug）
| # | bug | 后果 |
|---|---|---|
| 1 | `Create` 的 modem 路径写死 `Modem/0` | 本机是 `Modem/1` ⇒ `UnknownMethod`，`Send` 压根没执行，**而 webapi 无条件回 `ok`** |
| 2 | `dbus_bus_add_match` 规则里也写死 `path=…/Modem/0` | 一条 `Added` 信号都收不到 ⇒ 转发永不触发 |
| 3 | 收发共用 `dbus_bus_get` 的**共享连接**，超时传 `-1` | 监听线程抢走回复 ⇒ 发送线程永久挂死 |
- **修法**：`ObjectManager.GetManagedObjects` 动态取路径；match 规则只按 `interface`；
  发送侧改 `dbus_bus_get_private()` + 超时 30000。

#### 5.6.4 `getModemPath()` 读 `Modems` 属性失败
- **根因**：**MM 1.24 删掉了 manager 的 `Modems` 属性**，manager 接口也从
  `…ModemManager1.ModemManager` 改名成 `…ModemManager1`。
- **修法**：用 `GetManagedObjects` 扫 `…/Modem/N`。

#### 5.6.5 `dbus_message_append_args` 传字符串出错
- **根因**：对 `DBUS_TYPE_STRING` 应传 `ptr`，不是 `&ptr`（va_arg 语义）。
- **修法**：改用 `dbus_message_iter_append_basic`。

#### 5.6.6 API 回 `fail`，但短信其实发出去了
- **根因**：`Send` 的 D-Bus 回复**偶发超过 15 s**（实测 15.1 s 才回）。
- **修法**：超时 15000 → 30000；网页按真实返回弹窗。
- **纪律**：**回 `fail` 不等于没发出**，先 `mmcli -m 1 --messaging-list-sms` 确认，别重发。

#### 5.6.7 开机没网时来的短信永久丢失
- **根因**：蜂窝要 172 s 才有 IP，这期间 `wecom.py` 第一次 POST 必失败，原来直接放弃。
- **修法**：重试 3 次（0/3/10 s）→ 落 `/root/sms/wecom-pending.jsonl` →
  `z17s-sms-replay.timer` 每 5 min 补发。

#### 5.6.8 转发会把插件的 D-Bus 信号线程卡住
- **根因**：插件用**阻塞的** `system(ShellPath)`（`ProcessSmsSend/smsforwardmethod.h:510`），
  前台跑 `wecom.py` 最多卡 13 s。
- **修法**：`forward.sh` 里改成 `( … ) &` 后台执行。

#### 5.6.9 删短信报 `Couldn't delete 1 parts`
- **修法**：传完整路径 `--messaging-delete-sms=/org/freedesktop/ModemManager1/SMS/N`（传序号会失败）。

#### 5.6.10 `--messaging-create-sms` 属性串里有空格就报错
- **根因**：属性串是**逗号分隔**的，`text=` 里不能有空格。
- **修法**：`text=z17s_sms_test,number=10086`。

### 5.7 显示类

#### 5.7.1 `echo 4 > fb0/blank` 之后一堆 DPU 错误
- **症状**：立刻 13 条 `[dpu error]vblank timeout` / `wait for commit done returned -110` /
  `enc32 frame done timeout`，屏幕并没有干净关掉。
- **根因**：本机 mdss/dpu 的 atomic commit 在 blank 时超时（`-110` = `-ETIMEDOUT`），
  显示栈不完整。另外 `cat fb0/blank` 读出来是**空**，这个属性基本是摆设。
- **修法**：**只关背光**（`/sys/class/backlight/backlight`，max 4095 / 默认 2048），
  纯 LED 亮度，不触发 DRM commit。`z17s-screen off|on|status`。

### 5.8 方法论类（省时间的经验）

| 经验 | 说明 |
|---|---|
| **把可疑逻辑抽成 20 行独立 C 程序** | 设备上编 C++ 要 3.5 分钟；`gcc -O1` 秒级验证 D-Bus 逻辑，确认对了再写回大文件 |
| **时序一律用 dmesg 单调时间 + `/proc/uptime`** | wall clock 有 NTP 跳变，会得出错误结论 |
| **判活看计数器，不看链路状态** | `rmnet0` 有 IP / `wlan0 connected` 都会骗人 |
| **先做「零成本」的排除** | 例如 Wi-Fi 先试 `power_save off`、`dyndbg`，再考虑重编 |
| **一次只改一个变量** | 本项目多次因为「同时改两处」而误判 |
| **改完必须回滚预案** | 每个 ko / 配置都留 `.bak`，并写清回滚命令 |
| **文档即证据** | 每个结论都要带实测数字，否则下次会重新怀疑一遍 |

## 6 判据速查（怎么确认「真的通了」）

### 6.1 三层判据（蜂窝，缺一不可）

| 层 | 命令 | 通过标准 |
|---|---|---|
| modem 侧 | `grep tx_pkts_ok /root/z17s-call.log \| tail -1` | **非 0，且持续增长**（唯一可信） |

| 路由 | `ip route get 223.5.5.5` | 显示 `dev rmnet0` |

### 6.2 Wi-Fi

## 7 红线清单（违反即崩 modem / 丢数据 / 开不了机）

### 7.1 电源

1. **收尾一律物理断电**（长按电源 10–15 s），**禁止 `reboot`**（会卡在 `alsactl`）。
2. 断电前 `sync; sync; sync` 并等 5 s。
3. **换 SIM 卡必须断电换**。

### 7.2 IPA / modem

4. **`ip link set rmnet_ipa0 down` 无条件致命**（G4 那次冻死整机的问题没有根治，方案是绕开它）。
5. 严禁热卸载 / 热重载 `ipa.ko`；严禁 modem `stop`/`start`。
6. 严禁运行期 GSI / TABLE_INIT。
7. 严禁 `z17s_ep_cycle` / `z17s_gsi_ee*`（读 EE≥1 会总线中止）/ `z17s_patch_dst_ep` /
   `z17s_ready_go` / `z17s_uc_force`。
8. **同一 mux 绝不建第二条呼叫**。
9. `0x24` 每 boot 最多 1 条；DIAG 只发 `\x00`(VERNO)；**`0x7D op=5` 禁用**；
   F3 掩码**绝不能全开**。
10. `diag-router` **绝不 `restart`**（只 `stop` + `disable`）。

### 7.3 Wi-Fi

11. **绝不 `rmmod ath10k_snoc`**（会把 ADSP 和 modem 一起带走）。

### 7.4 显示

12. **绝不写 `fb0/blank`**（触发 DPU commit 超时）。

### 7.5 系统

13. **不要 `systemctl restart ModemManager`** —— 会重新枚举模组、`rmnet0` 掉线，
    蜂窝要重建呼叫（同一 mux 不能建第二条）。
14. 不要动 `persist` 分区。

│  ├─ 没有 ──> modem 注册了吗？

│  │           │   └─> 卡的问题（新卡不兼容 / 换卡没断电）
│  │           ├─ --dms-get-operating-mode 是 'shutting-down'
│  │           │   └─> 先发一次 online
│  │           └─ --nas-get-serving-system 不是 'registered'
│  │               └─> low-power → 等 8 s → online
│  └─ 有 IP ──> tx_pkts_ok 非 0 吗？
│              ├─ 是 ──> 真连接，继续查应用层
│              └─ 否 ──> 假连接
│                        ├─ insmod 早于 registered？ ──> 顺序问题

   ├─ 先量：单流 / 4 路并发 / 换服务器
   ├─ 并发 ≈ 单流 ⇒ 管道上限（套餐限速，本项目就是 3 Mbit/s，已打满）
   └─ 并发明显更高 ⇒ 单流受限（窗口 / RTT）

Wi-Fi 不通
├─ dmesg 有 "firmware crashed"？ ──> 补丁 ko 没生效（查 /lib/modules 是否被还原）
├─ 有 "Z17S ath10k: split-A-MSDU tolerance active"？
│  └─ 没有 ──> 跑的是原厂 ko
├─ iw dev wlan0 link 无 SSID ──> 关联失败（看 regdb / 信道）
